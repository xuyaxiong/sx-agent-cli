## 一、先分清两类文件（**维护方式完全不同**）

| 类别 | 有哪些 | 怎么维护 |
|---|---|---|
| **现行的**<br>描述"**现在**是什么样" | `solution.md` · `principles.md` · `scenarios.md` · `architecture-diagram.md` · `architecture-review.md` | **改了就直接改** —— 它必须反映当下，过时的内容要删或改写 |
| **历史的**<br>记录"**当时**怎么想、发现了什么" | `discussion-log.md` | **只追加，不改旧条目** —— 结论变了就新写一条并标明"取代了上面某条" |

> 🔴 **混用会出事**：
> 把"现行规定"写进日志 → 后人分不清哪句还有效；
> 把"当时的判断"写进方案文档 → 看着像现行规定，其实是废案。

## 二、我要写东西，写到哪？

| 我要写的东西 | 写到哪 | 怎么加 |
|---|---|---|
| 一次讨论的要点 / 关键决策 | `discussion-log.md`「**一、讨论记录**」 | **追加**一条 `YYYY-MM-DD · 第 N 次` |
| 实测发现 / 踩坑 / 修法 / 教训 | `discussion-log.md`「**二、实测发现**」 | **追加**一条 `F<N>`（现象 / 根因 / 证据链 / 修法） |
| 推演过程（当时的想法、已被取代的草案） | `discussion-log.md`「**三、推演过程**」 | 追加；**§ 编号保持原样**（旧引用对得上） |
| 需求变了 / 新增需求 | `solution.md` **§0.6 需求清单** | **改**（就地更新，每条标来源） |
| 设计 / 机制变了 | `solution.md` 对应章节 | **改** |
| 提示词改了 | **`proto/executor.py` 里的常量**（真值在代码） | 代码；只有"调优方向"变了才动 `solution.md` §十一 |
| 新场景 / 某条场景状态变了 | `scenarios.md` **和** `evals/cases/` | **两边都改**（人读版 ↔ 可执行版） |
| 架构图变了 | `architecture-diagram.md` + `figures/*.svg` | 🔴 **先改文档、再照它画图**（文档是唯一依据；图**只出 SVG**） |
| 某个交接的内容变了 / 多了一处 LLM 判定 | `architecture-diagram.md` **§三 数据交接** / **§四 软判断·硬判断** | **改**（这两节是"现状说明书"的承重墙） |
| 交接的**截断 / 落点**变了（加一处切片、调阈值、换载体） | `handoff-audit.md` | **改**（§一总账 ＋ 那一跳的详查；§五 隐患清单**修了就标"已修"，不删条目**） |
| 评审点有了新结论 | `architecture-review.md` | **改** |
| 处事原则变了 | `principles.md` | **改** |

> 🔴 **一条硬规矩：改了机制，同时落两处** ——
> 「发现 / 决策」进 `discussion-log.md`，「方案」进 `solution.md`。
> **只写代码不写文档，后人只看得见现状、看不见理由**（会在同一个地方再踩一次，
> 或者把有意为之的设计当成 bug 改掉）。

## 五、三条使用规矩

**① 改设计前先看需求清单**（`solution.md` §0.6）

> **某条需求如果被某个设计牺牲了，必须显式说明，不能悄悄丢。**

**② 每次架构迭代后跑一遍回归集**（`scenarios.md`）

> 架构迭代最容易"**修好一个、弄坏一个**"。
> 本次实测：去掉 `load_skill` 修好 S12，却立刻暴露 S13、S14。

**③ 结论必须实测，优先真实模型**

> 这半天里几乎每一条"想当然"都被实测推翻过（见 `principles.md` ③）。

## 六、提交规范

```
<type>(<scope>): <简短描述>

- <详细说明>
- <详细说明>
```

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `refactor` | 重构 |
| `perf` | 性能优化 |
| `style` | 格式调整 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建 / 工具链 / 依赖 |

**scope** 示例：`agent` · `executor` · `graph` · `skill` · `trace` · `evals` · `docs`

**三条纪律**（用户 2026-10-30：*"提交信息太随意了 格式不规范 内容也很冗长"*）：

1. **首行 = `<type>(<scope>): 简短描述`**，不写"这次我们……""重做：……"这类叙述
2. **正文用 `- ` 列表，一条一句** —— 不写小作文、不贴长段推理
3. **细节不往提交信息里塞** —— 过程与证据进 `discussion-log.md`，方案进 `solution.md`；
   提交信息只留"做了什么"，需要时**指路**（如 `见 discussion-log F15`）

> ⚠️ 第 3 条和"变更要能追溯到发现"**不冲突**：追溯靠**文档**，不靠提交信息的长短。
> 提交信息写长了，等于把文档抄了一份到 git 历史里 —— 两边都会漂。

## 七、配套代码

```
../proto/          最小原型（可运行，**两个领域 + 加载**，见下）
├── config.py      模型配置（环境变量 / .env）+ **应用根**（冻结后 = exe 目录）
├── llm.py         结构化输出 + 兜底
│
├── skills.py      【技能领域】Skill 是什么 + read_skill
│
├── handoff/       【交接】**一个交接点 = 一个模块 = schema ＋ 模板**（高内聚，2026-11-03 拆出）
│   ├── __init__.py  共享词汇表：段名 / 来源标注 / 出口分类 / 平台注入标记 / 每跳用哪几段
│   │                （**唯一来源** —— 渲染器与记录层共用，改段名 = 改提示词，要实测）
│   ├── briefing.py  委托单（平台 → 执行器）：Task / Turn / QA schema ＋ render_briefing
│   ├── receipt.py   回执（执行器 → 主 agent）：Receipt schema ＋ build/render_receipt
│   ├── ledger.py    台账（平台 → 主 agent）：stage 词表 ＋ render_ledger（**唯一故意短**的一跳）
│   │   ⚠️ `judgement.py`（判定）**2026-11-05 整个删了** —— 三态改由平台按**结构**定，
│   │      见 `architecture-diagram.md` §三 的交接表与 `executor._structural_status`
│   ├── nudge.py     推回去（平台 → 执行器）：nudge_text
│   └── ask.py       试答（平台 → 主 agent）：build_prompt（**全部消息、不截**）
│
│   ⚠️ 搬完 `executor.py` 只剩**执行循环**；`agent.py` 只剩**工具与编排**
├── skill_pack.py  【技能包】文件夹形态 → Skill + 自带文件的列/读 —— I/O + 格式，换存储只动这里
├── artifacts.py   【产物领域】产物库 + 类型派发 + 落盘 + write/read/list_artifact
│
├── executor.py    执行器（三态**按结构**定 + 出口限制 + `ask_user` 申报口）
├── agent.py       主 agent（工具 + 系统提示 + 交接书渲染）
├── graph.py       图（feed / prepare / agent / finalize）
├── trace.py       全量日志
└── __main__.py    交互式 CLI

> 🔴 **技能 ≠ 产物**（2026-10-30 分开）：Skill 是**静态技能包**，产物是**运行期交付物** ——
> 变化的原因完全不同，原来挤在一个文件里（叫"Skill 定义 + 产物库"），边界不清。

../evals/          跑批回归 —— case / 断言 / 评分 / 运行记录（见其 README）
│                  ★ 每次跑完，一个 run 一份 `_run.md`：逐轮全记录 + 软判断留档 + 原始 trace
├── harness.py     装配 + 记录层（交互式与跑批共用）+ 路径约定
├── chat.py        交互式入口（**你当用户**，F5 直接起）
└── cases/         场景的可执行版本（与 `docs/scenarios.md` 两边都改）

../experiments/    推演期的实验与诊断脚本（几个已跑不起来，见其 README）

../logs/           每次运行的原始 trace（含 LLM 原文）
```

**跑起来**：

```bash
cd langgraph-lab
uv run python -m evals.chat --skills evals/skills  # 交互式（技能来自文件夹，不再绑 case）
uv run python -m evals.run --tag baseline         # 跑批
uv run python -m proto                            # 裸原型（内置玩具技能）
```

> ⚠️ **没有 fake / 离线模式** —— 所有 LLM 调用都走真实模型。

**VS Code**：打开 **`agents-ref` 文件夹**（根），F5 选「交互式跑（你当用户）」。
配置在 `agents-ref/.vscode/`（**不在本项目里**，用户选的布局）；
**改 CLI 参数时记得同步它**（踩过：`--case` 改成 `--skills` 之后 F5 起不来）。
