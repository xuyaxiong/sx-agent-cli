### 2026-10-28 · 第十三次（补上「只说不做」的保险）

- 用户总结理解："判断正文，是提问就转提问，是完成就转 finish，不让它莫名其妙输出正文结束"

- **用户提出关键问题**：产物不止一种。除了落库文件，还有一类是

**修法**（三条路径合成一条）：

| | 之前 | 之后 |
|---|---|---|
| 交接内容 | 三条路径各拼各的，漏了答复 | **`agent.render_briefing(task)` 唯一入口** |

| 护栏 | 无 —— **全靠人记得** | **`evals/unit_briefing.py`**：每个非排除字段必须出现在渲染里，排除项要写理由 |

> 📌 **这一轮的元教训**：三条架构原则里，前两条是**结构性**的（代码长成那样就自动满足），
> 第三条是**纪律性**的 —— **事故恰好出在唯一没有机制保障的那条上**。
> 凡是靠记性守的原则，迟早会破。

## 为什么之前没发现

`scenarios.md` 是**单次采样**：每条场景手工跑 1 次，人读日志判对错。
这测的是"**能不能做到**"，不是"**稳不稳**"。

三个因素叠加，让下面这些问题全部隐形了：

1. **n=1** —— 概率性的问题会被当成"通过"
2. **玩具技能** —— 4 个内置技能都写着"150 字以内"，产出永远够不到 `_clip` 的 800 字预算
3. **人读日志** —— 只看"结论对不对"，不看"花了多少轮、写了几份产物"

第 2 条最致命：**长内容不只是"看不出隔离效果"，它还会触发一条完全不同的代码路径。**

## 🔴 F1 · 平台的截断标记，被判定当成了作者的占位符

### 现象

一个 11,953 字、内容**完整**的教案，被判成 `incomplete`。判定的 `missing` 原文：

> 产物中教案主体内容被省略了（"**此处省略 11153 字**"），实际并未提供完整的教学过程…

### 根因

`executor._clip()` 为了控制判定提示词的体积，把产物截到 800 字，中间插入：

```
……（此处省略 11153 字）……
```

而判定规则（`_JUDGE_RULES` 第 1 条）写着：

> 占位内容、待补充项、半成品（如「待补充」「TODO」「待填写」）**不能视为完成**

**判定把平台自己写的截断标记，当成了作者偷懒的占位符。**

### 证据链（可复核）

| 证据 | 位置 |
|---|---|
| 判定引用的数字 = `len(产物) - 800` | `art_002` 实际 5192 字，判定说"此处省略 **4392** 字"，`5192-800=4392` ✅ |
| 执行器**自己读回产物、发现是完整的** | 日志原文："我刚刚通过 `read_artifact` 读回了完整内容…**并未出现**「此处省略 4392 字」的标注" |
| 标记由平台生成 | `executor.py` 的 `_clip()` |

### 后果（实测）

| 场景 | 表现 |
|---|---|
| **s13**（一份长教案） | 3 轮判定全 incomplete → 推回去 3 次 → **写了 3 份重复教案**（11,953 + 15,280 + 7,292 字）→ 最终 `failed`。**607 秒 / 144k token** |
| **e13**（3 个并行任务） | 产物 4–5 个（应为 3 个）→ **单 run 79k token**。对照：不强制长产出时只要 **9.7k** —— **约 8 倍** |

### ⚠️ 它不是确定性的

同一轮里 `guided-learning` 判 completed、`lesson-prep` 判 incomplete。
**概率性触发**比确定性 bug 更糟 —— 它看起来像"偶发"，容易被归到"模型不稳定"。

### 为什么这是最该先修的

它是**整个基线里最大的成本项**，而且**产物越长越必然触发** ——
而"产物长"恰恰是这个架构要支持的正常场景。

### 修法与实测（`experiments/debug_clip_marker.py`）

我第一版修法是"改标记措辞 + 在判定规则里加说明"。**实测证明那个修法是有害的** ——
它把假阴性换成了假阳性。真正的修法是**调预算**。

**A/B（3 次采样）**：固定一个内容完整的 3112 字产物，只变"判定看到什么"。

| 变体 | 完整产物→`completed` | 真占位符→`incomplete` |
|---|---|---|
| **A 修复前**（旧标记+旧规则） | 🔴 0/3 | ✅ 3/3 |
| **B 只改标记** | ✅ 3/3 | 🔴 **0/3** |
| **C 标记+说明**（我的第一版） | ✅ 3/3 | 🔴 **0/3** |
| **D 不截断** | ✅ 3/3 | ✅ 3/3 |

> A 在反例上"判对"是**蒙对的** —— 它用同一个错误理由（"看到省略标记 → 判半成品"）蒙对了另一列。
> 而 B/C 让判定开始接受真正残缺的产物。**两列是一起看的，只看一列会得出完全相反的结论。**

**预算扫描**（标记用修复后的）：

| `JUDGE_ITEM_BUDGET` | 截断？ | 完整→`completed` | 真占位符→`incomplete` |
|---|---|---|---|
| 800（原值） | 是 | 3/3 | **0/3** |
| 1600 | 是 | 3/3 | 1/3 |
| 2400 | 是 | 3/3 | 2/3 |
| **4000** | 否 | 3/3 | **3/3** |

**单调** —— 判定判得准不准，基本取决于它能不能看到全文。
800 字时，反例里那两个真占位符（在 40% 和 75% 处）**正好落在被截掉的中段**，
判定根本没机会看到它们。

### 已落地的修法

1. **`JUDGE_ITEM_BUDGET` 800 → 4000，`JUDGE_TOTAL_BUDGET` 4000 → 16000**
   —— 这才是真正起作用的那一处
2. 标记措辞改成**只说平台知道的事实**：
   「你无法看到这部分，别仅凭'看不到'判未完成；但在看得到的地方发现占位符，照常判未完成」
   —— 不写"内容完整"（平台不知道，那是在替判定下结论）

> ⚠️ **但要说清楚这只把门槛往后挪了。** 产物再长（48k 课件）还是会截断，
> **截断之后判定就没有能力验证完整性** —— 那时它给的"完成"是**推测**，不是判断。
> 代码里 `_judge_material` 的 TODO（`need_more`：有界补看）正是为这种情况留的。

### 🔴 这件事的**最终真值只能靠人工审计**

上面所有数字都是拿"我造的"两个样本测的。真实产物完不完整，**判定说了不算**。
所以 `evals/` 现在会把**产物原文落盘**（`runs/<tag>/artifacts/<case>__r<rep>/`），
人可以直接看。**下一轮该做的是：人工标注一批产物的完整性，再回头量判定的准确率** ——
那才是"判定准不准"的真数字。

## 🟡 F4 · 协议块被主 agent 改写成表格 → 调用方解析不了

### 现象（`s07` r2，3 次里 1 次）

执行器交付得很正确：

````
```courseware-config
{"grade": "三年级", "subject": "数学", "topic": "分数的初步认识", "slides": 6}
```
````

主 agent 转达给用户的是：

> 已为您生成…课件配置，共 6 页，概览如下：
> | 页码 | 标题 | 核心内容 |
> …
> 以上课件配置已标注每页的版式建议…**可直接交给调用方解析使用**。

**它说"可直接交给调用方解析"，但真正能解析的那个块没了。**

### 根因

`delegate` 返回的是「**请原样转达**」+ 执行器的完整 `report`。

## 🟢 F5 · 并发竞态：机制真实，但实测撞不上

### 代码上的窗口

```python
aid = f"art_{len(ARTIFACTS) + 1:03d}"   # ① 算
ARTIFACTS[aid] = {...}                  # ② 写
```

先查后写。两个执行器同时算 ① 会拿到同一个 ID，**后者覆盖前者，产物静默丢失**。

### 实测

| 测法 | 结果 |
|---|---|
| 端到端（3 个并行 delegate） | 0/3 撞上。**写入时间戳间隔 4–205 秒**（每次写入前有几十秒 LLM 生成） |
| 单元（屏障同步 + `setswitchinterval(1e-6)`，24000 次写入） | **0 次撞上** |
| **对照**（人为把窗口撑开） | **撞掉 15,853 次** ✅ 说明测试**有**探测能力 |

**结论：风险真实，但窗口窄到压不出来。不是"安全"，是"难触发"。**

> 📌 **一个方法论教训**：我第一版有效性断言只数了"有几个线程"，它**绿了** ——
> 那是**假阳性**。多线程 ≠ 同时。改成看**时间间隔**才露出真相。
> 记在 `checks.py` 的 `artifact_writes_timing` 里。

## 🔴 F9 · `log` 每轮翻一倍（子图回吐 + reducer 叠加）

### 现象

`prepare` 明明只返回 3 条 log，`finalize` 进来却看到 8 条。
每轮翻一倍：`1 → 5 → 12 → 27 → …`（指数）。

### 根因

`agent` 是**子图**，`state_schema=State`（含 `log`）。
**子图会把它状态里的字段原样回吐给父图**，而父图 `log` 的 reducer 是 `operator.add`
→ 父图自己的 log 被子图又加了一遍。

`tasks` 不受影响 —— 它的 reducer 按 id 合并，是幂等的。

### ⚠️ 这是**既有** bug，不是新引入的

改动前的 `baseline` 日志就是 `[1, 5, 12]`，正好是翻倍序列。
**以前没暴露**，是因为那些 run 走了"主 agent 先问用户、不派发"的路径
（F3），`prepare` 直接返回 `{}`，**一条 log 都不产生**。

### 定位方式

`experiments/probe_double_prepare.py` —— 包一层节点，打印
"进入时 state.log 几条 / 返回时加了几条"。一跑就看出
`prepare` 返回 +3、`finalize` 却看到 8，中间那 4 条是子图加的。

### 修法

给主 agent 子图一个**不含 `log`** 的窄 schema（`AgentState`）。

> 📌 这条的教训和 F1 同源：**看不见，是因为路径没走到**。
> 场景覆盖不到的分支，bug 就一直在那儿。

## 🔴 F10 · 执行器会把「答非所问」当成答复，自己挑个默认值硬做

### 现象（`f7fix2/s08-topic-switch-keeps-pending__r1`）

平台把「算了，先帮我备一节课」原话投给待答的 quiz 任务后，执行器的回复是：

> 已完成！一份完整的《分数的初步认识》第一课时备课方案（**含 3 道随堂小题**）已写入产物库…
> 📝 **随堂小测（基础档）**…

它做了三件不该做的事：

1. **自己挑了「基础档」** —— 用户从没说过难度
2. **把"备课"揉进了小测任务** —— 那是另一个需求，不该它管
3. **声称完成** —— 产出了一份**基于未确认前提**的成品

### 它意味着什么

**F7 换了个地方复发**：不是主 agent 编参数，是**执行器将就着做**。

- 平台的机制是**对的**（问题透传了、答复投递了、待答没丢）
- 但平台**保证不了"执行器信息不全时不硬做"** —— 那取决于执行器遵不遵守技能里的
  「你需要知道 X——不知道就先问」

### 处理

**不是平台机制问题**，所以没在机制上管（那会变成替作者做判断）。
在 `executor._PLATFORM_RULE` 里补了针对性规则：

> ⚠️ **【用户答复】里不一定真的回答了你的问题**（用户可能换了个话题，或答非所问）。
> 拿到答复后先核对：**你缺的那项信息，它给了吗？**
> 没给 → 再问一次，**不要自己挑一个默认值硬做**；也不要顺手把答复里提到的**别的**需求做掉。

> 📌 **这一条属于"效果"，不属于"机制"。** 按 §0.6 ⑥「平台少约束作者」：
> 平台保证**形式能跑**（问题会到用户手上），**效果由作者迭代**。
> 这里补规则是因为它同时伤到了"不编造"这条平台级底线，不是为了替作者调效果。

## 🔴 F11 · 跨技能依赖没有结构化通道 → 主 agent 自己读全文再转述

**发现于**：`t2-same-turn` 首轮（2026-10-29，真实技能包，`--tag t2-probe`）。

### 现象

用户一条消息要三样（教案 / 导学单 / 交互网页），并明确要求后两样**参考教案内容**。
第 2 轮主上下文从 **1369 → 8817 字**（收尾时 9322），`main_ctx_under`（上限 8000）红了。

### 根因

执行器是**隔离上下文**，后序技能要拿到教案只有两条路：

1. 主 agent 在 `task` 文本里带上内容（**转述**）
2. 执行器自己 `read_artifact` —— 但它得先知道产物 ID

而平台**从没告诉主 agent 有第 2 条路**：`delegate` 的工具描述、主 agent 系统提示
都没提"执行器能读产物"。于是它走了唯一看起来可行的那条：自己 `read_artifact`
把 5162 字的教案读进上下文，再提炼成要点抄进两个 task。

### 证据链（当时只能反推 —— 这本身是问题，见 F13）

- 第 2 轮消息类型 = `Human, System, AI, ToolMessage, AI, ToolMessage, ToolMessage, AI`
  → **3 个 ToolMessage，但只有 2 次 delegate**；产物写入流水 3 次且标题都是执行器产的
  → 多出来那次工具调用只能是 `read_artifact`
- 上下文增量（+7448）≈ 教案字数（5162）+ 两段 task
- task 文本里的拼音写法（`莲蓬（lián peng）`…）与 `art_001` 逐字一致

### 后果

1. **隔离在这条链上让位** —— 5162 字永久占着主上下文
2. **转述失真** —— 对方拿到的是摘要，不是原文
3. 顺带**夹带了发明**（见 F12）

### 修法

`delegate(skill_name, task, artifacts=["art_001"])`：平台**当场校验 ID**（编的直接拒 + 给真实清单），
只把**清单**（ID/名称/字数/梗概）注入执行器，正文由执行器自己按需读。
依赖因此从"只能靠 LLM 评分判 task 文本"变成**可硬断言**（`task_refs_contain`）。

> 📌 **教训**：**没有结构化通道时，模型会自己找一条路，而那条路往往以牺牲架构目标为代价。**
> 光在提示词里写"不要读产物"没用 —— 它没有别的路可走。

## 🟡 F13 · 主 agent 的工具调用在日志里**没有任何痕迹**

**发现于**：复核 F11 时。结论是**推断**出来的，日志里查不到 —— 用户当场指出：
"谁干的你不要猜测，加强日志"。

`run_task` 会 `trace.dump_trace()` 把执行器的消息轨迹写进日志，
**主 agent 那一段没有对应的 dump** —— 它的 `delegate` / `read_artifact` / `write_artifact`

排查依赖类问题时只能靠"消息类型对不上"反推，而**推断不能当证据**。

### 修法

1. `graph.node_agent` 包一层：主 agent 每轮的消息轨迹 + 每个工具调用（名字 + 参数摘要）

3. `trace.tool_calls_of()` / `brief_args()`：短参数原样、长参数只留字数（正文不灌日志）

## 🔴 F14 · 执行器**读来的**产物，被算成**它交付的**

**发现于**：`t2-refs2`（F11 修法后的复测，2026-10-29）。

### 现象

guided-learning 只写了一份导学单，任务记录却是 `产出=['art_001', 'art_002']`；
interactive-webpage 同理 `['art_001', 'art_003']`。日志里判定也显示
「R03 判定看到：**2 个产物**（8223 字）」。

### 根因

`_recover_artifacts` 扫的是执行器**消息里出现过的产物 ID**。
新的依赖机制让执行器 `read_artifact("art_001")` 读前序产物 ——
读回来的正文里带着 `art_001` 这个字符串，于是被算成**它交付的**。

**这是 F11 的修法自己长出来的污染路径**：依赖传递让"读"变成常规动作，
而"读过什么"和"产出了什么"原来是同一份数据源（消息文本）—— 机制一改，旧口径就错了。

### 后果（三条都在核心链路上）

1. 主 agent 被告知「已交付 art_001, art_002」—— **台账失真**，它会以为前序产物是这次新产的
2. **判定取材跟着变**：有产物时判定看的是"产物正文"，于是**教案正文被当成这次任务的
   交付物**喂了进去（既费 token 又干扰判断）
3. `every_task_has_artifact` 这类断言可能被**假满足**（读到一份也算"有产物"）

### 修法

`run_task` 进来时快照 `preexisting = set(ARTIFACTS)`，`_recover_artifacts` **只认差集**。

> 📌 **教训**：新机制会长出新的污染路径。改机制时要回头问一句
> ——**哪些旧口径是建立在"旧机制不会这么做"之上的？**

## 🔴 F15 · 待答投递只带**最新一条**答复 → 同一个问题问两遍

**发现于**：**人在环**交互跑（2026-10-29，`evals/chat.py`，用户当场发现）。

### 现象

用户要"教案 + 导学单"，导学单技能按规格**一次问一个**：

```
问「这份导学单主要用在哪个环节？」→ 用户答「课前预习」
问「学生填写形式偏好？」          → 用户答「A」
→ **又问一遍「这份导学单主要用于哪个场景？」**
```

用户原话：*"你不是问过我吗…同样的问题问我两次 导学单用途"*。

### 根因

`graph._feed_waiting` 每次投递拼的是 `原始 task + **最新一条**用户消息`。
执行器是**隔离上下文、用完即弃** —— 每次投递都是一次全新的 `run_task`，
上一轮的答复**没有存在任何地方**，答第二个就把第一个冲掉了。

### 证据链（三次投递的提示词，逐字可查）

| 投递 | 提示词里带的答复 | 执行器的反应 |
|---|---|---|
| R03 | `课前预习` | 知道用途 → 问填写形式 ✅ |
| R04 | `A` | **用途没了** → 又问一遍用途 ❌ |
| R05 | `你不是问过我吗` | 还是不知道用途 → 再问 ❌ |

### ⚠️ 脚本化跑批**测不出来**

预置答复是一句话把两问都答了（"…导学单用在课前预习，填空形式…"），
恰好绕开了它。**这条是人在环测出来的** —— 记一笔：脚本化的"用户"太配合，
覆盖不到真实用户的节奏。

### 修法

答复**累积在 Task 上**（`answers` 列表），每次投递带上**全部历次答复**；
主 agent 试答补的 `agent_answer` 同理（同一类问题：用完即弃会被冲掉）。

### 但根因不止这一处 —— 同类还有四个字段

修完答复之后回头看，**Task 上"存了但没喂"的字段还有四个**：

| 字段 | 状态 |
|---|---|
| `progress` / `missing` | 早就在 Task 上（判定写的），**重入时没进提示词** |
| `report`（它上次说的话，含"它问过什么"） | 同上 |
| `artifacts`（已产出的产物） | 同上；且**非 completed 分支还会被丢掉**（写了产物但判成 waiting 时，Task 里记不下来） |

### 根治：一条渲染通道 + 一条覆盖断言

- **`agent.render_briefing(task)`** —— 首跑 / 试答后重跑 / 答复投递**三条路径共用**。
  之前是各拼各的，**漏一格没人知道**。
- **`evals/unit_briefing.py`** —— 覆盖断言：造一个**所有字段都填满**的 Task，
  断言**每个非排除字段的值都出现在渲染结果里**，排除名单**每项要写理由**。
  这把"状态必须显式落在 Task 上"从**纪律**变成**机制**（加字段忘了渲染就红）。
- `absorb_outcome()` —— 执行器返回后**四个字段一起写回 Task**（原来 `artifacts` 只在
  completed 分支写，非 completed 分支会丢）。

### 回归

- `evals/unit_briefing.py`（确定性）—— 已验：**把 `progress` 那块从渲染里摘掉 → 红**
- `evals/unit_feed_waiting.py`（确定性）—— 断言"投递的提示词 == `render_briefing(rec)`"
- `evals/cases/t3-split-answers.yaml`（真实 LLM）—— 技能"一次只问一个"、用户分两轮各答一个；
  带**有效性断言** `run_task_count_over`（它必须真的分了两次问，否则这条没压到重入路径）

> 📌 **教训**：**"用完即弃的执行器" + "只传最新一条的平台" = 状态静默丢失。**
> 凡是执行器需要跨轮记住的东西，必须**显式存在 Task 上** ——
> 它自己的上下文不算数（下一轮就没了）。
>
> 📌 **更深一层的教训**：三条架构原则里，前两条（执行器无状态、重入走新 worker）
> 是**结构性**的——代码长成那样就自动满足；第三条（状态显式落 Task）是**纪律性**的，
> **事故恰好出在它身上**。凡是靠记性守的原则，迟早会破 —— 要配断言。

## 🟡 F16 · `read_skill` 之后，主 agent 会把技能的**工作流当成自己的做**（未修，待讨论）

- **能力被绕过**：走机制的（Task / 判定 / 台账）和不走的（主 agent 自己干）混在一起，行为不一致

## 🟡 F17 · 上下文大小的两条断言，**在罚一个合法能力**（误伤）

**发现于**：2026-10-30，复核 F11 的"后半段"时重看 `t2-same-turn` 的历史跑批。

### 现象

`t2-same-turn` **7 轮跑批只绿 1 轮**（`t2-refs4`），其余各轮栽在不同断言上。
最近一轮（`t2-refs6`）两个红：

| 断言 | 读数 | 是不是真问题 |
|---|---|---|
| `main_agent_no_artifact_read` | 读了 1 次产物正文 | ❌ **误伤** —— 它有权读 |
| `main_ctx_under` | 14832 字（上限 12000） | ⚠️ 同一个事件的另一面 |

### 根因

**"主 agent 不许读产物正文"这条要求本身是错的。**
它把"按需读"（渐进式披露第二层，主 agent 不是包工头、也要能干活）当成了违规 ——

### 证据链

- `evals/runs/t2-refs4/report.md`（唯一全绿）、`t2-refs5`、`t2-refs6`（读了 1 次）
- 三份 `results.json` 里 `[工具] 主 agent → ...` 的调用流水对比
- 历史 7 轮：`t2-probe`(ctx 9322) / `t2-refs2`(12279) / `t2-refs4`(10124) / `t2-refs5`(7890) / `t2-refs6`(14832)

### 修法（用户 2026-10-30 定）

**删掉判据，留下读数**：上下文大小**只记录、不判**；
超 `CTX_WARN_CHARS`（12000）在 CLI 和 `_run.md` 里打一行 **warning**。
见 `discussion-log` 第十九次 + `solution.md` §4.3.7。

> 📌 **教训（比这一条本身更值钱）**：
> **写断言时先问一句"我判的这件事，是不是它本来就该有的行为"**。
> 断言写错比没断言更糟 —— 它会把一个正常行为**稳定地报成故障**，
> 然后逼着人去"修"一个没坏的东西（本次 7 轮只绿 1 轮，一半的红是这么来的）。

## 🔴 F19 · 打包成 exe 后翻出来的两个真 bug（编码 + 日志落错地方）

**发现于**：2026-10-30，**打包后在一台"没有仓库、没有 Python 环境"的目录里真跑了一遍**。
背景：要把交互式入口发给别人（没环境的业务人员）试用，收集更多场景 —— 见「第二十次」。

**为什么这条值得单记**：两个 bug 在**开发态永远碰不到** ——
开发时 `PYTHONUTF8=1` 由 `.vscode` 设着、日志目录也本来就在仓库里。
**只有"打成包 + 换个目录跑"这一步会把它们翻出来。**

### bug ① `stdin` 没设 UTF-8 → 一个坏字符整场崩掉

**现象**：

```
UnicodeEncodeError: 'utf-8' codec can't encode character '\udcae': surrogates not allowed
  File "chat.py", line 473, in main
  File "chat.py", line 174, in _to_file
```

**根因**：入口只 `reconfigure` 了 **stdout**。
- **stdin** 没设 → 管道/重定向喂进来的中文按 **GBK** 解 → 解不了的字变成 `\udcae`
  这类**代理字符** → 写日志时 UTF-8 编不回去 → **抛异常，整个会话结束**
- **stderr** 没设 → 报错信息落回 GBK，和 stdout 的 UTF-8 混在同一份重定向里

**修法**：`proto/config.py` 里三个流一起设（带 `try/except`，老终端不支持就算了）。
放这里而不是入口，是因为**最早的中文输出就是本模块抛的"缺少模型配置"**，
它走 stderr —— 入口那行 `reconfigure` 还没执行到就已经打出来了。

### bug ② 原始 trace 日志写进了 `_internal/`

**现象**：`proto/trace.py` 的 `LOG_DIR = Path(__file__).parent.parent / "logs"` ——
冻结后 `__file__` 在 `_internal/` 里，于是日志落在 `_internal/logs/`：
**用户不该碰的目录、重建就被清掉**。

**修法**：改成 `app_root() / "logs"`（开发时还是 `langgraph-lab/logs/`，打包后是 exe 旁边）。

> 📌 **顺带定下的目录约定**（`harness.py` 一处收口，别在别处自己算路径）：
>
> | | 开发时 | 打包后 |
> |---|---|---|
> | 应用根 | `langgraph-lab/` | **exe 所在目录** |
> | `.env` | `langgraph-lab/.env` | `<exe 目录>/.env` |
> | 技能 | `evals/skills/` | `<exe 目录>/skills/` |
> | 记录 / 日志 | `evals/runs/` · `logs/` | `<exe 目录>/runs/` · `<exe 目录>/logs/` |
>
> `.env` 那条**实测过**：改之前 `cd` 到别的目录 import，`MODEL_NAME` 读不到
> （`load_dotenv()` 从 **cwd** 往上找，不是从代码位置找）。

### 教训

**"能跑"和"能发给别人跑"是两件事，中间那道验收不能省。**
本次两个 bug 都不是逻辑错，是**环境假设**错 —— 而环境假设恰恰是开发机上最不容易暴露的那类。

## 🔴 F20 · 加"产物当场落盘"，把 **ID 竞态窗口撑开了**（单测当场抓到）

**发现于**：2026-10-30，改完 `store_artifact` 顺手跑单测时。

### 现象

`evals/unit_artifact_race.py` 的输出**当场从 🟡 翻成 🔴**：

```
改之前：🟡 原样 **没撞上** —— 窗口太窄，加压也没压出来
改之后：🔴 原样也撞了 18577 次 —— 真 bug，产物会静默丢失
```

### 根因

`store_artifact` 原来是"先查后写"，两步之间**只有一行**：

```python
aid = f"art_{len(ARTIFACTS) + 1:03d}"   # ① 算
ARTIFACTS[aid] = {...}                  # ② 写
```

窗口在**微秒级**，端到端跑不到（3 个并行 delegate 的写入间隔 4–205 秒），
所以一直是"风险真实、概率极低"。

这次给 `store_artifact` 加"当场落盘"，**在 ① 和 ② 之间插了两步**
（嗅探文件类型、拼文件名）—— 窗口被撑到能撞上了。

### 修法

```python
_ART_SEQ = itertools.count(1)
aid = f"art_{next(_ART_SEQ):03d}"       # `next()` 在 GIL 下原子
```

代价：产物 ID 不再等于"库里第几个"—— **没有任何地方依赖这个**（已核）。

### 教训

> 📌 **这个单测抓到了一个真实引入的回归，不是纸面风险。**
> 它当初写出来时只能证明"窗口存在但难触发"，看起来像"没用的测试"；
> 而这次是它**唯一一次真正拦住东西**。
>
> **在"先查后写"两步之间加活，等于把窗口撑开** —— 加的东西越多越危险。
> 这类改动**看不出问题、跑批也跑不出来**，只有把线程卡在同一起跑线的单测能探到。

## 1. 背景

### 1.1 项目与技术栈

- 技术栈：**LangGraph**（自研 agent）。子 agent 使用 **`create_sub_agent` 模式**
  （`create_agent` + `StateGraph` 包装，见 §5.2）。
- 目标能力：支持 **多 skill**，由 **subagent** 承载/执行。
- 现状：遇到很多问题，困难重重。
- 意图：深度探讨架构取舍；借鉴其它优秀项目；本文件持续记录。

### 1.2 业务场景（教育域）

- skill 与教育相关，例如：**备课 skill**、**导学单 skill**。
- **用户交互是这类 skill 的正常组成部分**（大量参数收集/确认环节）。
- **skill 由用户在 UI 中显式选中**。
- **参数无法提前声明**，很多要到运行中才出现。

### 1.3 现状配置（关键）

| 项 | 现状 |
|----|------|
| 父图 checkpointer | **memory**（进程内） |
| **subagent 子图 `checkpointer=`** | **`True`（per-thread）** |
| 子 agent 与用户交互方式 | **有调用 `interrupt()`**（在请求输入的函数内部），**但未产生挂起效果** |
| 子 agent 包装方式 | `create_sub_agent` 模式（**待最终确认**） |

### 1.4 原始设计与其隐含假设

> 用户自述的原始认知：
> 「只要是执行 skill，就会调用一个 subagent 来全权执行这个任务」——即 **skill ↔ subagent 一对一绑定**。

实现：subagent 全权负责该 skill 的整个任务生命周期；**直接具备与用户交互的能力**；
用户输入后"天然"可以唤起它继续执行（happy path 工作良好）。

| # | 隐含假设 | 实际后果 |
|---|---------|---------|
| A1 | **subagent 实例 = 任务状态的载体** | 依赖 subagent 的累积历史，而非显式 task 状态 |
| A2 | **提问 = 产生一段文本输出** | 不产生挂起点，"恢复"靠历史文本假装 |
| A3 | **skill 之间互不感知** | 同轮多个 skill 各自索要参数，无法去重 |
| A4 | **父 agent 能从子 agent 的文本看出其状态** | 无法区分"我在提问" / "我干完了" / "我失败了" |

> **修正**：A1–A4 才是问题，**"一对一绑定"本身不是**。

> 📌 **已移至 [`solution.md`](solution.md) §0.6** —— 它是**现行**的锚点，不是推演过程。


## 2. 问题清单

### P1 · 多个 skill 重复索取高度相似的参数

- **场景**：用户一轮选中多个 skill，参数空间高度重叠（备课 + 导学单，都要"年级/学科/教材版本/课题"）。
- **症状**：各自索要几乎相同的参数，用户看到**两次几乎一样的提问**。
- **感受**："我明明已经输入过了，为什么还要我再输一遍？"

### P2 · subagent"正常退出"但任务未完成，父 agent 重开一个从头干

- **场景**：subagent 在等待用户输入时结束了自己的运行；父 agent 调用全新 subagent 从头执行。
- **症状**：新 subagent 没有之前的上下文，**再一次请求同样的参数**。
- **特征**：**间歇性**（"有时候会"）→ 指向 namespace / 路由问题，而非必然行为。

### P3 · "请求参数"走正文输出，未通过 checkpointer 挂起自己

- **现状**：subagent 需要参数时**用正文输出**把问题抛出来；**实际已正常退出**，没有真正挂起。
- **走向不确定**：父 agent 转述后，用户回答时出现两种分支：
  1. 父 agent **重新调用全新 subagent**（→ 退化成 P2）
  2. 父 agent **决定自己干**（绕过 skill）

### 共同点

P1 / P2 / P3 是**同一根因的三个投影**。

## 3. 根因分析

### 3.1 三件事被揉成了一件事

| 概念 | 应该是什么 | 应由谁承载 | 生命周期 |
|------|-----------|-----------|---------|
| **Skill** | 能力定义：prompt、工具集、参数契约、资源 | 注册表（静态） | 长期 |
| **Task** | 一次具体工作：用哪个 skill、参数、进度、产物 | **持久化状态** | 跨多次交互，可挂起 |
| **Agent** | 执行引擎：取一个 task 干活 | 图的一次 invoke | 一次性、可丢弃 |

> **核心推论：Agent 必须无状态**（状态在 Task 里，不在 Agent 里）。
> 当前实现里，"task 状态"实际上**寄生在 subagent 累积的 message history 里**——
> 这是 §6 一切问题的总源头。

### 3.2 "提问"被当成了输出，而不是控制流事件

> ⚠️ **诊断对，但结论已被 §10.14 修正。**
> 当时推出"提问必须成为控制流事件（`interrupt()`）"——**最终设计否掉了这条路**。
> 正确结论是：**提问不必成为控制流事件，只要任务状态另有既有事实可判定**
> （= 产物库空不空 + `Task.stage`）。见 §10.14。

- **当输出**：模型生成文字 → 图继续走 → 图结束。提问只是**副作用**，没有任何东西被保存。
  用户答复时，系统只能**重新决策**要干什么。
  > 系统不是"选择"了重来，是它**不知道原来干到哪了**。
  > ← 这只在**执行器自己持有任务状态**时成立。最终设计里状态在 `Task` 上，不在执行器上。
- **当控制流事件**：调用 `interrupt()` → 图在**该点**冻结并持久化 → 交还控制权 →
  `Command(resume=...)` → **原地继续**。
  > ← 这条路最终被放弃：成本（悬空 tool_call、checkpointer 依赖、包装层透传）大于收益。

### 3.3 缺少协议：子 agent 的返回值不可区分

> ⚠️ **本节结论已被证伪。** 当时说"返回值必须是结构化的"，最终设计里
> **执行器没有任何返回协议**——完成与否由「产物库空不空」推断（§10.14）。
> **协议是过度设计。**

原文（**已作废**）：**返回值必须是结构化的**（`{status: needs_input | done | failed, payload}`）。
这是**协议问题，不是提示词问题**，改 prompt 治不好。

### 3.4 跨轮次参数复用没有分层

> ⚠️ **观察仍然成立，但"三层参数模型"这个解法已被 §10.14 取代**（参数不抽取、不分层）。
> **而且这个问题在最终设计里只被部分解决**——见下面的「仍然开放」。

教育场景里很多参数其实是**用户画像**而非**任务参数**（"三年级数学老师，人教版"）——
**问一次就该永远记住**。没有分层，是 P1 被放大的原因之一。

**仍然开放**：最终设计的「主 agent 先答」（§10.14）只在**同一会话内**解决复用
（主 agent 的上下文里有用户之前说过的话）。**跨会话不解决**——
新会话里主 agent 上下文是空的，执行器又拿不到那句话，只能重新问用户。

要跨会话复用，需要**长期记忆**（LangGraph `store` / sx-agent 的 `memory_context`），
那是**独立于本设计的一块**，本原型没做。已记入 §10.15 待验证清单。

## 4. 目标架构（草案 · ⚠️ 已被 §10.14 取代）

> ⚠️ **本节是讨论中途的草案，已被 §10.14 取代。** 保留只为记录推演过程。
> 其中「三层参数模型」「需求上抛 + 编排层统一提问」等提法，
> 在最终设计里**都不存在了**（参数不抽取、不分层、不提前问）。**以 §0 与 §10.14 为准。**

### 4.1 核心机制：需求上抛 + 编排层统一提问

1. **子任务发现缺参数 → 不直接问用户**，产出结构化请求并**停在原地**（真正挂起）。
2. **编排层收集所有待问请求**（跨任务、跨 skill）→ **合并去重** → **一次性**呈现。
3. 答复写入**共享参数台账** → **批量恢复**所有被暂停的任务。

> **这套机制 LangGraph 原生支持**，见 §5.3。

### 4.2 对"1:1 绑定"的修正

- 参数运行中才出现 → 每个 skill 确实需要**自己的执行上下文与挂起点** → **1:1 是合理默认，不致命**。
- 真正致命的是缺了三样：**编排层 / 显式挂起机制 / 返回协议**。

### 4.3 三层参数模型

| 层 | 例子 | 存储 | 提问频率 |
|----|------|------|---------|
| **L1 Profile** | 老师身份、常教年级/学科、教材版本 | 跨会话（`store`） | **一辈子一次** |
| **L2 Session** | 本轮选中的 skill 组合、会话内共享参数 | 父图 state | 会话内共享 |
| **L3 Task** | 本次任务特有参数（具体课题、课时） | task / 子图 state | 每任务一次 |

### 4.4 执行阶段的确定性

**原则：LLM 决策与执行分离。** P3 里"父 agent 决定自己干"就是执行阶段还在让 LLM 决策的后果。

## 5. LangGraph 机制核查（依据：本地离线文档）

> ⚠️ **阅读提示**：本节是**诊断阶段**的机制核查，**大部分围绕 `interrupt()` 展开**。
> 最终设计**不用 `interrupt()`**（§10.14），所以 §5.3–§5.6 与最终方案无关。
> 保留它们是为了记录"**当初为什么会往 interrupt 方向走**"——以及为什么那是弯路。
> **仍然有效的是 §5.1（子图持久化三模式）和 §5.2（namespace）**，它们解释了 P2 的成因。

### 5.1 子图持久化三模式 + 权威特性矩阵

`use-subgraphs.md:319-339`，权威矩阵在 `use-subgraphs.md:676-689`：

| Feature | Per-invocation（默认） | **Per-thread** | Stateless |
|---------|----------------------|----------------|-----------|
| `checkpointer=` | `None` | **`True`** | `False` |
| **Interrupts (HITL)** | ✅ | **✅** | ❌ |
| **Multi-turn memory** | ❌ | **✅** | ❌ |
| **Multiple calls (不同 subgraph)** | ✅ | **⚠️ 命名空间冲突** | ✅ |
| **Multiple calls (同一 subgraph)** | ✅ | **❌ 冲突** | ✅ |
| State inspection | ⚠️ 仅当前调用 | **✅** | ❌ |

> 🔴 **两个必须注意的硬限制（per-thread 列）**：
> 1. **同一 subgraph 不能被重复调用** —— 即**一个会话里，一个 skill 只能有一个活跃任务实例**。
>    教育场景下"同一会话备两节课"会直接撞上这条。
> 2. **不同 subgraph 在同一节点内调用会有命名空间冲突**。
>
> 官方建议用 `ToolCallLimitMiddleware(tool_name=..., run_limit=1)` 抑制并行调用。

### 5.2 命名空间按调用顺序分配 ⚠️

`use-subgraphs.md:606-621`：

> "If you call subgraphs inside a node, LangGraph assigns namespaces **based on call order**
> (first call, second call, etc.). This means **reordering your calls can mix up which
> subgraph loads which state**."

官方解法（**这就是文档里的 `create_sub_agent`**）：

```python
def create_sub_agent(model, *, name, **kwargs):
    """Wrap an agent with a unique node name for namespace isolation."""
    agent = create_agent(model=model, name=name, **kwargs)
    return (
        StateGraph(MessagesState)
        .add_node(name, agent)   # unique name → stable namespace
        .add_edge("__start__", name)
        .compile()
    )
```

补充（`use-subgraphs.md:651`）：
> "Subgraphs **added as nodes** already get **name-based namespaces** automatically,
> so they don't need this wrapper."

> **待确认**：用户是**把 subagent 作为节点 add_node**（自动获得稳定的 name-based namespace），
> 还是**在一个节点内部调用**（则 namespace 按调用顺序分配，必须用上面的包装）。
> **这一条直接决定 P2 的机理**。

### 5.3 批量恢复多个 interrupt —— P1 的官方原语 ✅

`interrupts.md:214-271`：

```python
# Step 1: 并行节点各自 interrupt，全部挂起
stream = graph.stream_events({"vals": []}, config, version="v3")
print(stream.interrupts)
# > (Interrupt(value='question_a', id='...'), Interrupt(value='question_b', id='...'))

# Step 2: 一次性恢复全部
resume_map = {i.id: f"answer for {i.value}" for i in stream.interrupts}
resumed = graph.stream_events(Command(resume=resume_map), config, version="v3")
```

> ✅ **这就是 §4.1「编排层统一提问」的 LangGraph 原生实现**，不需要自己发明轮子。

### 5.4 interrupt 可以放在 tool 里 ✅

`interrupts.md:456-593`：interrupt 可直接放在 tool 函数内，tool 会**暂停**。
`use-subgraphs.md:696` 补充：

> "**Interrupts still propagate to the top-level graph regardless of nesting.**"
> （但 "View subgraph state" **在 tool 内调用 subgraph 时不可用**）

### 5.5 interrupt 的五条铁律 🔴

`interrupts.md:694-955`：

| # | 规则 | 原因 |
|---|------|------|
| 1 | **不要用 bare `try/except` 包 `interrupt()`** | interrupt 靠**抛异常**实现，会被 except 吞掉 |
| 2 | **不要在节点内重排 / 条件跳过 / 循环 `interrupt()`** | resume 值**严格按索引**匹配 |
| 3 | **不要给 `interrupt()` 传复杂对象** | 必须可序列化 |
| 4 | **`interrupt()` 之前的副作用必须幂等** | **节点会从头重跑** |
| 5 | **禁止 `while True` + `interrupt()` 校验循环** | 每次 resume 重放全部历史迭代 → **指数级重跑** |

规则 5 的官方正确姿势（`interrupts.md:595-628`）：
> 「每个节点调用**只 `interrupt()` 一次**，把重问的问题存进 state，用**条件边**回环到该节点。」

> 💡 **对用户场景的直接推论**：
> - **"一次问一批参数"应做成一次 `interrupt()` 携带一组问题**（而非循环问 N 次）
> - **问句存进 state**（如 `pending_questions`），由**固定的 ask 节点**读取并提问
> - **ask 节点要独立、轻量**：resume 时节点从头重跑，把提问和重活放一起会导致重活被反复重跑

### 5.6 子图作为函数调用：父节点与子节点都会从头重跑 🔴

`interrupts.md:957-973`：

> "the parent graph will resume execution from the **beginning of the node** where the subgraph
> was invoked... Similarly, the **subgraph** will also resume from the beginning of the node
> where interrupt was called."

> 🔴 若 subagent 是在 `@tool` 里 `agent.invoke(...)` 的，恢复时**整个 tool 函数体从头重跑**。

### 5.7 其他相关机制（备查）

- `interrupts.md:975-981`：`interrupt_before/after` 是**静态断点用于调试**，
  明确 **"not recommended for human-in-the-loop workflows"** → 别拿它做参数收集。
- `use-subgraphs.md:333-335`：**父图必须编译带 checkpointer**，子图持久化特性才生效。
- `use-subgraphs.md:691-697`：`graph.get_state(config, subgraphs=True)` 可**查看子图状态**
  （per-thread 下可看到累积状态）——**这是验证 P2 的诊断工具**。
- `stores.md`：跨会话长期记忆（对应 §4.3 的 L1 Profile）。
- `use-time-travel.md`：checkpoint 回放/分支。
- `fault-tolerance.md`：持久执行与故障恢复。

## 6. 诊断（基于 `checkpointer=True` 的重新分析）

### 6.1 核心发现：per-thread 正在「隐式地」替 `interrupt()` 干活

这是理解一切的钥匙。

`checkpointer=True` 让 subagent 的 message history **跨调用累积**（文档原文：
"Each call picks up where the last one left off"）。于是发生了这件事：

```
第 1 轮：父 agent 调 备课 subagent
        → subagent 输出正文"请提供年级/学科/课题"，结束
        → 但它的 message history 被 per-thread 存了下来

用户回答 → 父 agent 再调同一个 备课 subagent
        → subagent 读到累积历史：[...自己上一轮的问句..., ...用户的回答...]
        → 于是"接着干"
```

**看起来像恢复，其实是一次全新的调用，只不过历史文本还在。**

> ✅ **这就是"正常情况下工作良好"的真相**——不是因为你实现了挂起/恢复，
> 而是因为 per-thread 的累积历史**碰巧**把上下文接上了。

### 6.2 三个裂缝，恰好对应 P1 / P2 / P3

| 问题 | 机制解释 |
|------|---------|
| **P3** | **`interrupt()` 调了，但挂起信号在某一层包装里被丢掉了**（详见 §6.7）。`interrupt()` 的语义是**返回值**（`result["__interrupt__"]` / `stream.interrupts`），**不是会自己穿透到顶层的异常**。若 dispatch 包装写的是 `return resp["messages"][-1].content`，interrupt 就在这一层消失，父 agent 只看到一个普通 tool 结果 → "其实已经正常退出了"。 |
| **P2** | 累积历史依赖 **namespace 正确解析**。若 subagent 是在节点内调用（而非 `add_node`），namespace **按调用顺序分配** → 调用顺序一变，**加载到别的 subagent 的 state 或空 state** → 表现就是"重开一个、从头来、重新问参数"。**这解释了 P2 的间歇性。** |
| **P1** | per-thread 下每个 subagent 有**自己的累积状态**，彼此隔离，且**没有编排层**做合并去重 → 各问各的。 |

### 6.3 一个结构性限制（可能是更深的隐患）

特性矩阵里 per-thread 的 **"Multiple calls (同一 subgraph) = ❌"**：

> 一个会话里，**同一个 skill 只能有一个活跃任务实例**。

对教育场景的直接冲击：**"同一会话里先备《分数》、再备《小数》"会撞上这条限制**
（两次调用写同一个 namespace → 冲突；或者状态被合并成一份，第二次备课看到第一次的参数）。

### 6.4 建议的方向：改用 per-invocation + 真正的 `interrupt()` ⚠️ 已被 §10.14 取代

> ⚠️ **这条建议已被推翻。** 最终设计**没有引入 `interrupt()`**，
> 而是用 `Task.stage` 推导等待状态（§10.14）。**不要按本节动手。**

| | per-thread（现状） | **per-invocation + interrupt（建议）** |
|---|---|---|
| Interrupts | ✅（未用） | ✅ |
| 并行调用 | ⚠️ 不同 subgraph 冲突 / ❌ 同一 subgraph | ✅ 都支持 |
| 一个会话多个同名任务 | ❌ | ✅ |
| namespace 冲突 | ⚠️ 有 | 无 |
| 跨调用记忆 | ✅ | ❌（**但用 interrupt 后不再需要**） |

**逻辑**：你现在需要 per-thread，是因为你要靠"累积历史"来接上下文。
一旦引入真正的 `interrupt()`，"**一次调用 + 多次挂起**"成为可能——
subagent 启动 → 挂起问参数 → 恢复 → 继续 → 完成，**全程是一次调用**。
per-invocation 明确支持"单次调用内继承父 checkpointer 以支持 interrupt"。
于是 per-thread 的两个硬限制（同名不能重复调用、多 subgraph 命名空间冲突）**同时消失**。

> ⚠️ 这是**基于文档推理的架构建议**，不是已验证结论。建议先用一个最小 demo 验证
> "per-invocation + 节点内 interrupt + 批量 resume"跑通，再动生产代码。

### 6.5 其他必查项

| # | 检查项 | 为什么 |
|---|--------|--------|
| 1 | **`thread_id` 是否每轮稳定** | per-thread 一切以 thread_id 为键；每轮换新 ID = 全部重置 |
| 2 | **subagent 是 `add_node` 还是节点内调用** | 决定 namespace 是 name-based 还是 call-order-based（§5.2） |
| 3 | **是否有 bare `try/except` 包住 interrupt** | 会吞掉挂起异常（§5.5 规则 1） |
| 4 | **memory checkpointer** | 进程重启即丢；教育场景用户可能几分钟才回来填表 → 建议 sqlite/postgres |
| 5 | **是否有并行调用同一 per-thread subagent** | 会 checkpoint 冲突 |

### 6.7 关键机制澄清：`interrupt()` 是「返回值」，不是「异常穿透」🔴

**这是理解 P3 的最后一块拼图。**

`interrupts.md:40-50` 描述了调用 `interrupt()` 后实际发生的五件事：

1. **图执行在调用点挂起**
2. **状态通过 checkpointer 保存**
3. **值返回给调用方** ——
   - 事件流式：`stream.interrupts`（`graph.stream_events(..., version="v3")`）
   - 默认 API：`result["__interrupt__"]`（`graph.invoke(...)`）
4. **图无限期等待**，直到你 resume
5. **resume 值回填**为 `interrupt()` 的返回值

> 🔴 **关键**：虽然 `interrupt()` 内部是靠**抛异常**实现的
> （`interrupts.md:696`："suspends execution by raising an exception"），
> 但**这个异常在图边界被运行时捕获，并被转换成一个普通的返回值**。
>
> 也就是说：**挂起信号不会自己穿透到最顶层调用者。**
> **每一层包装都必须显式检查并向上传递它**，否则它就在那一层消失。

**这恰好解释了用户观察到的两个症状：**

```python
# 假想的 dispatch 包装
@tool
def run_skill(skill: str, request: str) -> str:
    resp = subagent.invoke({"messages": [...]}, config)
    return resp["messages"][-1].content      # ← 灾难在这一行
```

- 若 subagent 中断了，`invoke()` **正常返回**，待问 payload 在 `resp["__interrupt__"]` 里
- 但这行代码读的是 `messages[-1].content` → **interrupt 被静默丢弃**
- 于是：
  - 父 agent 看到的是一个**普通 tool 结果** → 用户感受为 **"其实已经正常退出了"** ✅
  - 而 `messages[-1]` 很可能就是那句"请提供年级…" → 用户感受为 **"走的是正文输出"** ✅

**两个症状，一行代码解释完。**

### 6.8 这与 §3.3「返回协议」是同一件事 ⚠️ 已被 §10.14 取代

> ⚠️ **本节结论作废。** 最终设计里**执行器没有任何返回协议**——
> 完成与否由「产物库空不空」这个**既有事实**推断（§10.14）。
> §3.3 当时提出"返回值必须结构化"，后来被证伪：**协议是过度设计**。

原文如下（**已作废**）：

§3.3 说"子 agent 的返回值必须是结构化的（`needs_input | done | failed`）"。

**LangGraph 已经提供了那个信号**：`__interrupt__` / `stream.interrupts`。
它就是一个结构化的 `needs_input` 标记。

**问题不在于缺协议，而在于包装层把这个协议扔掉了。**

### 6.9 决定性诊断

```python
resp = subagent.invoke({...}, config)     # 或 subagent.stream_events(...)
print(resp.get("__interrupt__"))          # invoke 路径
# 或 print(stream.interrupted, stream.interrupts)   # stream_events 路径
```

| 结果 | 结论 |
|------|------|
| **有 `__interrupt__`** | interrupt **生效了**。是**包装层把它丢了** → 改包装，透传该信号 |
| **没有 `__interrupt__`** | interrupt **根本没触发** → 依次排查：bare `try/except`（§5.5 规则 1）、`thread_id` 是否随 config 传进 subagent、checkpointer 是否可达 |

### 6.10 两条修法 ⚠️ 已被 §10.14 取代

> ⚠️ **两条修法都已作废。** 最终设计里执行器**不问用户、不挂起**，
> 所以"透传 `__interrupt__`"和"包装层主动上抛"都不需要了（§10.14）。

| | **A. 透传嵌套挂起** | **B. 结构化返回 + 编排层统一提问**（推荐先做） |
|---|---|---|
| 做法 | subagent 内部照常 `interrupt()`；**每一层包装显式透传** `__interrupt__` / `stream.interrupts` | subagent **不** interrupt；缺参数时**正常返回** `{status: "needs_input", questions: [...]}`；**编排层**收集后统一 `interrupt()` 问用户 |
| P1 批量去重 | 靠 `stream.interrupts` + `Command(resume={id: value})` | 天然支持（提问权完全在编排层） |
| 嵌套挂起 | 需要，且要处理"子任务被挂起但 tool 已返回"的状态 | **不需要**，无嵌套挂起 |
| 依赖 | 包装层正确透传 | 跨调用记忆（**per-thread 已提供**） |
| 改动量 | 中（要动包装与恢复路径） | **小** |

> **推荐 B 作为主路径**：改动小、直接解决 P1、不依赖嵌套挂起，
> 且与 §4.1「需求上抛 + 编排层统一提问」完全一致。
> A 作为后续增强（当需要"一次调用贯穿始终"时）。
>
> ⚠️ 无论 A 还是 B，**§6.5 的 namespace / thread_id 检查项都必须做**——
> B 的"重新调用 subagent"依赖 per-thread 正确解析 namespace。

## 7. 落地路径（草案 · ⚠️ 已被 §10.14 取代）

> ⚠️ **本节是讨论中途的草案，已被 §10.14 取代。**
> 其中「第一步：止血——让提问成为真正的挂起点（`interrupt()`）」等步骤，

### 7.1 分四步走

1. **止血：让"提问"成为真正的挂起点**

   - 问句存进 state，保证 interrupt 次数/顺序确定
   - 子 agent 返回值**结构化**（`needs_input | done | failed`）
2. **补编排层：统一提问 + 批量恢复**
   - `stream.interrupts` 收集全部待问 → 合并去重 → 一次问用户

3. **修 namespace / 持久化模式**（§6.4、§6.5）
   - 确认 subagent 是 `add_node` 还是节点内调用
   - 评估改用 per-invocation
4. **补状态分层：Profile / Session / Task**（§4.3）
   - L1 走 `store`，把"年级/学科/教材版本"变成问一次就永久记住

> **P1 / P2 / P3 不是"隔离"的代价，
> 是「把 subagent 边界画在**整个 skill 生命周期**上」的代价。**

| 问题 | 为什么会发生 | 边界收窄后 |
|------|------------|-----------|
| **P1** 重复问参数 | 每个 subagent 各持一份参数，互不可见 | 参数收集归主 agent，跨 skill 天然可去重 ✅ |
| **P2** 没干完就退出 | subagent 必须跨轮存活 → 状态丢失 | 执行器**不跨轮存活** ✅ |
| **P3** 提问后走向不确定 | subagent 要问用户 → 需要挂起 → 挂起信号会丢 | 执行器**不问用户** ✅ |
| **上下文隔离** | — | **仍然保留** ✅ |

### 9.3 边界画在哪里

```
主 agent（交互上下文 · 小）
├─ 1. 装载技能指令
├─ 2. 收集参数（跨 skill 合并去重）
├─ 3. 参数齐了 → 派发执行器          ← 边界画在这里
│     └─ 执行器 subagent（隔离上下文 · 大）
│          ├─ 读参考文件 / 跑工具 / 生成产物
│          ├─ 把中间结果写进产物或草稿（断点外置）
│          └─ 返回 {产物ID, 摘要} 或 {NEEDS_INPUT, 缺什么, 断点}
├─ 4. 拿到摘要 → 继续对话
└─ 5. 若 NEEDS_INPUT → 主 agent 问用户 → 带答案重新派发（从断点续）
```

**两条纪律**：

1. **参数不齐不进执行器**——参数在主 agent 收齐
2. **执行器只回传摘要 + 产物 ID，不回传正文**

### 9.4 「参数运行中才出现」怎么处理

用户确认过：参数不能提前声明，很多要到运行中才出现。这**不与上面的设计冲突**：

执行器跑到一半发现缺参数 → **返回结构化结果然后正常退出**（不是挂起）：

```
NEEDS_INPUT | 缺 课时 | 已完成：目标与重难点分析 | 断点：art_draft_7
```

主 agent 拿到这个信号 → 问用户 → 带答案重新派发 → 执行器**从断点续**，不从头再来。

**关键：断点必须外置**（写进产物 / 草稿文件），不能只活在执行器的上下文里。
—— 项目已有 `create_artifact` / `read_product` 基础设施，机制现成。

### 9.5 实验量化（`exp06_context_isolation.py`）

模拟一份 2734 字的教案产物，对比主 agent 上下文体积：

### 9.7 与"是否重新绑定 interrupt"的关系 ⚠️ 已被 §10.14 取代

> ⚠️ **本节结论作废。** 最终设计**不重新绑定 interrupt**——
> 提问由 `Task.stage` 推导，不用挂起点（§10.14）。
> 本节当时以为"边界收窄后 interrupt 更好用"，实际是**边界收窄后 interrupt 根本不需要了**。

### 9.8 🔴 关键质疑：「主 agent 拿到用户输入后，能保证传回正确的执行器吗？」

这是整个提案成立与否的关键。**直接回答：靠 LLM 保证不了——所以不要让 LLM 参与。**

**机制：把「待办任务」变成 state 里的一等公民。**

```python
class State(TypedDict):
    messages: ...
    active_skill: NotRequired[str]
    pending_task: NotRequired[dict]   # {skill, missing, params, checkpoint_ref}
```

- `pending_task` 由 **dispatch 节点的代码写入**（执行器返回 `NEEDS_INPUT` 时），不是 LLM 决定
- 入口路由**看 state 字段**，不看 LLM：

```python
def entry_route(state):
    return "resume_task" if state.get("pending_task") else "chat"
```

- `resume_task` 节点**按名字查表**调用执行器，LLM 全程不参与：

```python
EXECUTORS = {"lesson-prep": beike_worker, "guided-learning": daoxuedan_worker}

def resume_task(state):
    task = state["pending_task"]
    return EXECUTORS[task["skill"]](...)   # 字典查表，不是 LLM 选择
```

**实验 07 证明（`exp07_deterministic_resume.py`）**

设计：给主 agent 一个**故意"困惑"的假模型**——若它在续跑轮被调用，会派发到**错误的**技能
（`lesson-prep`）。这样一旦路由依赖 LLM，实验立刻失败。

```
【第 1 轮】用户：帮我出导学单
   chat: LLM 决策 → 它选了 guided-learning
   dispatch: 调用 guided-learning → 'NEEDS_INPUT|缺 课时|断点：dx_draft_3'
   dispatch: 写入 pending_task(skill=guided-learning)
   ask_user: 就 guided-learning 的缺失项提问

【第 2 轮】用户答复：1 课时
   resume_task: 查表命中 guided-learning，未经过 LLM     ← 只有这一行
   → 调用计数 = {'lesson-prep': 0, 'guided-learning': 2}
```

> **`chat` 节点在第 2 轮根本没被调用**，困惑模型那条"选错"的响应从未被消费。
> 答复精确回到 `guided-learning`。

**原则：LLM 负责「启动」，代码负责「续跑」。**

### 9.9 项目里已经有这个模式的雏形

`app/engine/stream.py:684-693`：

```python
pending = _pending_interrupts(state)
if pending:
    return Command(resume=...)      # ← 确定性恢复：不经过 LLM
```

**同一行代码、同一个形状**，只需把触发条件从 "pending interrupt" 扩展到 "pending task"：

```python
pending_task = state.values.get("pending_task")
if pending_task:
    return Command(resume=...)      # ← 确定性续跑
```

### 9.10 唯一真正需要判断的地方，以及怎么处理

| 场景 | 处理 |
|------|------|
| **用户不回答，换话题了** | 确定性默认：**有待办时，下一条消息默认就是答复**；仅当消息明确表示放弃（"算了/取消/换个事"）才清空 `pending_task`。更稳的做法是前端给显式「取消任务」按钮，或有待办时 UI 明示"正在等待 X 的答复" |
| **多个待办** | `pending_tasks` 为列表，逐个续跑，顺序确定 |
| **待办过期** | 加 TTL，过期清空并留痕 |

> **关键收益：不再依赖 LLM 的"记性"。**
> 现状是模型要靠历史文本推断"用户在回答我哪个问题"；
> 改成 `pending_task` 后，这个推断变成 **state 里的一次字段读取**。

## 10. 最小原型与真实模型验证（`../proto/`）

> 环境：`langgraph 1.2.18` / `langchain 1.4.7` / Python 3.12。
> 代码：`../proto/`（`config.py` / `skills.py` / `graph.py` / `__main__.py` / `README.md`）

### 10.1 原型形状

```
START ──entry_route──┬─(无待办)─→ plan ──┬─(缺参数)→ ask ──┬─(已拿到答复)→ dispatch
                     │                  └─(参数齐)───────→ dispatch
                     └─(有待办)─→ answer ─────────────────→ dispatch
                                                                  │
                                           dispatch ──(执行器缺参数)→ ask
                                                  └─(全部完成)────→ END
```

两种提问模式可对照：`--mode message`（正文提问 + `awaiting` 确定性续跑）
与 `--mode interrupt`（`interrupt()` 挂起 + `Command(resume=...)` 恢复）。

### 10.2 三个断言的真实模型验证结果

| # | 断言 | 对应问题 | 结果 |
|---|------|---------|------|
| 1 | 参数在主 agent 收齐，可跨技能去重 | **P1** | ✅ "帮我备课和导学单，三年级数学" → 只问 **2 个**字段（`课题`/`课时`），不合并要问 6 个 |
| 2 | 执行器隔离上下文，产物正文不进主 agent | **上下文爆炸** | ✅ 见 §10.3，主上下文 **383 字** vs 产物库 **52553 字 = 137 倍** |
| 3 | 执行器缺参数 → 主 agent 问 → **确定性**回到正确执行器 | **P2 + P3** | ✅ 完整跑通，含运行期发现的参数与断点外置 |

### 10.3 关键数字：上下文隔离实测（DeepSeek v4 pro）

场景："帮我做个互动课件，三年级数学"（该技能有一个**运行期才暴露**的需求：呈现形式）

| 轮次 | 发生了什么 | 主 agent 上下文 | 产物库正文 |
|------|-----------|---------------|-----------|
| 1 | plan：只问 `课题`（静态需求） | 43 字 | 0 |
| 2 | 用户答 `课题` → 派发执行器 → **执行器报缺 `呈现形式`**，附真实断点描述；草稿落盘 | 228 字 | 12,301 字（**54 倍**） |
| 3 | 用户答 `呈现形式` → **确定性续跑** → 交付完整 HTML 课件 | **383 字** | **52,553 字（137 倍）** |

> **主 agent 全程只看到 `art_001` / `art_002` 两个 ID 和一句话摘要，
> 52,553 字的产物正文一个字都没进主上下文。**

### 10.4 执行器结果协议的可靠性（重要工程发现）

原型最初用 `create_agent(response_format=ExecResult)`。实测**豆包（Ark `doubao-seed-2.1-turbo`）
不产出 `structured_response`**：模型调了 `write_artifact` 干完活，然后返回**空消息**，
`structured_response = None` —— **静默退化**。

**改为显式终止工具 `finish(...)` 后稳定**：

```python
@tool
def finish(status, summary, missing_fields, done_so_far) -> str:
    """任务结束时必须调用本工具登记结果，这是你唯一的结果出口。"""
```

从消息轨迹里解析 `finish` 的 tool_call 参数，并保留三级兜底
（`structured_response` → `finish` 调用 → 从工具结果捞产物 ID）。

**实测对比**：

| 模型 | 备课执行器 | HTML 课件 |
|------|-----------|----------|
| 豆包 `doubao-seed-2.1-turbo` | 4/4 ✅（3300–3800 字/次） | ❌ **3/3 空响应** |
| DeepSeek v4 pro | 3/3 ✅（4400–4500 字/次） | ✅ **40,252 字 HTML** |

> 豆包对 HTML 内容返回空响应，是**该 endpoint 的模型能力问题**，与架构无关；
> 但它说明：**执行器这个模式对模型能力有要求，换模型要重新验证**。

### 10.5 轻量机制测试（日常回归用，44 秒）

上面的 137 倍来自 HTML 课件（单次 4 万字，跑得慢）。**机制验证不需要重内容**，
日常回归改用轻量技能 `quiz`（随堂小测，产出 150 字内），而且它的演示更纯粹：

```
plan:     技能=['quiz'] 已知=['年级','学科'] 待问=（无）    ← 静态参数全齐，不问
dispatch: quiz 报缺参数 ['难度']                            ← 运行期才发现
          （断点：已拟好3道随堂小题，题干与答案已存入 art_001 草稿）
answer:   抽取 ['难度'] → 参数={...}（路由未经过 LLM）        ← 确定性续跑
dispatch: quiz ✅ 已交付三年级数学基础随堂小测3道，含答案
```

> **静态参数一个不缺，执行器照样在运行中发现了需求**——
> 这是"参数要到运行中才出现"的最纯形态。

**教训：探测机制时，例子要挑轻的。** 内容体量不影响机制结论，只会拖慢每一轮。

### 10.6 interrupt 模式验证（真实模型）

**跑通了，结果与 message 模式完全一致。**

| | message 模式 | interrupt 模式 |
|---|---|---|
| 提问载体 | 正文 AI 消息 + `awaiting` | `interrupt()` 载荷 |
| 续跑入口 | `entry_route` → `answer` 节点 | LangGraph 原地恢复 `ask` 节点 |
| 交付产物 | `[art_001, art_002, art_004]` | `[art_001, art_002, art_004]` |
| 主 agent 上下文 | 333 字 | **143 字** |
| 耗时 | 1m22s | 1m20s |

> interrupt 模式的主上下文更小，因为**问题在 interrupt 载荷里，不进消息历史**。

### 10.7 🔑 关键发现：提问做成「图节点」而非「工具」，结构性避开悬空 tool_call

sx-agent 当初关掉 interrupt 的原因之一是（§8.5 坑 1）：

> "悬空 tool_call（无配对 ToolMessage）会在后续工具循环中重新进入 LLM 输入，
> 触发上游 API 400（insufficient tool messages following tool_calls）"

**实测：把提问做成图节点后，全程无悬空 tool_call（含用户放弃提问的场景）。**

原因：`interrupt()` 在**图节点**里调用时**不产生 tool_call**，所以压根没有"未配对的 ToolMessage"这回事。

而 sx-agent 的 `request_user_input` 是**工具**：LLM 调用它 → 产生带 tool_call 的 AIMessage →
工具内 `interrupt()` → 挂起时 ToolMessage 尚未产生 → **悬空**。

> **这是一个可以直接搬的设计改进：把提问从「工具」改成「节点」。**

### 10.8 用户换话题（放弃待办）—— 发现并修复了一个真 bug

**第一版原型的表现**：用户挂起后换话题 → 系统把它当成对上一个问题的回答 →
清空 `awaiting` → **重跑执行器**（产生新草稿）→ 又挂起问同样的问题 → **死循环**。

**修复**：`llm_extract` 增加 `is_answer` 判断（LLM 只做「判断 + 抽取」），
路由由纯函数决定：

```python
def after_answer(state):
    return "dispatch" if state.get("plan") else "plan"
```

`is_answer=False` → `_apply_answer` 清空 `plan` → 回 `plan` 重新规划。

**修复后**：换话题 → 放弃待办 → 重新规划 → 问新任务的参数 → 正常收敛，
**执行器一次都没重跑**（56 秒，比修复前 64 秒还快）。

> 这验证了 §9.10 的预判：**"用户不回答、换话题"是这套设计里唯一真正需要判断的地方**，
> 而且它必须显式处理，不能默认"下一条消息就是答复"。

### 10.9 🔑 正文提问怎么办（用户提出的测试点）

**场景**：skill 在执行过程中，**用回复正文**向用户要参数——不走 `interrupt()`、也不调 `finish`。
这正是 sx-agent 现在的做法（§8.3）。

**为什么这是个问题**：正文**没有结构化信号**。系统无法区分
「我在问你」/「我干完了」/「我失败了」——只能猜，猜错就是 P2/P3。

**处理办法：预防 + 兜底，落点统一**

| 层 | 做法 |
|---|------|
| **预防（主路径）** | 提示词强约束 + `finish` 协议，让执行器**不要**用正文提问 |
| **兜底** | 执行器没调 `finish` 时，**补一次 LLM 判断**：把它的正文交给 LLM，问「这是在要参数吗？要哪些？」→ 翻译成 `needs_input` |

> **关键：翻译完成后，后续路由与 `finish` 路径完全一样**——都写 `awaiting`，
> 都走 `entry_route` 的确定性续跑。
> **信号从哪来不重要，落点只有一个。** 这就是"统一到同一个状态机"的价值。

**实测**（`debug_body_question.py`，DeepSeek v4 pro）：

| 场景 | 执行器实际输出 | 结果 |
|------|--------------|------|
| 缺参数 | 正文："好的，三年级的数学随堂小测，就差一个信息了——请问你要 **基础 / 提升 / 挑战** 哪一档难度？" | ✅ 被翻译成 `needs_input ['难度']`，附 `done_so_far` |
| 参数齐全 | 正常出题 | ✅ `done` + 产物，**无误报** |
| **只说不做** | 正文："已经帮你把题出好了"（**但产物库是空的**） | ✅ 判为 **`failed`**，不放行 |

### 10.9.1 🔴 「是完成就转 finish」这半句必须加保险

**正文是「声称」，产物库里有没有东西才是「证据」。**

如果只凭正文说"我完成了"就判 `done`，会出现这种静默失败：
模型正文写"教案已完成，请查收" → 判 `done` → 主 agent 报"已交付" → **用户什么也没拿到**。
**这正是最初要消灭的那类问题——系统"看起来成功了"。**

完整的判定阶梯：

```
执行器返回
├─ 调了 finish                  → 用它的声明（权威：字段、断点、状态全有）
├─ 调了 write_artifact
│    └─ 产物库确实有东西         → done（summary 用产物标题兜底）
└─ 纯正文结束（没调任何工具）
     ├─ LLM 判为「在问参数」          → needs_input
     ├─ LLM 判为「完成了」+ 有产物    → done
     └─ 其余                          → ⚠️ failed（不放行）
```

代码里对应 `_parse_result` 的兜底 2（`../proto/skills.py`），
以及 `run_skill_safe` 里"执行器抛异常"也归为 `failed`（异常 = 没交付）。

**成本**：只在"执行器没调 `finish`"时多一次 LLM 调用。正常路径**零开销**。

**对 sx-agent 的启示**：正文提问不是"接不住"，而是**要补一层翻译**。
但更划算的是**从源头改成结构化**——兜底有误判风险，结构化协议（`finish` / `interrupt`）是确定的。

```
[08:59:37] 兜底命中：正文提问被翻译成 needs_input ['难度']
```

### 10.11 🔑 交付物清单：产物不止一种（用户提出的关键问题）

**用户追问**：如果有的 skill **两种产物都有**呢？另外，skill **必须显式声明**自己有什么类型的产物吗？

**答 1：必须显式声明，而且不能给默认值。**

我最初写的是 `delivery: ... = "artifact"`——**这是个坏设计**：

- skill 实际产 inline 但忘了声明 → 按 artifact 判 → **永远 failed**
- skill 实际两样都有但只声明了一样 → 另一样**静默丢掉**

**"忘记声明"变成静默错误**——正是我们一路在消灭的那类问题。交付形态是**契约**，不该有隐含默认。

**答 2：`delivery="both"` 不够，应该是「交付物清单」。**

`both` 只能表达"恰好两样"。真实场景需要：**三样产物**、**某样可选**、**报告"具体缺了哪样"**。
所以升级成一组具名交付物：

```python
@dataclass(frozen=True)
class Deliverable:
    name: str                            # "教案" / "课件配置块"
    kind: Literal["artifact", "inline"]  # 落库 还是 走正文
    required: bool = True                # 缺了算不算失败

@dataclass(frozen=True)
class Skill:
    ...
    deliverables: tuple[Deliverable, ...]   # 必填，无默认值
```

**每样交付物独立判定**，「证据」随形态而变：

| 形态 | 交付物去向 | **证据** | 进主上下文吗 |
|------|-----------|---------|------------|
| `artifact` | 产物库，主 agent 只拿 ID | 产物库里**确实有东西** | ❌ |
| `inline` | 回复正文 | 正文非空，**且不是在提问** | ✅（本来就要给调用方） |

平台约定按清单**精确注入**（对应 sx-agent 的 `_SKILL_BASE_INSTRUCTIONS`）：

```
1. 交付物「教案」→ 用 write_artifact 写入产物库（正文写全）。
2. 交付物「课件配置块」→ 直接写进你的回复正文（调用方会解析它），不要 write_artifact。
3. 最后必须调用 finish 登记结果：delivered 列出你实际交付了哪些。
```

**实测**（`debug_delivery.py`，DeepSeek v4 pro，48 秒）：

| 场景 | 结果 |
|------|------|
| 单样 · 落库（备课） | ✅ `教案 → art_001` |
| 单样 · 正文（课件配置） | ✅ `课件配置块 → 正文 151 字`，**产物库为空** |
| **多样 · 落库+正文** | ✅ `教案 → art_002` + `课件配置块 → 正文 49 字` |

### 10.11.1 🔴 踩到的 bug：模型自报的交付清单**不可信**

第一版按模型在 `finish` 里声明的 `delivered` 判定，结果 `lesson-with-config` **误判失败**：

```
模型自报：delivered = ['教案：分数的初步认识', '课件配置块']
skill 声明：           '教案'
精确匹配不上 → 判为"教案缺失" → failed
但产物库里明明有 art_002
```

**模型给名字加了后缀。** 而这正好印证了本讨论一路的原则：

> **以证据为准，不以模型自述为准。**

修正：`claimed`（模型自报）**完全不参与判定**，只写进日志供对照诊断。
判定只看两样东西——**产物库里确实有东西** / **正文非空**。

**这是同一个原则的第三次应用**：
1. §10.9.1「正文说完成了」不算数 → 要看产物库
2. §10.9.1「执行器报 done」不算数 → 要看证据
3. §10.11.1「模型报 delivered」不算数 → 要看证据

### 10.11.2 原设计缺陷：把交付形态写死成"必须落库"

**用户指出的两类产物**：

1. **落库文件** —— 教案 / 导学单 / 课件，进产物库
2. **正文协议块** —— skill 要求 LLM 生成的**特定标记 / 配置**，
   **业务侧（调用方）能识别，系统本身不关心**，**不落库**，**只能走正文**

**原设计的缺陷**：把"交付形态"写死成"必须落库"，
对第 2 类**直接判错**——那种 skill 会**永远 `failed`**（它压根不会去写产物库）。
§10.9.1 那条"产物库为空就是 failed"的保险，**只对 `artifact` 成立**，不能推广。

**另一个 bug（inline 交付物取错位置）**：
模型在 `finish` 之后还会补一句「课件配置已生成并交付…」的总结，
**最后一条 AI 消息不是交付物**。真正的交付物在**带 `finish` 调用的那条 AI 消息**的 content 里。
（见 `_inline_deliverable`）

### 10.11.3 对 sx-agent 的启示：从「提示词分流」改成「声明 + 强制」

`agent_builder.py:55-57` 那段注释**已经识别了这个区分**：

> 第 2 条区分"文件"与"只是给人看"两类出口：前者走产物，后者留在回复正文。
> 少了这条，模型会把本该留在正文里的内容（调用方要解析的协议块、边界标记）
> 当成"要交付成文件的内容"塞进产物，正文只剩一句"已生成"，调用方解析不到。

但它现在是靠**提示词让模型自己分流**（"要交付成文件的内容走 `create_artifact`，
只是给人看的留在正文"）——**属于"靠模型自觉"**。

而**交付形态其实是 skill 的静态属性**，应该在 skill 定义里**声明**、由平台**强制**：

| 收益 | 说明 |
|------|------|
| 平台约定**精确注入** | 不用写一段"你自己判断该走哪条路" |
| 判定完成**知道该看哪里** | 产物库 / 正文 / 两者，逐样核对 |
| 模型**少一个判断负担** | 出错面变小 |
| **可静态校验** | skill 模板里出现"协议块/标记"却没声明 inline → 校验期就报警（他们有 `app/skills/validating/`） |
- 模型少一个判断负担，出错面变小

### 10.12 🔄 重设计：Skill / Task / Sub Agent 三者正交

> 触发：读完 `ref/deepagents` 参考实现后，确认旧原型**过度设计**（§10.11.1）、
> 且**缺了 Task 这个显式概念**（`plan: list[str]` + `params: dict` 把 Task 拆散了）。

**用户强调的核心理念**：

> **Skill** 是专业能力（指令 + 工作流程 + 辅助资源，按需加载）
> **Task** 是具体业务工作
> **Sub Agent** 是**可选**执行者（复杂任务不意味着一定要建 Sub Agent；
> 只有并行、专业能力隔离、上下文隔离**确有收益**时才委派）

**新设计的三概念**：

| 概念 | 是什么 | 载体 | 生命周期 |
|------|--------|------|---------|
| **Skill** | 专业能力包（静态） | 注册表里的 `Skill`：`description` + `instructions` + **可选** `params` | 长期 |
| **Task** | 一次具体业务工作（动态） | `Task` TypedDict：`skill` + `params` + `status` + `artifacts` + `report` | **跨轮存活** |
| **Sub Agent** | **可选**执行者（一次性、通用） | `run_task()`：拿指令+参数干活，**不绑任何 skill** | 一次性 |

> **Task 是接合点**：主 agent 拿着 Skill 的知识，为一件具体工作建一个 Task，
> 再把它交给（可选的）执行者。**三者正交**——skill 不绑执行者，执行者不绑 skill。

**🔴 关键区分：`Task.status` 不是协议。**

它是平台**根据「产物落盘了没有」自己推断**的（`pending/done/awaiting/failed`），
执行器**什么都不用声明**。这与被砍掉的 `ExecResult.status`（执行器**声称**的）性质完全不同。

**流程**（方案 A：awaiting 时一律把用户下一条消息当补充）：

```
START ──entry_route──┬─(有待答复的 Task)→ dispatch ──→ END
                     └─(无)─────────────→ plan ──┬─(声明参数缺)→ END（问用户）
                                                  └─(齐)────────→ dispatch ──→ END
```

**砍掉的（对比旧原型）**：

| 砍掉 | 换成 |
|------|------|
| `finish` 工具 | **不需要** —— 产物落盘就是完成 |
| `ExecResult.status` 枚举 | **产物在不在**（既有事实） |
| `deliverables` 清单 + `Deliverable` 类 | **不需要** —— 平台约定只有一句"交付物调 write_artifact" |
| `_judge_deliverables` 判定逻辑 | 塌缩成"产物库空不空" |
| `_detect_body_question`（LLM 检测） | **不需要** —— "没产物就转述执行器的报告"是确定性的 |
| `interrupt` 模式 | **不需要** —— `awaiting` 由 Task 状态推导，不需要挂起点 |
| 草稿/断点外置 | **不要** —— 接受重跑，换掉一整类 bug |

**实测**（DeepSeek v4 pro，1分12秒，3 个技能 + 2 轮问答）：

```
plan: 能力=['lesson-prep','guided-learning','quiz'] 已知=['年级','学科']
plan: 声明参数并集=['年级','学科','课题','课时'] 减去已知 → 待问=['课题','课时']
   ↑ 并集是**代码算的**，模型只负责"选能力 + 抽已知"
dispatch: t1/lesson-prep ⚠️ 无产物 → awaiting（转述执行器的原话给用户）
dispatch: t2/guided-learning ✅ art_001
dispatch: t3/quiz ✅ art_002
（用户答"难度=基础"）
dispatch: t1/lesson-prep ✅ art_003
```

**全程零协议**：`quiz` 这个技能**故意没声明参数**（模拟"业务人员写 skill 时没想到"），
平台照样兜住——它缺参数时没产物，平台转述它的话，用户答完接着跑。

### 10.13 🔴 两个「LLM 不可靠」的发现，都用「交给代码」修掉了

重设计过程中实测到两个模型不可靠点，**都不是靠调提示词解决的**：

| 现象 | 错误做法 | 正确做法 |
|------|---------|---------|
| 模型把「年级」写成 `grade`、「课题」写成「具体章节或知识点」、「学科」写成「科目」 | 提示词里写"参数名必须逐字一致"——**实测无效**，照样改写 | **动态 schema 把参数名固定成字段**（`create_model`），模型**没有命名的自由**，只能填值 |
| 模型算不准"参数并集"（把 `guided-learning` 声明的「课时」漏掉） | 提示词里写"务必去重" | **平台用代码算**（`declared_params()`），模型只做"选能力 + 抽已知" |

> **同一条原则的又一次应用：**
> **能靠代码算的，不要交给 LLM；能靠 schema 约束的，不要靠提示词。**

### 10.14 🔄 再改：参数**不抽取**了 + 主 agent 先答 + 逐个问

> 触发：用户指出"**你怎么能要求大语言模型如何提取参数**——
> 任何基于规则、正则的方法都不靠谱，自然语言千变万化，**这些地方要柔性，不要硬来**"。

**先把两条原则分清（它们不矛盾，是分工）**：

| | 要柔性 | 要硬性 |
|---|---|---|
| **对象** | **理解**自然语言（用户说了什么、缺什么） | **状态机**（谁在问、答给谁、怎么恢复） |
| **手段** | LLM 自由理解，平台不抽取、不比对 | 代码判定，**不问 LLM** |

**用户确认的两条设计**：

1. **"主 agent 先答"这一层是需要的** —— 执行器缺信息时，
   **先让主 agent 用它的上下文试答**（它可能有记忆、产物、历史），答得上就不打扰用户
2. **乙：按 Task 逐个问** —— 同一时刻**最多一个** Task 处于 `awaiting_user`，其余排队。
   这样"谁在问、答给谁"完全确定

**新状态机**（`Task.stage` 就是身份，也是硬机制）：

```
pending        可以派发
awaiting_agent 缺信息，等主 agent 试答
awaiting_user  缺信息，已问用户，等答复   ← 同一时刻最多一个
done / failed  终态

START ──entry_route──┬─(有 awaiting_user)──→ dispatch   （用户这条消息是答复）
                     ├─(有 pending)───────→ dispatch
                     ├─(有 awaiting_agent)→ resolve      （主 agent 先试答）
                     └─(都没有)───────────→ plan（只选能力）

dispatch ──┬─(有 awaiting_user)──→ END（等用户）
           └─(有 awaiting_agent)─→ resolve ──┬─(答上了)→ dispatch（**不打扰用户**）
                                             └─(答不上)→ 抛给用户 → END
```

**这一版砍掉的**：

| 砍掉 | 原因 |
|---|---|
| `Plan.params` + 动态 schema | 硬来 —— 逼模型把用户的话塞进我的字段表 |
| `declared_params()` 并集计算 | 为硬来服务的 |
| **`Skill.params` 声明** | 就算写成"可选"，平台一用它，硬路径就回来；而且它**逼着作者声明参数 = 约束** |
| `Task.params` | 参数活在对话里，不存在 Task 里 |
| 假模型的 `k=v` 解析 | 教科书级硬规则 |

> **`Skill` 现在只剩 `description` + `instructions`** —— 平台对作者的约束降到最低。

**实测**（DeepSeek v4 pro，2分10秒）：

```
第 1 轮  plan: 能力=[备课, 导学单, 小测]（不抽参数，用户原话直接带进去）
        dispatch: t1 ✅ art_001   t2 ✅ art_002,art_003   t3 ⚠️ 无产物 → awaiting_agent
        resolve:  主 agent 答不上 t3 → 抛给用户          ← 一次只问一个 ✅
第 2 轮  dispatch: t3 收到答复 → ✅ art_004
```

> **全程只问了用户一次。** 平台没有抽取过任何参数——用户原话原样带给执行器。

**⚠️ 一个必须诚实说的观察**：真实模型下，`lesson-prep` **没问课题就直接产出了**。
假模型会问，真模型倾向"将就着做"。这不是 bug，是**柔性的代价**：
平台不强制作者声明参数，所以**执行器是否追问，取决于 skill 指令写没写清楚**。

> 这正是产品原则的体现：**"形式能跑就行，效果由作者迭代"**。
> 作者想要"必须问清楚课题"，就在 instructions 里写一句——那是**自然语言的约束**，
> 不是平台强加的结构约束。
