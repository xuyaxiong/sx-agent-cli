# 上下文交接审计 —— 逐点查「交接了什么 / 截没截 / 落在哪」

> 这份文档回答一个问题：**这个系统里，一共有多少处上下文交接，每一处到底交接了什么。**
>
> 判据是用户 2026-11-02 的「交接三问」（`principles.md` ⑪）：
> **① 交接了什么内容　② 内容是否被截断了　③ 过长的内容是否考虑了渐进式披露。**
> 再补一问（用户 2026-11-03）：**④ 它落在谁的上下文里、会不会一直涨** ——
> 因为"没被截断"不等于"安全"，**全文进上下文本身就是膨胀的隐患**。

---

## 〇、怎么读这份文档

| | |
|---|---|
| **范围** | 运行期（`proto/`）+ 评测期（`evals/`）**全部**把文本从一处搬到另一处的点，共 **23 处** |
| **判据** | 每一处都要能回答：**交接了什么 · 历史消息给到哪 · 截没截 · 落在哪** |
| **真值** | **代码**。本文与 `architecture-diagram.md` §三 不一致时，以本文（附 `file:line`）为准 |
| **与 §三 的关系** | §三 是**架构叙事**（13 跳，讲"数据怎么流"）；本文是**审计视图**（23 处，讲"交了什么、截没截、落在哪"）。§三 覆盖的是主链路，本文多出的是**执行器内部循环 / 快照与重放 / 评测层 / 播报层** |

**四种截断状态**（全文统一用这四种记号）：

| 记号 | 含义 | 允许吗 |
|---|---|---|
| ✅ **不截** | 一个字都没切 | ✅ 但**必须说清落在哪**（膨胀隐患） |
| ⚠️ **显式截断** | 切了，且**带标记 + 说出全文在哪** | ✅ 这是正当出路之一 |
| 📋 **清单 + 按需** | 常驻的只是清单（ID / 字数 / 梗概），正文用工具按需取 | ✅ 渐进式披露，最正当的出路 |
| 🔴 **静默截断** | 切了，读的人**不知道**自己被切了 | ❌ **最糟的一种**（原则 ⑪ ②） |

## 二、运行期逐点详查

### H1 · 用户输入（用户 → 图）

| | |
|---|---|
| 代码 | `evals/chat.py:650` / `evals/_child.py:66`：`graph.invoke({"messages": [HumanMessage(text)]})` |
| 交接了什么 | 用户原话，**不加工、不解析、不判断**（"答非所问就答非所问呗"） |
| 截断 | ✅ 不截 |
| 落点 | `state["messages"]`，**永久常驻**；且被 `_user_turns` 快照进每一个 Task |
| 隐患 | 用户**可能粘长文**（改教案那种）→ 主上下文一次涨几千字。这是**无法预防**的（原话是事实来源，不能切）—— 只能靠"别让它再被复制第三份"（见 §四） |

### H2 · 系统提示 + 能力清单（平台 → 主 agent）

| | |
|---|---|
| 代码 | `proto/agent.py:733` `build_agent()`；`_MAIN_PROMPT` 在 `proto/agent.py:44` |
| 交接了什么 | 平台约定（两种做法 / 委派纪律 / 产出范围 / 前序产物怎么传 / 点名依据 / 回复硬要求）＋ **每个能力的 `name` + `description`** |
| 截断 | ✅ 不截 —— 但**内容本身只有"名 + 一句话"**（渐进式披露第一层），全文走 `read_skill`（H16） |
| 落点 | **不在 `state["messages"]` 里**（`create_agent(system_prompt=...)` 不落 state），**每次 LLM 调用重发一遍** |
| 实测开销 | `_MAIN_PROMPT` 2149 字 + 能力清单 174 字 = **2331 字固定开销**（4 个内置技能时） |
| ⚠️ 计量缺口 | `harness._sys_prompt_chars()`（`evals/harness.py:342`）**没算 `_MODE_NOTE`** —— `exec_path=delegate/inline` 时低估 82 字（`proto/agent.py:721`） |

### H3 · 派发参数（主 agent → 平台）

| | |
|---|---|
| 代码 | `proto/agent.py:522` `delegate(skill_name, task, artifacts, based_on_turns)` |
| 交接了什么 | `task`（**LLM 写的自由文本**）、`artifacts[]`（产物 ID）、`based_on_turns[]`（点名轮次） |
| 历史消息给到哪 | `based_on_turns` **不搬历史**，只搬"点名"这个动作；真正的搬运在 H4 由平台做 |
| 截断 | ✅ 不截（平台不加工 LLM 给的参数） |
| 校验 | 轮次 / 产物 ID 不存在 → **当场拒绝派发**并给出真实清单（`proto/agent.py:560`/`:572`）——防"静默降级" |
| 落点 | `state["messages"]` 的 `AIMessage.tool_calls`，**永久常驻**（写多长就背多久） |

### H4 · 交接书（平台 → 执行器）★ 所有重入路径的唯一入口

| | |
|---|---|
| 代码 | `proto/handoff/briefing.py` `render_briefing(task)`；调用点：`proto/agent.py` 的 `delegate`（首跑 / 试答后重跑）、`proto/graph.py` 的 `_feed_waiting`（答复投递） |
| 交接了什么 | 六段，逐段见下 |

| 段 | 内容 | 截断 |
|---|---|---|
| 【任务】 | 主 agent 写的 `task` 全文 | ✅ 不截（**标了来源**："主 agent 交代的，可能补了用户没说的"） |
| 【用户原话】 | **全部**用户轮次，一轮一行；`based_on_turns` 点名的那几轮**给全文** | ⚠️ **没点名的轮次切到 40 字**（`_one_line`，`proto/handoff/briefing.py`）：带 `…` ＋ 块尾一句"要看完整上下文就用 `read_user_turn(轮次)` 读，不要凭那几十个字猜" |
| ↳ 每轮的「它在回答的上一句」 | 紧邻的前一条 AI 消息（`after`） | ⚠️ 同样切到 40 字 —— **逃生口同 `read_user_turn`** |
| 【问答经过】 | `qa` 逐对：**执行器问的原话** ＋ **谁答的** ＋ 答复全文，**按时间序**；末尾接 `report`（"它最后说的那句"）——⚠️ 它和「最后一问」**逐字相同时折叠成一条**（确定性去重，2026-11-03），标记写在文本里 | ✅ 不截（折叠的那条**原样在上一行**，不是切掉） |
| 【上次判定】 | 判定给的 `progress` / `missing`（**段头标"判定说"**） | ✅ 不截 |
| 【已经产出的产物】/【可读产物】 | **清单**：`art_id《标题》（N 字）—— 梗概` | 📋 正文不进来，走 `read_artifact` |
| 【续跑提示】 | 固定一句 | ✅ |

| | |
|---|---|
| **历史消息的范围** | `Task.user_turns` 是**派发那一刻的快照**（`proto/agent.py:241`）：**全部** `HumanMessage` 的顺序编号 ＋ 每轮紧邻的前一条 `AIMessage`。派发**之后**用户说的话不进 `user_turns`，进 `qa`（H14）—— 两者时间上不重叠，天然去重 |
| **逃生口** | `read_user_turn(n)`（`proto/executor.py:372`，**闭包造**，并行 delegate 不互相覆盖）返回**整轮**：原话全文 ＋ 它回答的那句全文 |
| **落点** | 执行器上下文（`HumanMessage(task_text)`），**用完即弃** —— 不常驻、不累积 |
| 隐患 | ① 每轮 40 字是**位置信息**，执行器不主动读就只看到开头（设计如此，已带指路）；② `_index()`（`proto/handoff/briefing.py`）对**不在产物库里的 ID 静默跳过**（无标记）—— 跨 run 清库后旧 Task 的产物行会无声消失 |

### H5 · 能力指令 + 技能文件清单（平台 → 执行器）

| | |
|---|---|
| 代码 | `proto/executor.py:455` `task_text = 【能力指令】{skill.instructions}{refs}\n\n【已知信息】{briefing}` |
| 交接了什么 | ① `skill.instructions` **全文**；② 技能自带文件**清单**（相对路径 + 字数）；③ 整份交接书（H4） |
| 截断 | ✅ instructions 不截；📋 文件正文不进来 |
| 逃生口 | `read_skill_file(skill_name, path)` —— 清单里**必须写明 `skill_name`**，否则执行器只能猜技能名（实测试了 4 个变体、卡了 121 秒后放弃，`proto/executor.py:442`） |
| 落点 | 执行器上下文；每次重入**重新发一遍**（`skill.instructions` 重复 N 次不累积，因为执行器用完即弃） |

### H6 · 产出落库（执行器 → 产物库）★ 隔离的落点

| | |
|---|---|
| 代码 | `proto/artifacts.py:99` `store_artifact()` / `:129` `write_artifact()` |
| 交接了什么 | `title` / `summary` / `file_type` / `content`（**全文**）→ 内存 `ARTIFACTS` ＋ 当场落盘 |
| 回给调用方的 | **只有**：`已写入产物 art_001（N 字，md）\n文件：<真实路径>`（`proto/artifacts.py:144`） |
| 截断 | ✅ 不截（正文全文落库；**回执极短**） |
| 落点 | 内存库 + 磁盘。**主 agent 的上下文里没有正文** —— 这正是整个架构的核心收益 |

### H7 · 推回去（平台 → 执行器，react 循环内）

| | |
|---|---|
| 代码 | `proto/executor.py:518`：`messages = list(resp["messages"]) + [HumanMessage(nudge)]`；`nudge_text` 在 `proto/handoff/nudge.py` |
| 交接了什么 | `progress`（"你已经完成了"）＋ `missing`（逐条）＋ 固定两句（接着做 / 别用"已完成"收尾），**全文字段** |
| **历史消息的范围** | 🔴 **累积**：`resp["messages"]` 是**上一轮执行器子图的全部消息**（含它自己写的正文、工具返回、读来的产物全文），原样再发一遍 ＋ 新 nudge |
| 截断 | ✅ 不截（`unit_handoff.py` ⑧ 有断言） |

### H8 · 判定输入（平台 → 判定）★ 唯一带"保头保尾"的交接

| | |
|---|---|
| 代码 | `proto/handoff/judgement.py`：`build_prompt()`（输入模板）＋ `_judge_material()`（取材）＋ `_clip()`（截断）；**LLM 调用**在 `proto/executor.py` 的 `_judge()` |
| 交接了什么 | ① `skill.instructions` **全文**；② `briefing`（**整份交接书**）**全文**；③ `material`；④ 产物条数；⑤ 判定规则（静态） |
| `material` 的取材 | **有产物** → 产物正文（**不含散文**）；**无产物** → **全部轮次**的 AI 产出（只取最后一条会让判定看不到前面几轮） |
| 截断 | ⚠️ **显式**：每项 4000 字（`JUDGE_ITEM_BUDGET`）、保头 60% + 保尾 40%、中间插标记；总量 16000 字（`JUDGE_TOTAL_BUDGET`），超了砍后面的项并**说明少了几项** |
| 标记措辞 | `……【平台截断：中间 N 字因提示词长度限制未展示给你。**你无法看到这部分**，所以不要仅凭「看不到」判未完成；但若在**看得到**的部分发现占位符、待补充、半成品，照常判未完成】……`（`proto/handoff/judgement.py`） |
| 落点 | **一次性调用，不留存** —— 但它是**执行器每一轮都跑一次**的额外 LLM 调用，输入 = instructions ＋ 整份 briefing ＋ 最多 16000 字材料 |
| 隐患 | ① **briefing 全文进来**意味着交接书在这里被**又发了一遍**（与 H4 同源、不同调用）；② 4000 是**可调阈值**，产物再长仍会截，那时判定的"完成"是**推测**不是判断（`proto/handoff/judgement.py` 已记档，完整性最终靠落盘 + 人工审计） |

## 四、膨胀账：谁在长、长多快

**主 agent 上下文的逐轮增量**（T 轮、每轮 N 个 Task）：

```
Δ(每轮) ≈ 用户原话
        + 台账 SystemMessage        ← 每轮一份，永不删除（H12）
        + delegate 参数（task 全文）  ← 在 tool_calls 里（H3）
        + 回执 ToolMessage          ← 含执行器 report 全文（H10）
        + 透传 AIMessage            ← 同一段 report 再来一遍（H13）
        + 按需读的产物 / 技能原文     ← 读了就一直在（H15/H16）
```

**三条最值得盯的**：

| 现象 | 量级 | 出处 |
|---|---|---|
| 🔴 **同一段执行器的话，一轮进两次** | 2 × `report` | H10（回执【执行器说】）＋ H13（finalize 透传）。**纯开销** —— 两个出口说的是同一件事 |
| 🔴 **台账每轮重注入** | T × N 行 | H12。T 轮之后主上下文里有 T 份台账，每份含 150/200/150 字的截断详情 |
| 🟠 **`user_turns` 全文快照存 N 份** | N × 用户原话总量 | H17。不进 LLM 上下文，进内存 / checkpoint；多 Task 时同一段原话存多份 |

**实测读数（2026-11-03，`handoff-verify`）**：

```
report1（275 字）在主 agent 消息里出现 2 次：ToolMessage(513 字) + AIMessage(938 字)
report2（661 字）在主 agent 消息里出现 2 次：ToolMessage(890 字) + AIMessage(938 字)
→ 两条报告合计 936 字，一轮之内进了两遍（回执一次、透传一次）

主上下文逐轮读数：3053 → 4763 → 5928 → 7925 → 16357 字
                  （末轮那一跳 = 读了 5931 字的产物正文，当场超告警线 12000）
产物库 14388 字全程不进主上下文 —— 直到用户开口要它。
```

**读数在哪**（已经有的，不用新建）：

- `harness.CTX_WARN_CHARS = 12000`（`evals/harness.py:312`）：超线**只告警不判红**（读产物是合法能力）
- `harness.snapshot()` 的 `main_ctx_chars`（**不含 system prompt**）＋ `sys_prompt_chars`；真实上下文 = 两者相加
- CLI 每轮打一行：`主上下文 N 字（消息 X + system Y）｜产物库正文 Z 字`（`evals/chat.py:507`）
- 参照读数（历史跑批）：单技能隔离场景 517–1109 字；多技能长产物场景 7890–14832 字

**不进主上下文的三条路**（隔离之所以成立）：

1. 产物正文 → 落库落盘，只回 ID（H6）
2. 技能自带文件正文 → 清单常驻、正文按需（H5/H16）
3. 执行器内部的全部过程 → 随执行器丢弃（H4/H7/H14）

## 五、隐患清单（本次审计发现，**均未修**）

> 排序按"会不会造成错误结论"：会让人**误以为没问题**的排前面。
>
> 📌 **本节的 1 / 2 两条已在真实运行里实测坐实**（2026-11-03），
> 另**新翻出 4 条**本节没写的问题（台账不入 trace、透传被标成主 agent 的话、
> 跑批无产物路径、工具归属错配）—— **见 §九 9.4**。

### 1. 🔴 评测层的回执分段标记**全部失配** → `_run.md` 里回执被静默降级成 1200 字截断

- **现象**：`_RECEIPT_KINDS`（`evals/harness.py:459`）和 `_RECEIPT_SPLIT`（`:485`）里的标记，
  是照**旧回执**（"已交付…"/"⚠️ 这次没完成，它在请求信息"/"执行器说："/"\n\n【已做到】"）写的；
  2026-11-02 `render_receipt` 形式化之后，回执变成了「【交付】…」「【执行器说】（**它说的**…）」
  「【下一步】…」—— **没有一条标记还命中**。
- **证据**（实测）：

  ```
  KINDS hit: []      # 7 条前缀标记，一条不中
  SPLIT parts: 0     # 7 条分段标记，一条不中
  ```

  **全仓回归（2026-11-03）**：`新回执格式 且 分段命中 = 0`（8 份），
  `旧回执格式 且 分段命中 = 38`，**最后一次命中是 11-02 16:39** —— 分界点正是 `render_receipt` 上线。

- **后果**：① 回执在 `_run.md` 里走 `content[:1200]` 兜底（**标记为"…（共 N 字）"，但是切了**）；
  ② "哪句是平台的框架话、哪句是执行器的原话"这层**分段信息全没了** —— 而这正是当初做
  `_split_receipt` 的理由（用户："哪些是提问 来源是哪里"）。
- **讽刺的是**：`_RECEIPT_SPLIT` 的注释自己写着"**命不中的标记不会报错，只会静默失效**"，

## 八、改这一层时的三条硬规矩

1. **切了必须标**，并说清**全文在哪**（`【平台截断：还有 N 字，全文见…】`）。
   悄悄切一刀 = 让读的人分不清"它就说这么多"和"被切了"——而这两种情况该做的决定**完全不同**。
2. **长了只有两条正当出路**：渐进式披露（清单常驻 + 正文按需），或显式截断。
   没有第三条。**摘要 ≠ 截断**：要短就另写一段短的话，不要把原话切一刀。
3. **加字段 / 加返回口时**：要么渲染它，要么在排除名单里写明为什么不渲染
   （`unit_briefing.py` / `unit_receipt.py` 的 `EXCLUDED`）——**加切片时**，要么豁免，要么别加
   （`unit_handoff.py` 的 `ALLOWED`）。

### 9.4 实测翻出的**新问题**（原清单没有，全部有日志）

#### 新 1 🔴 台账注入**在 trace 日志里根本没有记录**

  全仓 **731 份** trace 日志里 `SystemMessage(` **0 份**，仅 4 份出现台账，且全部是
  **试答 prompt 的副产物**（`_ask_prompt` 把全部消息渲染进去时偶然带上的）。

#### 新 2 🔴 透传消息在 `_run.md` 里被标成"**主 agent 输出**"

#### 新 3 🟠 跑批模式下**产物回执没有路径**，而系统提示断言"路径已经给到你了"
