### 0.1 最终设计：Skill / Task / Sub Agent 三者正交

| 概念 | 是什么 | 载体 |
|------|--------|------|
| **Skill** | 专业能力（静态） | 只有 `description` + `instructions` |
| **Task** | 一次具体业务工作（动态） | `{skill, given, stage, artifacts, report}`，**跨轮存活** |
| **Sub Agent** | **可选**执行者（一次性） | 通用 `run_task()`，**不绑任何 skill** |

### 0.2 四条设计原则

1. **理解要柔性，状态机要硬。**
   平台**不抽取参数**——用户原话原样带给执行器，由它自己理解。
   但「谁在问、答给谁、怎么恢复」**必须确定性**，代码判定，不问 LLM。

2. **能靠既有事实判定的，不要发明协议。**
   **完成 = 产物库非空**。执行器不声称 `status`、不调 `finish`、不报交付物清单。

3. **能靠代码算的，不要交给 LLM；能靠 schema 约束的，不要靠提示词。**
   （实测：模型会漏字段、会改写参数名）

4. **平台少约束 skill 作者。形式能跑即可，效果由作者迭代。**
   任何**依赖作者配合**的机制都是脆的——作者一句自然语言就能覆盖平台约定。

### 0.3 三个原始问题的最终解法

| 原问题 | 最终解法 |
|--------|---------|
| **P1** 重复问参数 | 执行器读**同一份用户原话** → 都不会问已知的；各自缺的**逐个问** |
| **P2** 没干完就重开 | **Task 是状态载体**，执行器一次性、不跨轮 → 结构上不可能"重开" |
| **P3** 正文提问走向不定 | **`Task.stage` 是身份**，入口路由纯代码判定 → "谁在问、答给谁"确定 |

### 0.4 全部砍掉的东西（曾经以为必需）

`finish` 工具 · `ExecResult.status` 枚举 · `deliverables` 清单 · `Deliverable.required` ·
`_detect_body_question`（LLM 检测）· `interrupt()` + `Command(resume)` · 草稿/断点外置 ·
`Skill.params` 声明 · 动态 schema 抽参数 · `declared_params()` 并集计算

### 0.5 关键发现（推演过程中最有价值的几条）

1. **"提问"曾经是输出，不是控制流事件** —— 没有挂起点，"恢复"只能靠历史文本假装（§3.2、§6.1）
2. **`interrupt()` 是「返回值」不是「异常穿透」**，每一层包装都得显式透传（§6.7）
3. **把提问做成「图节点」而非「工具」**，结构性避开悬空 tool_call → API 400（§10.7）
4. **DeepAgents 的子 agent 是纯函数**（ephemeral / stateless / 一次报告），
   所以 P1/P2/P3 在它那里**不存在**——不是解决了，是压根不会发生（§10.12）
5. **模型的话是线索，不是事实**：正文说"完成"不算、执行器报 done 不算、
   自报 delivered 不算——**一律看证据**（§10.9.1、§10.11.1）

## 一、要解决的问题

### 1.1 用户最初的三个症状

| # | 症状 |
|---|------|
| **P1** | 多个 skill 参数重叠，**重复问用户**（"我明明已经输入过了"） |
| **P2** | subagent 没干完就退出，主 agent **重开一个从头干**，又请求参数 |
| **P3** | subagent 用**正文输出**请求参数（没挂起），用户答复后走向不确定 |

### 1.2 用户的真实诉求与约束

- **要上下文隔离**（"防止上下文爆炸"）——这是当初引入 subagent 的唯一理由
- **业务人员写 skill，不懂 agent 运行机制，短期无法改善**
- **平台要尽量少约束 skill 作者**："形式上流程能跑，效果由作者迭代"

### 1.3 需求清单是「锚点」（改设计前必看）

**F1–F10 功能 / Q1–Q5 质量 / C1–C4 约束 / N1–N3 非功能 / X1–X6 明确不做** ——
逐条列在本文 §0.6，每条都标了**来源**（用户原话或场景编号），可追溯。

**规矩**：

> **改架构前先看它。某条需求如果被某个设计牺牲了，必须显式说明，不能悄悄丢。**

**「明确不做」的（X 类）也要记** —— 避免反复讨论同一个已被否掉的方案。
本次明确不做的两条已经落位：

| # | 不做什么 | 为什么 | 落在 |
|---|---------|--------|------|
| **X1** | **不恢复 plan 节点** | 职责已被主 agent 的循环吸收 | §2.1.1 |
| **X4** | **不做草稿 / 断点外置** | 接受重跑，换掉"草稿 vs 成品"一整类 bug | §2.1.1 · §8.4 |

其余（`X2`/`X3`/`X5`/`X6`）见 §1.5。

### 1.4 一句话结论

> **P1/P2/P3 不是"隔离"的代价，是「把 subagent 边界画在整个 skill 生命周期上」的代价。**
> 把边界收窄到「**参数齐了之后的执行段**」，三个问题结构性消失，**而隔离保留**。

## 二、核心设计

### 2.1 三个概念，三者正交

| 概念 | 是什么 | 载体 | 生命周期 |
|------|--------|------|---------|
| **Skill** | 专业能力包（静态） | `description` + `instructions` | 长期 |
| **Task** | 一次具体业务工作（动态） | `state["tasks"]` 里一条 `{skill, given, stage, artifacts, report}` | **跨轮存活**（同一 thread 内） |
| **Sub Agent** | **可选**执行者 | `create_agent` 建的一次性实例 | **用完即弃** |

**关键推论**：

- **Skill 不绑执行者** —— 加一个技能不需要动平台（`run_task(skill, given)` 通用）
- **执行器不持有状态** —— 状态在 `Task` 上，所以"重新起一个"是无害的
- **Task 只在主 agent 决定委派时才建** —— 不委派就没有 Task
- **执行器从不直接问用户** —— 它只把"缺什么"回给主 agent。这是 **P3 结构性消失**的原因：
  提问者**永远是主 agent 自己**，所以不存在"答给谁"的歧义

> ⚠️ **"跨轮存活"是 P2 修复的承重属性。** Task 不是"随一轮图结束就没了"，
> 它靠 checkpointer 跨轮活着。**前提是同一会话的 `thread_id` 必须跨轮稳定** ——
> 每轮换新 `thread_id` 会**静默**退化成"每次都是新会话"，
> Task、台账、supersede 全部失效，而且**不报错**。

### 2.1.1 被明确否决的方案（免得走回头路）

| 方案 | 为什么否决 |
|------|-----------|
| **断点 / 草稿外置**（把执行进度写进产物或草稿，供下次续跑） | **接受重跑** —— 宁肯让执行器重跑一遍，也不要"草稿 vs 成品"这个状态区分，那会一次引入**一整类 bug**。代价是重复劳动 + 产物重复（见 §9.1 T3/T4），这个代价是**已知且接受**的 |
| **恢复用 `interrupt()` + `Command(resume)`** | 见 §8.4「为什么不走 interrupt」 |
| **恢复 plan 节点**（复杂任务先规划再执行） | 职责已被主 agent 的循环吸收；`delegate` 是同步的，依赖在主 agent 循环里天然解决 |

### 2.2 主 agent 是**完整的 agent**，不是纯路由器

```
主 agent 循环
  ├─ 直接答            —— 闲聊 / 追问 / 澄清（不建 Task）
  ├─ write_artifact    —— 自己产出短内容（不建 Task）
  ├─ list_artifacts    —— 看产物清单（ID/名称/字数/梗概，不含正文）
  ├─ read_skill        —— 按需读技能原文（核对交付标准）
  ├─ read_artifact     —— 按需读产物全文（渐进式披露第二层）
  └─ delegate(...)     —— 需要专业能力时（建 Task）
```

> ⚠️ 后三个是 **2026-10-29 加的**（F11/F12）：主 agent **不是包工头** ——
> 它要能执行、也要能按需读技能与产物。**常驻的只有 `name + description` 与产物清单，
> 全文一律按需**（渐进式披露），否则主上下文会被长文撑爆。

**为什么"技能活一律委派"**（去掉了 `load_skill`）：
实测给了它"自己干技能活"的路，它就会走——**隔离全丢**。
而且**它在派发前无法判断产出有多长**（备课可能 300 字也可能 3000 字），所以不要让它猜。

### 2.3 平台在旁边只做两件事

| 节点 | 做什么 | 硬/软 |
|------|--------|-------|
| `prepare` | 把**任务台账**注入主 agent 上下文 | **硬**（平台保证注入） |
| `finalize` | 检查待答都问出去了吗，没问就补 | **硬**（保证不丢） |

**都只提供事实，不替它做决定**（"用户是不是在回答"是理解问题，该柔性）。

## 四、模块详解（结合代码）

### 4.1 `skills.py` —— Skill 定义 + 产物库

**Skill（只有两个字段）**：

```python
@dataclass(frozen=True)
class Skill:
    name: str
    description: str    # 主 agent 靠它判断"什么时候该用"
    instructions: str   # 完整工作流程；派发时给执行器，判定完成时也带进提示词
```

**被删掉的字段**（记在 docstring 里，免得走回头路）：

| 字段 | 为什么删 |
|------|---------|
| `params` | 逼作者声明参数；而"参数名"是平台的词汇表，用户的自然语言不该被塞进去。实测模型会改写参数名（「学科」→「科目」） |
| `deliverables` / `finish` / `status` | 能靠既有事实判定的，不要发明协议 |
| `completion_criteria` | **没有增量价值** —— 要求本来就在 `instructions` 里，再抄一遍是重复；而且会把"必须包含 X"硬套到不该套的任务上。`debug_criteria.py` **自己写的测试 9/9 全过仍然被否**（⚠️ 早先记的"4/6 更差"已不可复现，见 §7.1） |

> 📌 **这两组记在两个地方**，别只找一处：
> `skills.py` 的**类 docstring** 记 `params` 与 `completion_criteria`（它自己写的是"两个"），
> **模块级 docstring** 记 `deliverables` / `finish` / `status`。

> 🔴 **`completion_criteria` 的否决比"4/6"更硬**：`experiments/debug_criteria.py`
> **自己写的测试 9/9 全过，仍然被否** —— 理由是**没有增量价值**（要求已经在 `instructions` 里），
> 不是"测得不好"。有人拿"我测过 criteria 全过"重提时，这就是反驳材料。
>
> 若将来真要保留，评审建议的放法是 **`metadata.platform`**（兼容通用 skill 规范 ——
> DeepAgents 就是把 `include_tools` 放在 `metadata` 里的），**不要新增顶层字段**。

**产物库**（"文件系统"的替身，**上下文隔离的落点**）：

```python
ARTIFACTS: dict[str, dict[str, str]] = {}     # ⚠️ 内存 dict，生产必换

def store_artifact(title, summary, content) -> str   # 返回 art_001 这样的 ID
@tool write_artifact(title, summary, content) -> str # 梗概由**产出方**在交付时一起给
@tool read_artifact(artifact_id) -> str              # 按需读回全文（渐进式披露第二层）
@tool list_artifacts() -> str                        # 清单：ID/名称/字数/梗概，**不含正文**
```

**原型里的 4 个技能**：

| 技能 | instructions 要点 |
|------|------------------|
| `lesson-prep` 备课 | 需要知道「**课题**」和「**课时**」——不知道就先问 |
| `guided-learning` 导学单 | 需要知道「**课时**」 |
| `quiz` 随堂小测 | 需要知道「**难度**」（基础/提升/挑战） |
| `courseware-config` 课件配置 | 产出**正文协议块**（不落库，给调用方解析）——用来验证 S7 |

### 4.2 `llm.py` —— 结构化输出 + 兜底

> 🔴 **一条贯穿全案的施工规范：决策的结果必须结构化。**
>
> 所有 LLM 判定都走 **Structured Output**（OpenAI `response_format` /
> LangChain `with_structured_output`）—— 把 JSON Schema 传给模型，
> **模型原生保证结果符合结构**，不需要靠提示词去"求"它按格式输出。
>
> **不要靠工具参数去传决策。** 反面教材就是早期的 `finish` 工具：
> 让模型"调一个工具来宣告完成"——**模型不调，决策就静默丢了**。
> 不报错、不抛异常，只是没人知道任务完成了。这正是 `finish` 被砍掉的**真正原因**
> （不只是"能靠既有事实判定"那么简单）。
>
> **通用检查动作**：以后新增任何 LLM 判定，都问一遍「**它的输出结构化了吗？**」
> 结构化之后，代码才能拿它做逻辑转移判断。

```python
def safe_structured(schema, prompt, default, *, tag="") -> Any:
    """重试 1 次 → 仍失败则退化到**保守默认值**"""
```

**为什么需要兜底**：实测 DashScope 偶发
`grammar validation or compilation failed: sandbox grammar compile timed out`
——**一次抖动就炸掉整个 turn**（踩过两次）。

**三个调用点的保守默认值**（都朝"不丢信息"的方向退化）：

| 调用点 | 失败时默认 | 理由 |
|--------|-----------|------|
| `_judge` | `incomplete` | 会让它再 react 一轮 |
| `_ask_main` | `can_answer=False` | 交给用户，而不是编一个答案 |
| `_which_unasked` | `asked=False` | 宁可重复一句，不能把待答丢掉 |

### 4.3 `executor.py` —— 执行器（判定 + 出口限制）

#### 4.3.1 平台约定（**逐字**）

```python
_PLATFORM_RULE = (
    "你是任务执行者。按下面的能力指令完成任务。\n"
    "要交付成文件的内容，调用 write_artifact 写入产物库：**名称、一句话梗概、正文**三样都给，\n"
    "正文写全（梗概是对外露出的那一层，别人靠它决定要不要读全文）。\n"
    "任务里列出的【可读产物】只是一份**清单**（名称与梗概）——需要全文时用 read_artifact 读，\n"
    "不要凭标题或梗概猜内容。\n"
    "\n"
    "如果缺少完成任务所必需的信息：\n"
    "- **明确说明你需要什么**（缺哪个参数、要什么确认）——你的请求会被转给能提供它的一方；\n"
    "- **不要编造**，也不要用「已完成」之类的话收尾。\n"
)
```

> **措辞理由**：说"**转给能提供它的一方**"，不说"向用户提问"——
> 因为**执行器是隔离的，它不知道有主 agent**。

#### 4.3.2 出口三态 + 结果结构

```python
OutcomeStatus = Literal["completed", "waiting_for_input", "incomplete"]

@dataclass
class ExecOutcome:
    status: OutcomeStatus = "incomplete"
    artifacts: list[str] = field(default_factory=list)
    report: str = ""
    rounds: int = 0        # 实际 react 了几轮
    progress: str = ""     # 已经做到什么程度
    missing: list[str] = field(default_factory=list)   # 还缺什么
```

**判定的输出结构**（`_Judgement`，走 `with_structured_output`）：

```python
class _Judgement(BaseModel):
    status: Literal["completed", "waiting_for_input", "incomplete"]
    progress: str = ""
    missing: list[str] = Field(default_factory=list)
    reason: str = ""       # 一句话理由 —— 只写日志，供事后复盘误判
```

> `reason` 是**唯一的可观测面**：trace 日志里能看到"判定为什么这么判"。
> 重实现时最容易漏 —— 漏了就没法复盘误判。

> **为什么用枚举不用两个布尔值**：两个布尔有 4 种组合、只有 3 种合法，
> "矛盾组合"只能靠约定排除；**枚举从类型上就闭合**。

> 🔴 **同一类错的第二种形态：隐式 `else`。** 主 agent 试答后重跑，结果有三种，
> 但代码只判了两种 —— **`incomplete` 被隐式当成"在请求信息"，于是去问用户**。
> 用户根本没被问过，系统却去问他 —— 这就是 **P3 复发**。
> **修法不是加个 `else`，是把三个分支显式写全。**

#### 4.3.3 判定规则（**逐字**）

```
根据任务要求和实际执行结果，判断任务状态：
- completed：任务已完成，且满足必要的交付条件。
- waiting_for_input：任务尚未完成，且明确请求了继续所必需的信息。
- incomplete：任务尚未完成，但不属于请求信息的情况。

判定规则：
1. **需要文件产物的任务**：检查产物是否存在、完整且符合要求。
   产物可能有**多个**——逐个检查，缺一个都不算完成。
   占位内容、待补充项、半成品（如「待补充」「TODO」「待填写」）**不能视为完成**。
2. **不需要文件产物的任务**：确认实际工作已经完成。
   不能仅凭执行者声称完成、或输出确认性文字（如「好的」「我了解了」「已收到」）判定。
3. 只有**明确请求继续所必需的信息**，才能判定为 waiting_for_input。
   解释失败原因、表达困惑、描述缺少的信息，**都不算**请求信息。

另外，只要不是 completed，都要填写：
- `progress`：**已经做到什么程度**（哪些部分已完成）——让下一轮能**接着推进**，而不是从头再来；
- `missing`（仅 incomplete 时）：**还缺什么**，逐条列出，越具体越好。
```

#### 4.3.4 判定提示词的**完整输入**（缺一不可）

```python
prompt = (
    f"【任务要求】\n{skill.instructions}\n\n"
    f"【执行者已经拿到的信息】\n{given.strip() or '（无）'}\n\n"
    f"【实际执行结果】\n---\n{target[:2500]}\n---\n\n"
    f"【产物情况】{art_line}\n\n"      # "执行者产出了 N 个文件" / "没有产出任何文件"
    f"{_JUDGE_RULES}"
)
```

⚠️ **`target` 是什么** —— 这一段最容易实现错：

```python
target = _artifact_text(arts) if arts else report
```

- **有产物** → 是**产物正文**（多个产物拼起来）—— 判定要能看到产物**内容**，才能判断完不完整
- **没产物** → 是**执行器的回复正文**

`[:2500]` 是**截断**（判定只看前 2500 字）。

> 若把 `target` 写成"执行器的回复"（而不是产物正文），判定就**看不到产物内容** ——
> 正好是这套机制反复踩的那个坑。

> 🔴 **前两项缺一不可**，**实测各踩过一次**：
> - 不带 `instructions` → "按任务要求判断"是空话
> - 不带 `given` → 明明给了"第1课时"，判定说"未询问用户课时信息" → 误判成 `waiting_for_input`
>
> （第三个坑在 `failed` 分支：没带 `progress`/`missing` —— 见 §5.3。）
>
> **通用检查动作**：每加一个 LLM 判断，都问一遍「**它看得到做这个判断所需的信息吗？**」

##### 🔴 第四个坑：取材取错了那一条（2026-10-29 修复）

**前三个坑都是"提示词忘了带某个字段"，第四个不是** —— 信息**明明在消息列表里，但取错了那一条**。所以前三次的检查法（"字段带了没有"）**发现不了它**。

**症状**：`target` 在**无产物**时用的是 `report = _last_ai_text(resp)` = **最后一条 AI 消息**。而出口循环里消息是**累积**的：

```python
messages = list(resp["messages"]) + [HumanMessage(nudge)]   # ← 上一轮的全部内容都带下去
```

所以第 2 轮的 `resp` **包含第 1 轮的产出**，但只取了最后一条 —— **第 1 轮的交付物判定看不到**。真实日志里执行器自己写着「我没有从头再来，**继续接着上面的进展**」，而"上面"判定看不到。

**修法**：`_judge_material()` —— **两条路的取材不同，别合并**：

| | 交付物是什么 | 判定看什么 |
|---|---|---|
| **有产物** | **产物正文**（就是它） | 产物正文，**不含散文** |
| **无产物** | 只能从 AI 产出里找 | **全部轮次**的 AI 产出 |

每一项**各自**保头保尾（`_clip`）+ **显式标注省略了多少字**，而不是整体截断 ——
这样**每一轮都保证有代表**，不会被整体截断挤掉中间那轮。

> ⚠️ **"有产物时不要把散文喂进来"是实测踩出来的回归**：改的时候我顺手把散文也加上了，
> 结果执行器在产物之后补了句礼貌收尾「……**需要调整吗？**」，
> 判定看到后把它当成"明确请求继续所必需的信息" → 判成 `waiting_for_input`，
> **而产物其实已经完整交付**。（`debug_exit` 的 B 用例当场从 ✅ 变 ❌。）
>
> **标注省略比保头保尾本身更重要** —— 不标的话，判定**不知道自己没看全**，
> 会基于不完整信息**自信地下判断**，那比"猜"更糟。

**回归测试**：`experiments/test_judge_material.py`（纯函数，不调 LLM，18 个断言）。

##### 📌 已记档、暂不做：`need_more` —— 有界的一次补看

现在信息不够时，判定只能**硬判**。可以给它加一条"要更多"的通道：

```python
class _Judgement(BaseModel):
    status: Literal["completed", "waiting_for_input", "incomplete"]
    progress: str = ""
    missing: list[str] = []
    reason: str = ""
    need_more: str = ""     # ← 新增：点名要看哪一段（如"第 2 轮的完整内容"）
```

平台看到 `need_more` 就把那段补上，**再判一次**（**只允许一次**，第二次不许再要）。

- **好处**：判定不再"信息不够也硬判"
- **代价**：多一轮 LLM 调用；而判定在**出口路径**上、`run_task` 里最多跑 3 次，所以延迟会翻倍
- **为什么先不做**：本版刚把"判定看得到全部轮次"修好，**先看实测** ——
  判定还会不会因信息不够判错。**会，再加；不会，就别为一个不出现的问题加一轮调用。**

> 另外 **"有产物"那条路同样受截断影响**：48k 字的课件，判定只看得到前 800 字（`JUDGE_ITEM_BUDGET`）。
> 它判得了"有没有东西"，判不了"完不完整"。**这条路将来也需要渐进式披露**（先给首尾/目录，要细节再要）——
> 和 `need_more` 是同一件事，可以一起做。

#### 4.3.5 出口限制循环

```python
MAX_REACT_ROUNDS = 3

for round_i in range(MAX_REACT_ROUNDS):
    resp = agent.invoke({"messages": messages})       # ⚠️ 不传 config
    outcome.artifacts = _recover_artifacts(resp, preexisting)   # 只认这次新写的
    outcome.report    = _last_ai_text(resp)
    outcome.rounds    = round_i + 1

    j = _judge(skill, outcome.artifacts, outcome.report, given)
    outcome.status   = j.status
    outcome.progress = (j.progress or "").strip()
    outcome.missing  = [x.strip() for x in (j.missing or []) if x and x.strip()]

    if j.status in ("completed", "waiting_for_input"):
        break
    # 剩下只有 incomplete —— 穷举完了，没有第四种

    if round_i + 1 < MAX_REACT_ROUNDS:
        messages = list(resp["messages"]) + [HumanMessage(_nudge_text(j))]
    else:
        # 显式写出：推满了，不再推 → outcome 保持 incomplete → delegate 判 failed
        ...
```

**推回去的提示词**（把判定吐出的信息都喂回去）：

```
任务还没完成。

**你已经完成了**：{progress}

**还缺**：
- {missing 逐条}

请**接着往下做**，不要从头再来。

如果确实缺少必要信息才能继续，就**明确说明你需要什么**（缺哪个参数、要什么确认）；
否则不要用「已完成」之类的话收尾。
```

> **实测效果**：那一轮执行器只把内容写在正文里没落库，判定发现 → 推回去 →
> **下一轮就落库了**。如果不告诉它"内容已设计好、只差落库"，它很可能从头再设计一遍。

#### 4.3.6 产物识别（硬机制）

```python
def _recover_artifacts(resp, preexisting: set[str]) -> list[str]:
    for m in resp["messages"]:
        for aid in ARTIFACTS:          # ← 只遍历产物库里**真实存在**的 ID
            if aid in text and aid not in found and aid not in preexisting:
                found.append(aid)
```

两条口径缺一不可：

1. **必须在产物库里查得到** —— LLM 编 `art_999` 无效
2. 🔴 **必须不是这次跑之前就存在的**（`preexisting`）—— 依赖机制让执行器会
   `read_artifact` 读前序产物，读回来的正文里带着那个 ID，不排除就**把读来的算成它交付的**
   （F14，2026-10-29 实测：guided-learning 读 `art_001` → 任务记录变成"产出 art_001、art_002"）

#### 4.3.7 可调优点（落地后调优从这里入手）

**这套机制的效果，几乎全由下面 6 个地方决定。** 改完**不要凭感觉** ——
跑 `experiments/debug_judge_variants.py` + `debug_exit.py` 验一遍。

| # | 调什么 | 位置 | 往哪调 |
|---|--------|------|--------|
| 1 | 判定规则 1：**需要产物**的任务怎么算完成 | `_JUDGE_RULES` 规则 1 | 松 → 残次品放行；紧 → **吹毛求疵**（实测推 3 轮 4m29s） |
| 2 | 判定规则 2：**不需要产物**的任务怎么算完成 | `_JUDGE_RULES` 规则 2 | 同上。注意"**只说不做**"必须判不完成 |
| 3 | 判定规则 3：什么算"**明确请求信息**" | `_JUDGE_RULES` 规则 3 | 松 → 解释失败也被当成提问 |
| 4 | 执行器缺信息时怎么表达 | `_PLATFORM_RULE` | 说得越清楚，越早走请求信息路径，越少被硬推 |
| 5 | 推回去时怎么说 | `_nudge_text` | 关键是"**你已经完成了 X，还缺 Y，接着做**"，别让它从头再来 |
| 6 | **最多推几轮** | `MAX_REACT_ROUNDS`（现 3） | 调大 → 更执着但**更烧 token**；调小 → 更早交给主 agent |

> 📌 **第 6 条的取舍**：3 轮是"够它自我纠正一次、又不至于无限烧钱"的折中 ——
> **不是算出来的，是试出来的**。

> 🔑 **`_PLATFORM_RULE` 的一个副作用（好的）**：它让执行器**主动说明需要什么** ——
> 于是"干不成"的任务**不再被推满 3 轮**（1–2 轮就说明需要什么了），自然走请求信息路径。
> **早说早处理，不用硬推。** 所以 3 轮上限在实践中**很少被用满**。

#### 4.3.8 正文提问：预防 + 兜底（迁移 `sx-agent` 的必经之路）

`sx-agent` 的 skill **全部是"把问题写进回复正文"**（见 §8.1）。所以每个现存 skill
迁移过来之后，**都会走"正文提问"这条路**。这套机制对它是**预防 + 兜底**两层：

| 层 | 机制 | 作用 |
|---|------|------|
| **预防** | `_PLATFORM_RULE`（"明确说明你需要什么"） | 引导执行器**说清楚缺什么**，而不是含糊地"我做不到" |
| **兜底** | `_judge` 的**判定规则 3** | 把正文里的提问**翻译**成 `waiting_for_input` |

**实测三个场景**：

| 场景 | 结果 |
|------|------|
| 缺参数 | ✅ 被翻译成 `waiting_for_input`（`missing=['难度']`） |
| 参数齐全 | ✅ `completed`，**没有误报** |
| **只说不做**（正文说"已经帮你把题出好了"，但产物库是空的） | ✅ 判 **`failed`，不放行** |

> 🔴 **第三个场景最关键** —— 它就是"**系统看起来成功了，但用户什么也没拿到**"。
> 不写清这条，实现时会把假成功放行。

> ⚠️ 这三个场景当时由 `experiments/debug_body_question.py` 验的，
> **该脚本现在已跑不起来**（依赖被删的 API），见 `../experiments/README.md`。

### 4.4 `agent.py` —— 主 agent

#### 4.4.1 工具集（五个）

| 工具 | 用途 |
|------|------|
| `delegate(skill_name, task, artifacts=[...])` | 委派一件具体工作（**建 Task**）；`artifacts` 是这次要参考的**产物 ID**，平台当场校验 |
| `write_artifact(title, summary, content)` | 自己产出短内容（**不建 Task**） |
| `list_artifacts()` | 产物清单（ID/名称/字数/梗概），**不含正文** |
| `read_artifact(artifact_id)` | 按需读回产物全文（渐进式披露第二层） |
| `read_skill(skill_name)` | 按需读技能原文（渐进式披露第二层）——写 task 前核对交付标准 |

#### 4.4.2 系统提示的**四块**（逐字要点）

**① 两种做法**
```
1. **直接答**：闲聊、追问、解释、澄清、简单修改——不需要专业能力的事，你自己说。
2. **delegate 委派**：需要下面列出的**专业能力**时，**一律委派**，不要自己凭感觉做。

为什么必须委派：专业能力的产出可能很长，自己干会把你的上下文撑爆。
**你在派发前无法判断产出有多长**，所以不要猜——需要专业能力就委派。

委派回来如果显示「没完成」，**先看自己的上下文里有没有它要的信息**：
有就直接再委派一次（带上信息）；确实没有，才向用户提问。
```

**② 信息不全时怎么办**（B2 的落点）

> **实测依据（不写这段会怎样）**：不写的时候，**三轮下来 `Task` 始终 = 0** ——
> 它一直在问，**从来没委派过**。执行器本来就能自己判断缺什么，
> 平台抢先替它问，等于把执行器的活抢了。

```
## 信息不全时，**不要一律问** —— 先判断能不能推进

- 能推进就**先推进**（真的缺东西时，执行器会告诉你）；
- 确实推进不了的，才问用户；要问就**一次问完**（别挤牙膏）；
- **哪些参数是必答的、哪些有默认值，以技能指令为准** —— 平台不替你猜，你也别猜。
```

**③ 产出范围**（用户要求"保守优先"）

> **实测依据（走了一段弯路）**：加上 ② 之后，第一次修法是"**列默认值**" ——
> 结果它**一次派了 3 个技能**，自行扩大了产出范围。所以 ③ 必须单独写死。

```
## 🔴 产出范围**以用户明确说的为准**，不要自行扩大

用户说「帮我备课」就**只出教案**；不要说「我顺便把导学单和小测也做了」。
**用户没要的，不要直接做掉**——那会浪费他的时间和成本。

想提供的话，**在回复末尾提一句**就行（如「需要的话我也可以出导学单和随堂小测」），
让用户自己决定要不要。
```

**④ 前序产物怎么交给下一个任务**（2026-10-29 加，F11/F12 的直接产物）
```
**传 ID，不要转述正文。** 需要前面交付的产物当输入时：
delegate(skill_name="...", task="...", artifacts=["art_001"])
执行器会拿到它的名称与梗概，需要全文自己读。

- 把正文抄进 task 是**错的**：对方拿到的是你的摘要而不是原文（失真），
  而且正文会一直占着你的上下文。
- 不确定有哪些产物 → list_artifacts()
- 不确定某个能力**交付什么、按什么标准交付** → read_skill(name) 读原文核对，
  **不要凭一句话描述猜**：你猜出来的要求会压过能力自己的交付标准。
- 传了不存在的产物 ID 会被当场拒绝，并告诉你现有的清单。
```

**⑤ 回复用户时的硬要求**（隔离的关键）
```
**产物正文不要搬进你的回复。** 委派完成后，只告诉用户：
交付了哪几样、各自的产物 ID、以及执行器给的一句话摘要。

- **不要**用 `read_artifact` 把产物正文读出来贴进回复
- **不要**自己用 `write_artifact` 重新写一遍执行器已经交付的内容
- `read_artifact` 是**按需**能力：用户明确说「给我看看内容」「改一下某处」、
  或你自己确实要核对内容时才读；只是转交给下一个任务，传 ID 就够
```

#### 4.4.3 `delegate` 的返回口（**6 个可达**）

| # | 触发 | 返回给主 agent 什么 |
|---|------|-------------------|
| 1 | **技能名不存在** | `没有能力「X」。可用：…`（**不建 Task**，直接拒绝） |
| 2 | `completed` + 有产物 | `已交付 art_001。摘要：…` |
| 3 | `completed` + 无产物（正文交付） | `已交付（成果在**执行器**的回复里，**请原样转达给用户，不要改写**——它可能是调用方要解析的协议块）：…` |
| 4 | **`waiting_for_input` → 试答成功 → 自动重跑 → `completed`** | `已交付 …（你补了信息：…）。摘要：…` |
| 5 | `waiting_for_input`（试答后仍缺信息） | `⚠️ 这次没完成，它在请求信息。执行器说：…` + `_outcome_note` |
| 6 | `incomplete` → `failed` | `⚠️ 执行器跑了 N 轮，仍然既没完成任务、也没说明需要什么信息。` + `_outcome_note` + `它最后说：…` + 处置提示 |

> 🔴 **第 4 个出口最容易漏实现。** 试答成功时，平台会**带着补充信息自动重跑一次执行器**
> （`run_task(skill, task + 【补充信息】)`），成功了**直接交付** ——
> 这是 `waiting_for_input` 主回路的**成功半边**。
> 若实现成"试答完就登记待答"，主 agent 的答案永远用不上，白多一轮往返。

> ⚠️ 代码 `agent.py` L240-242 那个 `if outcome.status == "completed"` 分支是**死代码**
> （走到那里时 `outcome` 只可能是 `waiting_for_input` 或 `incomplete`）。重实现时**不要照抄**。

> 🔴 **正文交付有个"取错位置"的陷阱 —— 已实测确认成立。**
>
> `report = _last_ai_text(resp)` 取的是"最后一条**有内容的** AI 消息"。
> 在出口循环里，若第 1 轮写出了协议块 → 判定 `incomplete` → 推回去 →
> **第 2 轮只回了句总结**，那 `report` 就**只剩总结，协议块丢了**，调用方解析不到。
>
> **实测**（把出口循环累积出的消息列表直接喂给 `_last_ai_text`）：
>
> ```
> report = '好的，课件配置已经生成完毕，请查收。'
> 协议块还在吗？ False          ← ❌ 协议块丢失
> ```
>
> **触发条件**：正文交付的 skill（`courseware-config` 这类）**第 1 轮被判 `incomplete`**。
> 主流程（第 1 轮就 `completed`、直接 `break`）**不触发** —— 是**边缘路径**，
> 但**机制上确凿**，而且 `courseware-config` 正是 S7 要验的那条路。
>
> **这个位置踩过一次**：当时的修法是定位"带 `finish` 调用的那条 AI 消息"
> （`_inline_deliverable`）；后来 `finish` 被砍掉，就退回了"取最后一条 AI 消息" ——
> **修法没了，坑还在。**
>
> **修法建议**：`report` 应取"**最后一条产生了交付内容的** AI 消息"，
> 或者干脆把正文交付也走产物库（那就不需要这个特判了）。

#### 4.4.4 `_outcome_note` —— 信息交接（用户原则 ①）

```python
def _outcome_note(outcome) -> str:
    parts = []
    if outcome.progress:
        parts.append(f"【已做到】{outcome.progress}")
    if outcome.missing:
        parts.append("【还缺】\n" + "\n".join(f"- {x}" for x in outcome.missing))
    return ("\n\n" + "\n".join(parts)) if parts else ""
```

**用在所有"没完成"的出口**——主 agent 看到"做到什么程度、还缺什么"，
才能决定是**换个说法重派**还是**向用户说明**。

#### 4.4.5 `_supersede_old` —— 防台账挂过期项

```python
def _supersede_old(runtime, skill_name) -> list[dict]:
    for t in runtime.state.get("tasks") or []:
        if t.get("skill") == skill_name and t.get("stage") in ("waiting_for_input", "failed"):
            out.append({**t, "stage": "superseded"})
```

**只取代 `waiting_for_input` / `failed`**：
`completed` 的是**历史记录**，不能被抹掉（用户可能还要看产物）。

#### 4.5.2 State

```python
class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    tasks: NotRequired[Annotated[list[dict], _merge_tasks]]   # ← 按 id 合并的 reducer
    log: NotRequired[Annotated[list[str], operator.add]]
```

```python
def _merge_tasks(old, new) -> list[dict]:
    merged = {t["id"]: t for t in (old or [])}
    for t in new or []:
        merged[t["id"]] = t
    return list(merged.values())
```

> **为什么必须用 reducer**：模型会**并行**发多个 `delegate` 调用，
> 每个工具都读到同一份旧 state —— 直接覆盖会**只剩最后一个 Task**。

#### 4.5.3 `prepare` —— 注入台账

**注入格式**：

```
【平台提示】你已委派出去的工作（共 N 项）：
- t92d26841  「quiz」  ⚠️ 等用户答复
      已做到：已理解任务，就差难度档位
      还缺：难度
      执行器说：三年级随堂小测，就差一个信息——难度要「基础/提升/挑战」哪一档？
- t8e89a3d4  「lesson-prep」  ✅ 已完成 → art_001

用户这条消息**很可能是对上面「等用户答复」那条的答复**——若确实如此，
带上信息重新 delegate 那一条（**不必重跑已完成、且不受影响的**）。
如果它明显是别的话题，忽略本提示，正常处理。
```

> 🔴 **已知坑：用户换话题时容易死循环。** 第一版把换话题**当成对上一个问题的回答** →
> 清空待答 → **重跑执行器**（产生新草稿）→ 又挂起问同样的问题 → **死循环**。
>
> 所以上面那句逃生话（"如果它明显是别的话题，忽略本提示，正常处理"）
> **不是客套，是必须的** —— 它对应这套设计里**唯一真正需要判断的地方**：
> **不能默认"下一条消息就是答复"**。（修复后 56 秒，比修复前的 64 秒还快。）
>
> **观测方式**：同一轮里反复出现"重派 → 又 `waiting_for_input`"，就是它。

**哪些状态展开细节**：`_NEEDS_DETAIL = ("waiting_for_input", "failed")`
—— 其余（`running` / `completed` / `superseded`）只列一行。

> ⚠️ **目前是全量注入**（用户确认）。台账变长到撑上下文时，可改成只注入活跃的。

> 📌 **多待办 / 待办过期（TTL）尚未处理** —— 现在没有"这条待答挂了多久、要不要作废"的机制。见 §9.5。

#### 4.5.4 `finalize` —— 兜底补问

```python
waiting = [t for t in tasks if t["stage"] == "waiting_for_input"]
if not waiting: return {}
unasked = _which_unasked(state, waiting)     # LLM 判断"问出去了没"
if not unasked: return {"log": ["finalize: N 条待答都已问出 ✅"]}
# 没问出去的 → 平台把执行器的原话补进回复
```

`_which_unasked` 的兜底：调用失败时 `asked=False` → **当作没问出去 → 补问**。

> 📌 **这条实测无法从日志验证 —— 两个分支走的是不同通道。**
>
> `node_finalize` 里：
> - 「都已问出」→ `return {"log": [...]}` → **只进 `state["log"]`、只显示在控制台，不落文件**
> - 「没被问出 → 平台补上」→ `trace.note(...)` → **这个才写日志文件**
>
> 所以 `../logs/` 里查不到「都已问出」是**必然的**，**不构成反证**。
>
> ⚠️ 但日志里「没被问出 → 平台补上」**出现过 9 次** ——
> 说明**兜底在其他运行里确实触发过**。
> 所以「兜底没用上」**不能当作一般结论**，只能说明**那一次**主 agent 自己问全了。

## 五、关键机制详解

### 5.1 任务完成判定（三态）

**核心**：问「**任务完成了没**」，不是「产物生成了没」。

```
run_task 内部循环（最多 3 轮）
  ① 执行器干活
  ② 判定：completed / waiting_for_input / incomplete
       completed          → 出口
       waiting_for_input  → 出口
       incomplete         → 推回去继续（带 progress/missing）
```

**为什么"产物库非空"不够**（评审人 C2）：

| 反例 | 产物库 | 实际 |
|------|--------|------|
| 生成了文件但缺章节 | 非空 | **未完成** |
| 纯分析任务没有文件 | 空 | **可能已完成** |

**三条原则在这里交汇**：

1. 问「**任务完成了没**」，不是「**产物生成了没**」—— 产物只是证据之一
2. **产物 ID 必须真实存在**（`art_999` 编不出来）—— 见 §4.3.6
3. **模型自报的清单不参与判定** —— 见 §10.3

> 🔴 **第 3 条踩过一次**：让模型**自报交付物清单**，拿它去精确匹配 skill 声明的名字 ——
> 模型给名字加了后缀 → 匹配不上 → **误判"教案缺失" → `failed`**，
> 而产物库里明明有 `art_002`。
> **修法：`claimed` 完全不参与判定，只写进日志供对照诊断。**

### 5.2 出口限制（不许随便停）

> **执行器没干完活是它的问题，不该转嫁给用户。**

```
incomplete → 推回去继续（最多 3 轮）→ 推满仍不行 → failed，交给主 agent
```

**实测（注意：这个行为变过，两份文档各记了一半）** ——
一个"干不成、又不许问"的死局任务：

| 时期 | 表现 | 记录在 |
|------|------|--------|
| **早先**（14:14 / 15:00 / 15:04 的运行） | **推满 3 轮** → `incomplete`，没去烦用户 | `../scenarios.md` S18 |
| **后来**（15:09 之后的运行） | **1–2 轮就说明需要什么** → 走请求信息路径 | 本节 |

行为变化的原因是 `_PLATFORM_RULE` 让执行器"**早说早处理**"（见 §4.3.7）——
它不再硬扛到轮次上限，而是早点把缺什么说清楚。**这是好事**（少烧 token、少一轮往返）。

> ⚠️ **但它的代价要看清**：§5.2 的立意是「**执行器没干完不该转嫁给用户**」——
> 而死局任务现在**会经主 agent 触达用户**。也就是说，
> **这个立意在新行为下并未完全达成**，是"早说早处理"换来的。
> 这属于**已知取舍**，不是 bug；但别以为死局一定不会打扰用户。

### 5.3 信息交接链（用户原则 ①）

**七个交接点** —— 前六个是 `progress` / `missing`，第七个是**决策本身**：

| 交接点 | 内容 | 状态 |
|--------|------|------|
| 判定 ← | `instructions` + `given` + 产出 + 产物数量 | ✅ |
| 判定 → 执行器（推回去） | `progress` + `missing` | ✅ |
| 判定 → 主 agent（`failed`） | `_outcome_note()` | ✅ |
| 判定 → 主 agent（`waiting_for_input`） | 同上 | ✅ |
| 执行器 → 主 agent **试答**（`_ask_main`） | 同上 | ✅ |
| 平台台账 → 主 agent（`prepare`） | 同上 | ✅ |
| **决策是否结构化**（能不能被代码用） | 三处判定全用 `with_structured_output`，无"用工具传决策" | ✅ |

**这条链上实测踩过三次**，全是同一类错 ——「**信息在内部产出了，但需要它的地方看不到**」：

| # | 缺什么 | 后果 |
|---|--------|------|
| 1 | 判定提示词没带 `instructions` | "按任务要求判断"是空话 |
| 2 | 判定提示词没带 `given` | 明明给了"第1课时"，判定说"没询问用户课时信息" → 误判成 `waiting_for_input` |
| 3 | `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道缺什么 → `_outcome_note()` 就是为它加的 |

> **通用检查动作**：每加一个机制，顺着信息流走一遍——
> **产出它的环节 → 需要它的环节，中间断了吗？**

### 5.4 Task 生命周期（5 态）

```
running ──┬─→ completed          已完成
          ├─→ waiting_for_input  等用户答复
          ├─→ failed             推满 3 轮仍 incomplete
          └─→ superseded         同技能被重新委派（不用管了）
```

**与 `_Judgement.status` 的关系**：前三个**同名**，唯一映射 `incomplete → failed`。

#### 🔴 四条语义区分（实现时的防错清单）

这四个"不等于"是 D1 的动机所在，写代码时最容易混：

| 不要混 | 说明 |
|--------|------|
| `waiting_for_input` **≠** Graph 运行失败 | 前者是**正常状态** —— 图跑得好好的 |
| `completed` **≠** 某次模型调用正常结束 | 模型正常返回 ≠ 任务完成 |
| `failed` **≠** 模型返回了错误字符串 | 它的定义是"推满 3 轮仍**既没完成、也没请求信息**" |
| **某个 Sub Agent 执行完成 ≠ Task 已经完成** | 执行器"跑完了"和"干完了"是两回事 |

**暂未实现的三个**（记清了为什么、什么时候该做）：

| 状态 | 为什么现在不做 | 什么时候该做 |
|------|--------------|------------|
| `pending` | 建 Task 就立刻派发，没有"创建了还没跑"的窗口 | 做「计划-执行分离」时 |
| `waiting_for_dependency` | `delegate` 是**同步**的，依赖在主 agent 循环里天然解决 | 做「异步委派」时 |
| `cancelled` | 要给主 agent 新工具，场景**尚未实测到** | 真遇到时 |

### 5.5 上下文隔离

**落点**：产物正文只在产物库，主 agent 只拿 ID + 摘要。

**实测数据**：

| 场景 | 主 agent 上下文 | 产物库正文 | 比 |
|------|---------------|-----------|-----|
| 3 技能（轻量内容） | ~1500 字 | ~8000 字 | 5-13 倍 |
| **48k 字 HTML 课件** | **~2600 字** | 48,873 字 | **~19 倍** |

**隔离靠三条纪律**：
1. 执行器只回 `(产物ID, 报告)`
2. `delegate` 只把 ID + 摘要给主 agent
3. **主 agent 不把正文搬进回复**（系统提示的"硬要求"）

### 8.2 建议的落地顺序

| 步 | 做什么 | 对应 |

| **1** | **恢复主 agent 的"自己答"能力** —— 它现在缺（"你好"返回"（无产出）"） | 主 agent 改造成完整 agent |

| **5** | **产物存储换真表** —— `ARTIFACTS` 是内存 dict | §8.3 |
| **6** | **checkpointer 换持久化** —— `MemorySaver` → Sqlite/Postgres | S16 |

### 8.3 必须做但原型没做的

| # | 事项 | 为什么 |
|---|------|--------|
| 1 | **产物库换真存储** | 原型是内存 dict，重启即丢 |
| 2 | **checkpointer 换持久化** | `MemorySaver` 重启即丢（S16）—— 真实严重度见下方 ⚠️ |
| 3 | **长期记忆**（`store` / `memory_context`） | 跨会话参数复用（S15） |
| 4 | **把"哪些参数必答"写进每个 skill 的 `instructions`** | 平台不猜（B2 的分工） |
| 5 | **前端 `pendingSkill` 要持久化** | 现在只存在内存，**刷新页面即丢**。新设计把"待答"变成 `Task.stage = waiting_for_input`，前端必须能承接这个状态，否则用户会看到"问过的问题又没人接" |
| 6 | **若保留 HITL 提问，必须做成图节点而非工具** | 见 §8.4 代价 1（悬空 `tool_call` → 400） |

> **挡不住进程重启 / 多 worker / 部署**。`MemorySaver` 是内存态、随 graph 实例走 ——
> 这是 **P2 在现网的真实来源之一**。**上线前必须解决，不能排后面。**

### 8.4 不需要改的

- **不需要引入参数声明**（D1）
- **不需要引入交付物声明 / 结果协议**（D1）
- **不需要把 Task 独立成业务实体**（F2，除非前端要任务列表）
- **不需要做断点 / 草稿外置**（接受重跑，见 §2.1.1）
- **不需要恢复 plan 节点**（职责已被主 agent 循环吸收）
- **不需要重新绑定 `interrupt()`**（F3）—— **理由见下**，这条最容易被误读成"提问机制整个不要了"

#### 🔴 为什么不走 `interrupt()` —— 完整成本清单

`sx-agent` 里这条路的代码是**半开的**：挂起（`tools_core.py` 的 `answer = interrupt(payload)`）、
传播（`graph.py` 的 `except GraphInterrupt: raise`）、恢复（`stream.py` 的
`if pending: return Command(resume=...)`）—— **三段全都写好了，只差工具没绑给模型**。

所以实施者最自然的动作就是"**把它接回去**"。接回去要付这些代价：

| # | 代价 | 说明 |
|---|------|------|
| 1 | **悬空 `tool_call` → 上游 API 400** | `interrupt()` 在**工具**里调用时，带 `tool_call` 的 AIMessage 已产生、`ToolMessage` 还没产生 → 挂起时**悬空** → 后续工具循环把它重新送进 LLM 输入 → `insufficient tool messages following tool_calls`。**项目已踩过**，也是当初关掉 HITL 的原因之一 |
| 2 | **传了 `config` 会静默吞掉挂起** | 实验 01–05 的决定性结论：唯一决定成败的变量是「dispatch 包装是否给 subagent 传 `config`」。**传了就静默吞掉** —— 裸 `checkpointer=True` 会 RuntimeError，但**套壳之后是静默的** |
| 3 | **包装层必须逐层显式透传** | `interrupt()` 是**返回值**、不是"异常穿透"。每层包装都要显式处理，漏一层就没了 |
| 4 | **节点会从头重跑 → 副作用必须幂等** | 子图作为函数调用时，父节点与子节点**都会从头重跑** |
| 5 | **五条铁律** | 裸 `try/except` 会吞异常 · resume 值**按索引匹配**（多中断下极易错位） · 不可传复杂对象 · 之前节点的副作用必须幂等 · **禁止 `while True` + `interrupt` 校验循环**（指数级重跑） |
| 6 | **子图持久化三模式的硬限制** | 见 §8.5 |

**不是"interrupt 不好"，是它要解决的问题我们已经用别的方式解决了**：

- **"提问走向不确定"** → 执行器**从不直接问用户**（§2.1），没有"答给谁"的歧义
- **"挂起恢复"** → `Task.stage` 由**代码**写，恢复是**纯代码查表**，LLM 不参与

> 📌 **实测数据（被放弃的收益，别误读成"interrupt 有问题"）**：
> `interrupt` 模式**跑得通**，而且主上下文更小 ——
> **143 字 vs message 模式 333 字**（问题在 interrupt 载荷里，不进消息历史），
> 耗时基本持平（1m20s vs 1m22s）。它只是在这个架构里**没必要**。

> 🔑 **一个可直接搬的结构性改进**：如果将来确实需要 HITL 提问，
> **把提问做成「图节点」而不是「工具」** —— 节点里调 `interrupt()` 不产生 `tool_call`，
> 于是**压根没有"未配对的 ToolMessage"**，代价 1 从根上消失。

### 8.5 旧路径的机制结论（备查）

下面两条在推演中自述"**仍然有效**" —— 它们解释了 **P2 为什么是「间歇性」的**。

**① 子图持久化的三种模式**

| 模式 | 语义 | 限制 |
|------|------|------|
| `checkpointer=None`（默认） | 每次调用一个全新状态 | — |
| `checkpointer=True`（**per-thread**） | 同一 thread 内**累积** | ⚠️ **同一个 subgraph 不能被重复调用** → 一个会话里一个 skill 只能有**一个活跃任务实例**；不同 subgraph 的同名节点会**命名空间冲突** |
| `checkpointer=False` | 无状态 | — |

**② 命名空间按「调用顺序」分配**

> *"reordering your calls can mix up which subgraph loads which state"*

**这就是 P2「间歇性」的唯一解释** —— 调用顺序一变，就加载到别的 / 空的 state。
它同时也是评估「subagent 该做成节点、还是节点内调用」的依据。

`sx-agent` 现状用的正是 `checkpointer=True`（per-thread），
上面那两个硬限制**直接适用** —— 换持久化 checkpointer 时要一并处理（§8.3 第 2 条）。

### 8.6 sx-agent 现状核查（改之前先看这些）

| 项 | 现状 | 影响 |
|---|---|---|
| **HITL 代码** | 挂起 / 传播 / 恢复**三段完好**，只差工具没绑定 | 落地成本评估的关键 —— 是"**能力已存在、只差绑定**"，不是"要重写一套 HITL" |
| **提问提示词** | **两处**在指示模型把问题写进回复正文：`agent_builder.py` 的平台约定、`engine.py` 的参数占位符 | **这正是 P3 的直接来源** |
| **关闭 HITL 的三条理由** | ① 「单 agent 架构下没作用」**不成立** —— 正文提问没有挂起点，正是 P1/P2/P3 的总根源；② 「同一问题被问两遍」成立，但成因是**双通道同时开着**，解法是只留一个；③ 「多个挂起中断无法用单一回答恢复」**已被证伪** —— `Command(resume={interrupt_id: value})` 就是官方为此设计的 | ⚠️ 理由 ③ 是写在项目自己文档里的**错误结论**，不纠正会继续据此否掉批量提问类设计 |
| **前端 `pendingSkill`** | 只存在内存 | 刷新即丢，与"Task 跨轮存活"配套不上 |
| **现状配置** | 父图 memory checkpointer · 子图 `checkpointer=True`（per-thread）· interrupt 调了但不挂起 | 见 §8.5 |

> ⚠️ **一处内部矛盾，落地前必须定**：`sx-agent` 自己的文档里，
> §8.4 的解法写的是"**留工具、删正文指令**"，而 §8.6 又明确"**不要删该约定**"。
> 两者**相反**，而本方案对此原先沉默 —— 实施者二选一都可能改错。
>
> **本方案的立场**：正文提问的提示词是 P3 的成因，**应当处理**；
> 但**不要在执行器里重新绑定 `interrupt()` 工具**（理由见 §8.4）。
> 具体改哪一处、怎么改，落地时单独定。

**落地前的自查清单**（对应 §6.5 的必查项）：

1. 同一会话的 `thread_id` 是否**跨轮稳定**？（不稳定 → Task / 台账 / supersede 全失效，**且不报错**）
2. subagent 是 `add_node` 还是**节点内调用**？（决定命名空间行为，见 §8.5）
3. 有没有**裸 `try/except` 包住 `interrupt`**？（会吞掉挂起信号）
4. memory checkpointer 的实例**活多久**？（多 worker 下是否共享）
5. 有没有**并行调用同一个 per-thread subagent**？（per-thread 的硬限制）

### 9.4 换模型必须重新验证（硬约束）

**执行器这个模式对模型能力有要求。** 实测（同一份代码、同一个任务）：

| 模型 | 备课（3300–3800 字） | HTML 课件 |
|------|-------------------|----------|

> 🔴 **这是最危险的一类失败**：症状是"**系统看起来成功了**"，团队会去怀疑架构，
> 而不是模型。本方案全案依赖 `safe_structured`（§4.2），选错模型就会静默退化。
> **上线选型 / 换端点 / 升级模型后，必须重跑一遍端到端验证。**

## 十、设计原则（贯穿全案）

### 10.1 四条**设计**原则

| # | 原则 | 落地 |
|---|------|------|
| **①** | **理解要柔性，状态要硬** | 平台不抽参数（原话原样传）；但状态由代码写、分支穷举 |
| **②** | **能靠既有事实判定的，不要发明协议** | 删掉了 `finish` / `status` / `deliverables` / `criteria` |
| **③** | **能靠代码算的，不要交给 LLM；能靠 schema 约束的，不要靠提示词** | 三处判定全用 `with_structured_output`（§4.2）；实测模型会漏字段、会改写参数名 |
| **④** | **平台少约束 skill 作者** | 形式能跑即可，效果由作者迭代。任何**依赖作者配合**的机制都是脆的 —— 作者一句自然语言就能覆盖平台约定 |

### 10.2 处事原则（8 条 —— 本次推演的工作方式）

> 这几条**不是产品设计**，是"这次怎么把设计做出来"的规矩。
> 它们同样适用于**下一次架构迭代**。

| # | 原则 | 一句话 |
|---|------|-------|
| ① | **批判性审视，不要照办** | 先看业界怎么做，再决定要不要自造 |
| ② | **讨论先行** | 要写代码前，先说清"验什么 / 怎么验 / 预期结论" |
| ③ | **结论必须实测，优先真实模型** | 想当然的结论几乎全被推翻（见 §10.4） |
| ④ | **分支必须闭合** | 分类要覆盖所有情况、互斥、每个都被妥善处理。**靠约定排除的组合，说明该用枚举** |
| ⑤ | **信息交接要说细节 + 决策要结构化** | 产出它的环节 → 需要它的环节，中间不能断（§5.3） |
| ⑥ | **平台少约束作者** | 同 §10.1 ④ |
| ⑦ | **保留讨论历史，不删** | 过期结论标"已被 §X 取代"+ 一句为什么被推翻。**未标记的过期内容比没有更糟** |
| ⑧ | **场景沉淀成回归集** | 每次架构迭代回来跑，防"修好一个、弄坏一个"（实测：去掉 `load_skill` 修好 S12，立刻暴露 S13、S14） |

### 10.3 一条贯穿的观察：「**模型的话是线索，不是事实**」

这个坑**踩了三次**，每次都是同一件事 —— **拿模型说的话当事实用**：

| # | 场景 | 后果 | 修法 |
|---|------|------|------|
| 1 | 执行器在正文写"教案已完成，请查收" → 判 `completed` | 主 agent 报"已交付"，**用户什么也没拿到** | 判定规则 2：不能凭声称完成判定 |
| 2 | 让模型**自报交付物清单**，拿它去精确匹配 skill 声明的名字 | 模型给名字加了后缀 → 匹配不上 → **误判"教案缺失" → failed**，而产物库里明明有 `art_002` | `claimed` **完全不参与判定**，只写进日志供对照诊断 |
| 3 | 想靠提示词让模型**按格式输出参数名** | 模型把「学科」改写成「科目」 | 用 `with_structured_output` / schema 约束（§10.1 ③） |

> **推论**：凡是"模型的产出"要参与逻辑判断的地方，
> **要么用代码验证它**（产物 ID 必须在产物库里查得到），**要么别用它**。
>
> ⚠️ 这个坑会复发的地方：`sx-agent` 有 `app/skills/validating/` —— 加"交付物核对 / 参数核对"时最容易重犯。

### 10.4 附：被实测推翻的"想当然"

| 想当然 | 实测 |
|--------|------|
| "criteria 是确定性检查" | 它本质也是 LLM 判断；**自己写的测试 9/9 全过，仍无增量价值**。砍它的理由是"**没必要**"，不是"分数低"（早先记的"4/6 更差"已不可复现 —— 见 §7.1） |
| "有产物就算完成" | 有产物但内容是残次品 → **误判成完成** |
| "出口限制救不了『干了一半就停』" | **救得了** —— 改成问"任务完成了没"就行 |
| "判定带上 `instructions` 就够了" | 还要带 `given`，否则误判 |
| "`failed` 分支不用带 `progress`/`missing`" | 主 agent 只知道"没做成"，不知道缺什么 |
| "两个布尔值表达三态没问题" | 4 种组合只有 3 种合法 → **该用枚举** |
| "**隐式 else 没问题**" | 试答后重跑只判两种 → `incomplete` 被当成"在请求信息" → **去问用户，P3 复发** |
| "提示词写'符合要求'就行" | 太笼统导致**吹毛求疵**（推 3 轮 4m29s vs 1 轮 1m5s） |
| "模型自报的交付清单可以用来核对" | **不可信**（§10.3 第 2 条） |
| "豆包和 DeepSeek 等价可用" | 豆包在 `response_format` 上**静默失效**，HTML 3/3 空响应（§9.4） |

### 10.5 设计依据 —— 不是我们自己推的

`Skill` / `Task` / `Sub Agent` **三者正交**、**执行器不问用户**、**skill 与 subagent 解耦** ——
这几条**不是本次推演的独创**，是从参考实现里读出来的：

| 来源 | 借鉴了什么 |
|------|-----------|
| **DeepAgents**（`../ref/deepagents`） | subagent 的 `task` 工具 · skills 渐进式加载 · **文件系统作为共享记忆** · **async subagents（后台非阻塞，未拉取）** |
| **Claude Code Skills** | `SKILL.md` 渐进式披露 · **subagent 上下文隔离（子 agent 不能反问用户）** |

**决定性发现**（读 `ref/deepagents` 得到的）：那里的子 agent 是
**ephemeral / stateless / 一次报告 = 纯函数** ——
所以 **P1/P2/P3 在它那里压根不会发生**。
skill 里写"必须先委派给 researcher" → **拆分由 skill 决定、交接靠文件系统**。

> 这也是为什么"**执行器从不直接问用户**"是一条**硬边界**，而不是措辞选择。
>
> 同时说明：这套设计的**新颖部分很少** —— 主要是把业界已验证的结构
> 搬到"需要跨轮交互"的场景上，并补上 `Task` 这一层状态载体。

## 十一、任务完成判定机制

> 2026-10-29 由 `completion-mechanism.md` 并入。
> ⚠️ **原文里那些"逐字提示词"副本已删** —— 真值在代码（下面标了常量名）。
> 删它们不是偷懒：并入前它们**已经和代码脱节了**（`given` 改名 `briefing`、
> 判定预算 800→4000、判定 prompt 改成按需记录），而这份文档的读者恰恰是来调提示词的。
> 副本必然漂移 —— 要改提示词，直接改 `proto/executor.py` 里的常量。原文件见 git 历史。

### 11.1 要回答的三个问题

执行器干完活之后，平台必须回答：

1. **这次到底完成了没有？** —— 不能只看"产物库空不空"（有文件但缺章节 ≠ 完成；
   纯分析任务没有文件 ≠ 未完成）
2. **没完成的话，是在请求信息，还是就是没做完？** —— 两者后续处理完全不同
3. **没完成的情况下，下一轮怎么接着推进？** —— 只说"没完成"，推回去它也不知道干什么

### 11.2 三态（用户拟的）

| 状态 | 含义 | 后续 |
|------|------|------|
| `completed` | 任务已完成，且满足必要的交付条件 | 交付 |
| `waiting_for_input` | 任务尚未完成，且**明确请求**了继续所必需的信息 | 主 agent 先试答 → 答不上问用户 |
| `incomplete` | 任务尚未完成，但**不属于**请求信息的情况 | 推回去继续；推满 → 交给主 agent |

**闭合性**：完成 / 未完成且在请求 / 未完成且不在请求 —— **覆盖所有可能**，
且 `Literal` 类型保证模型输出不了第四个值。流程与出口限制见 `architecture-diagram.md` §二。

### 11.3 判定的输入（**缺一不可**）

| 喂给判定的 | 不带会怎样（都实测踩过） |
|---|---|
| 技能的 `instructions` | "按任务要求判断"变成空话，判定只能凭常识猜 |
| 本次的**交接书**（`briefing`） | 明明给过"第1课时"，判定却说"未询问用户课时信息" → 误判成 `waiting_for_input` |
| **实际执行结果** | 有产物时给**产物正文**、无产物时给**全部轮次**的产出（只给最后一条会丢掉前面交付的东西） |
| **产物数量** | 不数产物，判定会把"写了文件"和"只在正文里说了"混为一谈 |

逐字见 `proto/executor.py` 的 `_judge()` / `_JUDGE_RULES` / `_judge_material()`。

> 🔴 **通用检查动作**：每加一个机制，顺着信息流走一遍 ——
> **产出它的环节 → 需要它的环节，中间断了吗？**（这个坑踩过三次）

### 11.4 实测：五种判定提示词对比

`experiments/debug_judge_variants.py`，6 个用例（完整产出 / 缺章节 / 在问用户 /
有产物但残次品 / 纯分析无产物但完成 / 什么都没干）：

| 变体 | 全对 |
|------|------|
| A 只给产出 | 3/6 |
| B 产出 + `instructions` | 5/6 |
| C 产出 + `completion_criteria` | **4/6** |
| E 产出 + instructions + 反省式 | 6/6 |
| **F 用户拟的模板（三态 + 明确规则）** | **6/6** ✅ 生产用这个 |

**结论**：`completion_criteria`（把要求拆成字段声明）**反而最差** —— 要求本来就在
`instructions` 里，再抄一遍是重复，还会把"必须包含 X"硬套到不该套的任务上。
**"带 instructions + 明确规则"就够了。**

> ⚠️ 单次采样的分数会漂（重跑过一次，A/B/C/E 全变成 5/6）——**别拿单个数字当论据**。

### 11.5 踩过的坑

| 坑 | 后果 | 修法 |
|---|---|---|
| 判定提示词没带 `instructions` | "按任务要求判断"是空话 | 带上 |
| 判定提示词没带交接书 | 把"已经给过的信息"当成"没问" → 误判成在请求信息 | 带上 |
| `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道该重派还是该问 | 带上（`_outcome_note`） |
| 用两个布尔表达三态 | 4 种组合只有 3 种合法，"矛盾组合"只能靠约定排除 | **改用枚举** |
| 隐式 else | 试答后重跑有三种结果只判了两种 → `incomplete` 被当成"在请求信息"，跑去问用户 | 显式穷举 |
| 措辞太笼统（"符合上面的要求吗"） | 模型吹毛求疵，推 3 轮跑了 4m29s | 规则**列举具体失败形态**（占位/待补充/半成品），同任务降到 1 轮 1m5s |

### 11.6 可调优点（**提示词是效果的关键**）
