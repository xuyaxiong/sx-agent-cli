### 0.1 最终设计：Skill / Task / Sub Agent 三者正交

| 概念 | 是什么 | 载体 |
|------|--------|------|
| **Skill** | 专业能力（静态） | 只有 `description` + `instructions` |
| **Task** | 一次具体业务工作（动态） | `state["tasks"]` 里一条 —— **11 个字段**，见 `architecture-diagram.md` §5.1，**跨轮存活** |
| **Sub Agent** | **可选**执行者（一次性） | 通用 `run_task()`，**不绑任何 skill** |

### 0.2 四条设计原则

1. **理解要柔性，状态机要硬。**
   平台**不抽取参数**（不做 schema 抽取、不算并集）；但「谁在问、答给谁、怎么恢复」
   **必须确定性**，代码判定，不问 LLM。
   ⚠️ 原来这句写的是"用户原话原样带给执行器"—— **那话只对一半**：
   成立的是**答复投递**那条路（`_feed_waiting` 把原话投给待答任务），
   **首次派发不是**（执行器拿到的是主 agent 的转述，见 §9.2 与原则 ⑤）。

2. **能靠既有事实判定的，不要发明协议。**
   执行器不调 `finish`、不报交付物清单、不声称 `status`。
   **三态由平台按结构算**（调了 `ask_user` / 交了产物 / 都没有，见 §5.1）——
   ⚠️ 早期写的"**完成 = 产物库非空**"**已被推翻**（反例：有文件但缺章节 / 纯分析任务没文件），
   留在这里只为说明**原则没变、口径变了**。
   📌 **2026-11-05 又变了一次**：三态中间那一版是**判定**（一次 LLM 调用）回答"任务完成了没"，
   现在判定退休 —— 平台**只说"交了东西"这个事实**，"够不够"由**主 agent** 判（见 §11.2）。

3. **能靠代码算的，不要交给 LLM；能靠 schema 约束的，不要靠提示词。**
   （实测：模型会漏字段、会改写参数名）

4. **平台少约束 skill 作者。形式能跑即可，效果由作者迭代。**
   任何**依赖作者配合**的机制都是脆的——作者一句自然语言就能覆盖平台约定。

5. 🔴 **交接是硬机制的活；软判断只负责"不得不判"的那一点。**
   系统里只有两类东西：**代码硬逻辑决策** 与 **LLM 软判断**。
   而软判断的效果**完全取决于喂给它的上下文** —— 所以"合理、充分地把决策上下文组织出来"
   是这套系统能不能跑好的**根本**，而这件事**必须由代码做**：
   委托给谁、带哪些信息、以什么结构带过去，一律**硬拼**。
   **不能靠 LLM 转述** —— 转述就有损失（用户 2026-11-02：
   *"工作委托给 subagent，委托包含哪些信息，要精挑细选深思熟虑，是否是硬机制，
   而不是依靠 llm 转述（转述就有损失）"*）。
   反过来，**软判断那部分要收紧到最紧**：能不问就不问、能枚举就枚举、能带全上下文就带全。

   > ⚠️ **这条和原则 ① 是同一件事的两面**：① 说"**用户**的原话不要被平台抽取加工"，
   > ⑤ 说"**平台**该给的东西不要交给模型转述"。两边合起来就是
   > **"凡是能由代码确定地搬过去的信息，都不许过 LLM 的手"**。
   > 现在还没完全做到 —— 见 §9.2 的「**首次派发时执行器看不到用户原话**」。

### 0.3 三个原始问题的最终解法

| 原问题 | 最终解法 |
|--------|---------|
| **P1** 重复问参数 | 执行器拿到**同一份交接书**（历次答复**累积**在里面，见 `architecture-design.md` §3.2.2）→ 不会问已知的；各自缺的**逐个问** |
| **P2** 没干完就重开 | **Task 是状态载体**，执行器一次性、不跨轮 → 结构上不可能"重开"；重入走**同一份交接书**（`render_briefing` 是唯一入口） |
| **P3** 正文提问走向不定 | **`Task.stage` 是身份** + **平台无条件透传 / 投递**（2026-10-29 改）→ "谁在问、答给谁"确定 |

`finish` 工具 · `ExecResult.status` 枚举 · `deliverables` 清单 · `Deliverable.required` ·
`_detect_body_question`（LLM 检测）· `interrupt()` + `Command(resume)` · 草稿/断点外置 ·
`Skill.params` 声明 · 动态 schema 抽参数 · `declared_params()` 并集计算

### 0.5 关键发现（推演过程中最有价值的几条）

1. **"提问"曾经是输出，不是控制流事件** —— 没有挂起点，"恢复"只能靠历史文本假装（§3.2、§6.1）
2. **`interrupt()` 是「返回值」不是「异常穿透」**，每一层包装都得显式透传（§6.7）
3. **把提问做成「图节点」而非「工具」**，结构性避开悬空 tool_call → API 400（§10.7）
4. **DeepAgents 的子 agent 是纯函数**（ephemeral / stateless / 一次报告），
   所以 P1/P2/P3 在它那里**不存在**——不是解决了，是压根不会发生（§10.12）
5. **模型的话是线索，不是事实**：正文说"完成"不算、执行器报 done 不算、
   自报 delivered 不算——**一律看证据**（§10.9.1、§10.11.1）

| # | 不做什么 | 谁决定的 | 为什么 |
|---|---------|---------|--------|
| **X1** | 不恢复 `plan` 节点 | 用户 | 职责已被循环吸收（选能力→工具选择；建 Task→delegate 内部） |
| **X2** | 不引入参数声明 / 交付物声明 / 结果协议 | 用户 + 实测 | 约束作者；且实测模型会改写参数名、算错并集 |

| **X4** | 不写草稿 / 断点外置 | 用户 | 接受重跑，换掉"草稿 vs 成品"一整类 bug |
| **X5** | 不把"产物重复"当 bug 修 | 用户 | 那是 LLM 的抉择，收敛应在产物库层面。**「交付清单里没有『最终版』」也归这里** —— 见下面的注 |
| **X6** | 台账**全量注入**（暂不做"只注入活跃的"） | 用户 | 先简单；变长再切换（备选记在 `node_prepare` docstring） |
| **X7** | **不把"主 agent 整轮失败"的兜底放进平台**（跑批入口断了就记整轮失败） | 用户 2026-11-05 | 跑批是**测试用途、不是用户入口**：它挂了 = 那个 case 判红，而**改成平台接住它照样红**（活没干完，断言过不了）—— 结论不变，只是换个说法红。真实用户走的 chat 入口**已经接住了**（`proto/__main__.turn()` 按轮捕获 → "这一轮没跑成，把刚才那句再说一遍就行"）。让两个入口"行为一致"是**给测试入口造一个它不需要的机制**（用户原话：*"跑批断了就断了呗 真有啥影响 chat入口能兜住不就行吗？"*） |

> 🔴 **「交付清单里没有『最终版』」也归 X5**（2026-11-05 用户认）——
> 执行器的产物是**边干边记账**的（`run_task` 的 `created`），一轮跑完把整份清单原样交出去，
> **没有"哪份是成品"这个概念**。两个真会发生的形状：
>
> - **形状一：一轮里写了两份**（模型写了教案、觉得不行又在同一轮重写）→ 回执列两份、
>   Task 记两份，主 agent 和用户**分不出哪份是它最后认可的那版**；
> - **形状二：写了一份又提问**（调 `ask_user`）→ 平台按"**申报优先**"记成"在要信息"，
>   那份半成品留在清单里；用户答完重跑写出完整版 → 平台**覆盖**成新的 →
>   **旧的那份没人指向了**，但还在产物库里、`list_artifacts` 照样列出来。
>
> （审计里"被推回去重写 3 份教案"那个极端例子 —— 那是**判定时代**才有的：判定说"不够"
> → 推回去 → 再写一份。现在"写了产物就算交付、直接收工"，**那条路已经不可达**。）
>
> **为什么不修**（和 A3 那次**不是一回事**，别拿同一个标准看）：A3 是**平台说了假话** ——
> 有正确答案（"这是平台故障"），它说成了"执行器没干成"→ 该修。这里是**平台不知道答案**：
> 模型写了教案又写学案时，**两份都是成品**；写了草稿又重写时，**只有后一份是**。
> 这两种情况在平台眼里**长得一模一样**（都是"一轮里写了两份"），要分开只能**读内容判断**
> —— 那正是**判定**干的活，而判定就是死在这上面（读正文猜"够不够"：礼貌收尾被当成要信息、
> 截断后给出错误结论）。**要平台标"最终版"，等于要它做质量判断。**
>
> 📌 真要做，唯一可靠的路是**让模型自己声明**（`write_artifact` 加一个"这份替代 art_001"）
> —— 那是**新机制**、且靠模型自觉（它经常不会填）。**没看到真被咬到之前不造。**

> 🔴 **N2 的边界（2026-11-05）**：流式重试**只在"还没走完第一步"时发生** ——
> 从头重跑 = `state` 干净、**副作用不干净**：实测重试会把这一轮**已经做过的工具调用再做一遍**
> （`delegate` 重跑 = 执行器再跑 60–120 秒 ＋ 再写一份产物，而模型在重试的 state 里
> **看不到自己刚派过**，很可能再派一次）。**数据**：216 个历史 run 里真·瞬时的抖动只有 3 个，
> 其中 **2 个落在"已经动过手之后"** —— 正是现在不再重试的位置。落在那里就**如实失败**，
> 由调用方兜（执行器 → fault 出口；主 agent → 入口）。
>
> 📌 **记一个没做的更彻底做法**（用户 2026-11-05 定：*"先按做法二，做法三以后再试，现在这种方式够用"*）：
> **从最后一个走完的 super-step 接着跑**，而不是从头来 —— 已跑过的 `delegate` /
> `write_artifact` **不会再跑**（它们的 `ToolMessage` 和 `tasks` 更新都在那个 `state` 里），
> 重放窗口缩到"失败的那一个 super-step"，用户完全无感。
> **没做的原因**：① 要先用 spike 验"拿一个 `create_agent` 子图的**中间 state** 再 `stream` 一次"
> 行为是否真如预期（step 计数 / pending writes / 消息会不会重）；② 它和 §五 **X4**
> （不写草稿／断点外置）是**同一族**，得先把边界说清 —— 这是**单轮、内存内**的续跑。
> 细节与实测数据在 `proto/trace.py` 的 `_stream_with_retry` docstring。

> **回归验证**：每条功能/质量需求的实测状态，见 `scenarios.md` 的场景编号。

### 0.65 已定**待做**的（方向定了，还没动手 —— 免得反复讨论）

>
> 📌 **两个边界（用户 2026-11-05 定）**：
> - **弹框先不允许同时开多个**（一次只开一个）—— 简单为先（同时开多个是更强的版本：用户想先答哪个答哪个、也不会像串行那样逼他排队，留作以后）
> - **被否的备选（记下来免得重新讨论）**：主输入框的话**也**投给所有待答任务（＝保留今天的广播、两套并存）。用户定：**先按 (a)** —— 主框只给主 agent，**通道决定归属，不猜**

**分三步（前两步在平台侧，跟 UI 无关）**：

1. ✅ **把"问题"存下来**（2026-11-05 做完）—— `ask_user` 那句原话原来**只活在当轮**（`ExecOutcome.asked`），任务进入"待答"之后就丢了 ✗，跨轮只剩 `report`（执行器最后说的那段话）✗。后果两条：透传给用户的是**那段散文**（实测："好的，我先来进行第一步的分析，然后进入第二步——生成前确认。## 第一个问题 这节课你希望侧重哪种上法？…"）而不是那句干净的原话；**没有对象就做不了"框"**。现在 `Task.asked` 存着它，透传从**对象**渲染（`【{skill}】问：…`）。⚠️ 这跟 A3（故障没落进 `Task` → 台账只能说假话）**是同一个病、隔一个字段**。
2. ✅ **定向投递**（2026-11-05 做完）—— `_feed_waiting` 从"广播给所有待答"改成"**只投给 `answer_to` 指的那一条**；**没有标识就一条都不投**（那是主 agent 的输入）"。顺带把"N 个待答 = N 倍等待"也解决了（只跑一个）。
3. **"框"** —— ✅ **2026-11-05 做完**：CLI 里它就是一个**带标识的提示符**（用户原话：*"弹框是引导你的说法啊 你看看在cli里面怎么搞啊"*）：

   ```
   ❓【lesson-prep】问：这节课希望侧重哪种上法？（…）
   ↩ 答它（回车跳过，回 👤 说别的）┃
   ```

   **在这个提示符下打的字，属于那条请求**（带 `answer_to` 投回去）；**回车跳过** → 回 `👤`，
   在那里打的字只给主 agent。**一次只摆一个**（答完接着摆下一个）。
   两个 CLI（`proto/__main__` 交互 ＋ `--say`、`evals/chat`）都走**同一个** `graph.next_pending()`
   —— "该摆哪一条"**只此一处**。真正的图形弹框留给 UI 层（不在本仓库）。
   ⚠️ **代码里的"框"目前就是提示符** —— 将来接 UI 时，把"用户在哪个框里答"映射成
   `answer_to` 即可，**平台侧不用再动**。

### 0.7 交付物的边界：**平台只保证产物**（2026-11-02 定）

> 用户原话：*"我们的机制**唯一能保证的稳定交付物就是产物**（产物可以有多个），
> 其余的**不需要平台机制保证**，我们就是要**遵循大多数 agent 的搞法，不要自己去随便造机制**。"*

#### 平台对产物保证什么（**全是代码做的**）

| 保证 | 落在哪 |
|---|---|
| **落库**（当场写盘） | `artifacts.store_artifact` |
| **给 ID 和真实路径** | `write_artifact` 的返回；`delegate` 的回执（`render_receipt`）顺路带上去 |
| **跨轮次累积** | 执行器的 `write_artifact` **按 run 记账**（`make_write_artifact(created)`），收全部轮次的产出 |
| **主 agent 看得见**（清单 ＋ 按需读全文） | 回执的【产出的产物】（ID ＋ 标题 ＋ 字数 ＋ **真实路径**）；正文走 `read_artifact` |
| **可以有多个** | 一次任务产出多份，各自独立 |

#### 平台**只有一种交付：产物** —— 「正文交付」是**反模式**

🔴 **用户 2026-11-03 定的立场**（原话）：

> "我们平台**根本就不保证**正文交付这条路径，参考的几个优秀开源 agent 项目**也都不保证** ——
>  我觉得这是**合理的**，因为**正文交付就是反模式**。"

所以：执行器把成品写在**回复正文**里时，平台**不为它做任何机制**：

- **不解析** —— 不认识任何业务标记（`@@SXW_PLAN_START` 这种是**业务**的）
- **不校验** —— 不检查块在不在、全不全
- **不抽取** —— 不把内容从正文里拿出来（"切一刀"是 **fail open**）
- **不累积** —— 跨轮次的正文产出**会碎**，回执只带最后一条
- **不做硬透传** —— 也别提"给正文交付造一条机制"（这个提案被当场否掉过）

**能走通就走通；碎了、丢了，都可能。**

> 📌 **别拿它当现行形态设计**（2026-11-03 的教训）：真技能**都已经改成落产物** ——
> `zhiwo-ai-multi-role-agent-builder`（当年踩坑的那个）现在明写
> *"方案与配置**一律落成产物**（调用 `write_artifact`），**不要写在回复正文里**"*；
> `lesson-prep` / `guided-learning` / `interactive-webpage` 同样。
> 只为压这条反模式而造的东西**已删**：`r1-protocol-delivery` / `r2-body-delivery`
> 两个 case、`evals/fixture-skills/`、内置玩具技能 `courseware-config`。
>
> ⚠️ **一个例外别混进来**：**任务本来就不需要文件产物**（纯分析）时，
> 成果在它的话里是**正常的** —— 那不算"正文交付"。
> 📌 平台**不判质量**（判定 2026-11-05 退休）：它只记"**交了产物没有**"，
> "这次交付够不够"由**主 agent** 判（回执把交付账摆给它，见 §11.2）。

#### 为什么不做（每条路都看过，都有硬伤）

| 想法 | 硬伤 |
|---|---|
| **平台无条件贴**（B2） | 🔴 **四家参考实现没有一家做** —— deepagents 明文"not shown to the user"（工具描述 + TUI/ACP 两道硬过滤）；deer-flow / nanobot / protoAgent 的直送**全走旁路 UI**（卡片 / 面板 / 独立气泡）。**没有一家把 subagent 的正文拼进主 agent 的回复** |
| **声明标记 + 存在性校验** | 要平台认识**具体业务字符串** → 约束作者，违反 **C2**；而且它就是 `deliverables`（已砍，见 X2）换名复活 |
| **平台自动落库** | 四家都没为"保真"这么做过 —— 它们的落库都在**异步 / 批量**路径上，动机是"异步"和"容量"，不是保真。而且产物库会脏 |
| **拼接全部轮次** | 混过程话术 + **块重复**（第 2 轮的块是"补充版"，和第 1 轮**不一致**）→ 下游不知道该信哪个 |

#### 实测证据（2026-11-02，真技能 `zhiwo-ai-multi-role-agent-builder`）

> 📌 **（历史）这次跑的时候判定还在**（2026-11-05 退休）—— 下面链条里的"判定"是当时的机制。
> 它证明的结论**与判定无关**：问题在"正文交付"这个形态本身。

| 跑法 | 主上下文 | 交付结果 |
|---|---|---|
| `auto`（主 agent 自己干） | **72k 字** | 完整 ✓ —— 它自己写的，**不用过手** |
| `exec_path: delegate`（强制委派） | **12.7k 字**（隔离生效 ✓） | 🔴 **只有 1/6** |

强制委派那次的完整链条：

```
执行器第 1 轮 → 产出五类配置
判定 → incomplete（"缺少预置输入项模块"）✓ 判得对
推回去
执行器第 2 轮 → "你说得对…下面补上：" + 补的那一类
回执 = report = _last_ai_text(resp)  ← 只取最后一条 → 前五类全丢
主 agent → "六类模块已齐全！"（它被回执误导了）→ 用户只拿到 1 类
```

**判定全程判得对**（它看得见**全部轮次**）—— 说明问题不在判定，**在"正文交付"这个形态本身**：
**产物天然累积，正文不累积**，多轮 react 必然把它碎掉。

> 📌 **顺带纠正一处**：回执只取最后一条（`_last_ai_text`）**不是 bug** ——
> 四家参考实现**全部**取最后一条（deepagents / deer-flow / nanobot / protoAgent 都是
> "倒序第一个非空 `AIMessage`"）。那是**标准做法**，**不改**。

#### 所以 skill 作者该怎么做

**要平台保证交付 → 用 `write_artifact` 落成产物。**
写在回复正文里的，**自己承担"不保证"** —— 平台不拦，也不管。

> 真技能 `zhiwo` 的 SKILL.md 就是这么写的，照着做。

## 二、核心设计

### 2.1 三个概念，三者正交

| 概念 | 是什么 | 载体 | 生命周期 |
|------|--------|------|---------|
| **Skill** | 专业能力包（静态） | `description` + `instructions` | 长期 |
| **Task** | 一次具体业务工作（动态） | `state["tasks"]` 里一条（**11 个字段**，见 `architecture-diagram.md` §5.1） | **跨轮存活**（同一 thread 内） |
| **Sub Agent** | **可选**执行者 | `create_agent` 建的一次性实例 | **用完即弃** |

**关键推论**：

- **Skill 不绑执行者** —— 加一个技能不需要动平台（`run_task(skill, given)` 通用）
- **执行器不持有状态** —— 状态在 `Task` 上，所以"重新起一个"是无害的
- **Task 只在主 agent 决定委派时才建** —— 不委派就没有 Task
- **执行器从不直接问用户** —— 它只把"缺什么"回给主 agent。这是 **P3 结构性消失**的原因：
  提问者**永远是主 agent 自己**，所以不存在"答给谁"的歧义

> ⚠️ **"跨轮存活"是 P2 修复的承重属性。** Task 不是"随一轮图结束就没了"，
> 它靠 checkpointer 跨轮活着。**前提是同一会话的 `thread_id` 必须跨轮稳定** ——
> 每轮换新 `thread_id` 会**静默**退化成"每次都是新会话"，
> Task、台账、supersede 全部失效，而且**不报错**。

### 2.1.1 被明确否决的方案（免得走回头路）

| 方案 | 为什么否决 |
|------|-----------|
| **断点 / 草稿外置**（把执行进度写进产物或草稿，供下次续跑） | **接受重跑** —— 宁肯让执行器重跑一遍，也不要"草稿 vs 成品"这个状态区分，那会一次引入**一整类 bug**。代价是重复劳动 + 产物重复（见 §9.1 T3/T4），这个代价是**已知且接受**的 |
| **恢复用 `interrupt()` + `Command(resume)`** | 见 §8.4「为什么不走 interrupt」 |
| **恢复 plan 节点**（复杂任务先规划再执行） | 职责已被主 agent 的循环吸收；`delegate` 是同步的，依赖在主 agent 循环里天然解决 |

### 2.2 主 agent 是**完整的 agent**，不是纯路由器

```
主 agent 循环
  ├─ 直接答            —— 闲聊 / 追问 / 澄清（不建 Task）
  ├─ write_artifact    —— 自己产出短内容（不建 Task）
  ├─ list_artifacts    —— 看产物清单（ID/名称/字数/梗概，不含正文）
  ├─ read_skill        —— 按需读技能原文（核对交付标准）
  ├─ read_skill_file   —— 按需读技能包里的某一份文件（渐进式披露第三层）
  ├─ read_artifact     —— 按需读产物全文（渐进式披露第二层）
  └─ delegate(...)     —— 需要专业能力时（建 Task）
```

> ⚠️ 后三个是 **2026-10-29 加的**（F11/F12）：主 agent **不是包工头** ——
> 它要能执行、也要能按需读技能与产物。**常驻的只有 `name + description` 与产物清单，
> 全文一律按需**（渐进式披露），否则主上下文会被长文撑爆。

**为什么"技能活一律委派"**（去掉了 `load_skill`）：
实测给了它"自己干技能活"的路，它就会走——**隔离全丢**。
而且**它在派发前无法判断产出有多长**（备课可能 300 字也可能 3000 字），所以不要让它猜。

### 2.3 平台在旁边只做两件事

| 节点 | 做什么 | 硬/软 |
|------|--------|-------|
| `prepare` | ① 把用户原话**投给待答任务**（`_feed_waiting`）② 把**任务台账**注入主 agent 上下文 | **硬**（平台保证投递与注入） |
| `finalize` | **无条件**把待答的执行器原话贴进回复（透传） | **硬**（保证不丢） |

**都只提供事实，不替它做决定**（"用户是不是在回答"是理解问题，该柔性）。

## 四、模块详解（结合代码）

### 4.1 `skills.py` + `skill_pack.py` + `artifacts.py` —— 技能领域 / 技能包 I/O / 产物领域

> 🔴 **三个文件，两个领域 + 一层 I/O**（2026-10-30 拆开）：
> `skills.py` = **技能领域**（`Skill` 是什么）· `skill_pack.py` = **技能包 I/O**（怎么从磁盘读）·

### 4.2 `llm.py` —— 结构化输出 + 兜底

> 🔴 **一条贯穿全案的施工规范：决策的结果必须结构化。**
>
> 所有 LLM 判定都走 **Structured Output**（OpenAI `response_format` /
> LangChain `with_structured_output`）—— 把 JSON Schema 传给模型，
> **模型原生保证结果符合结构**，不需要靠提示词去"求"它按格式输出。
>
> **不要靠工具参数去传决策。** 反面教材就是早期的 `finish` 工具：
> 让模型"调一个工具来宣告完成"——**模型不调，决策就静默丢了**。
> 不报错、不抛异常，只是没人知道任务完成了。这正是 `finish` 被砍掉的**真正原因**
> （不只是"能靠既有事实判定"那么简单）。
>
> **通用检查动作**：以后新增任何 LLM 判定，都问一遍「**它的输出结构化了吗？**」
> 结构化之后，代码才能拿它做逻辑转移判断。

```python
def safe_structured(schema, prompt, default, *, tag="") -> Any:
    """重试 1 次 → 仍失败则退化到**保守默认值**"""
```

**为什么需要兜底**：实测 DashScope 偶发
`grammar validation or compilation failed: sandbox grammar compile timed out`
——**一次抖动就炸掉整个 turn**（踩过两次）。

**调用点的保守默认值**（都朝"不丢信息"的方向退化）：

| 调用点 | 失败时默认 | 理由 |
|--------|-----------|------|
| `_ask_main`（试答） | `can_answer=False` | 交给用户，而不是编一个答案 |
| 评测层各 rubric | `None` → 判**不通过** | **评分调用失败不判「通过」**（见 `architecture-diagram.md` §4.5） |

> 📌 **（历史）判定时代**这里还有两行：`_judge` → `incomplete`（"会让它再 react 一轮"）、
> `_which_unasked` → `asked=False`（那个 LLM 判断 2026-10-29 已删）—— 两个调用点现在都没有了
> （判定 2026-11-05 退休，见 §11.2）。

### 4.3 `executor.py` —— 执行器（三态由结构定 + 出口限制）

#### 4.3.1 平台约定（**逐字**）

```python
_PLATFORM_RULE = (
    "你是任务执行者。按下面的能力指令完成任务。\n"
    "要交付成文件的内容，调用 write_artifact 写入产物库：**名称、一句话梗概、正文**三样都给，\n"
    "正文写全（梗概是对外露出的那一层，别人靠它决定要不要读全文）。\n"
    "任务里列出的【可读产物】只是一份**清单**（名称与梗概）——需要全文时用 read_artifact 读，\n"
    "不要凭标题或梗概猜内容。\n"
    "\n"
    "如果缺少完成任务所必需的信息：\n"
    "- **明确说明你需要什么**（缺哪个参数、要什么确认）——你的请求会被转给能提供它的一方；\n"
    "- **不要编造**，也不要用「已完成」之类的话收尾。\n"
)
```

> **措辞理由**：说"**转给能提供它的一方**"，不说"向用户提问"——
> 因为**执行器是隔离的，它不知道有主 agent**。
>
> 🔴 **"要信息"的出口是 `ask_user` 工具**（`make_ask_user`），工具说明里写死了两条：
> **要信息必须用它**（写在回复正文里平台看不到 —— 平台**不读正文**）、**能自己判断的别问**。
> 平台看到这次调用就**结束这一轮**（见 §4.3.5）。

#### 4.3.2 出口三态 + 结果结构

```python
OutcomeStatus = Literal["completed", "waiting_for_input", "incomplete"]

@dataclass
class ExecOutcome:
    status: OutcomeStatus = "incomplete"   # ← 由 _structural_status 按**结构**算（见下）
    artifacts: list[str] = field(default_factory=list)  # 这次新写的产物 ID（记账）
    report: str = ""        # 最后一条有内容的 AI 消息（**只给回执用**，不参与判断）
    rounds: int = 0         # 实际 react 了几轮
    asked: str = ""         # 它申报要的信息（`ask_user` 参数里那句原话）
    fault: str = ""         # 平台故障（非空 = 这一轮**根本没跑成**，不是执行器干不了）
```

**三态怎么算出来的**（`executor._structural_status`，**抽成函数是为了可单测**）：

```python
if outcome.asked:      return "waiting_for_input"   # ① 申报优先
if outcome.artifacts:  return "completed"           # ② 只说"交了东西"
return "incomplete"                                 # ③ 都没有 → 推回去
```

> 🔴 **申报优先**：它可能交了一部分之后卡住 —— 那时该去要信息。
>
> 🔴 **`completed` 只说"交了东西"这个事实**，不说"够不够 / 对不对"—— 那是**主 agent** 判的
> （回执把交付账摆给它）。**平台判质量是判定时代的做法，毛病就在那。**

> **为什么用枚举不用两个布尔值**：两个布尔有 4 种组合、只有 3 种合法，
> "矛盾组合"只能靠约定排除；**枚举从类型上就闭合**。

> 🔴 **同一类错的第二种形态：隐式 `else`。**（判定时代踩的）主 agent 试答后重跑，结果有三种，
> 但代码只判了两种 —— **`incomplete` 被隐式当成"在请求信息"，于是去问用户**。
> 用户根本没被问过，系统却去问他 —— 这就是 **P3 复发**。
> **修法不是加个 `else`，是把三个分支显式写全。**

> 📌 **~~`_Judgement`~~（判定的输出结构）2026-11-05 随判定整个删掉**：原来是
> `{status, progress, missing, reason}` 的 `with_structured_output` 输出 —— `reason` 是
> "判定为什么这么判"的**唯一可观测面**（重实现时最容易漏）。判定退休后**没有这次调用**，
> 也就没有这个 schema；"任务往哪走"由上面那三行函数定。

（原 §4.3.3 与 §4.3.4 两节合并成这一节；**后面的小节编号不动** —— 别处引用的 §4.3.5 起都还指得准。）

> 材料取材 `_judge_material` · 两条字符预算（`JUDGE_ITEM_BUDGET` / `JUDGE_TOTAL_BUDGET`）·
> `need_more` 那个"先标记、未来可能做"的 TODO —— 判定那个模块**整个文件没了**。
> 它是被**根因移除**的：那两个问题（"任务结没结束" / "在不在要信息"）本来就不该由一次判断回答。
>
> **留在这里的几条教训仍然成立**（它们管的是"给 LLM 喂上下文"这件事，不限于判定）：
>
> | 教训 | 出处 / 佐证 |
> |---|---|
> | **它看得到做这个判断所需的信息吗？** —— 前三个坑是"提示词忘了带某个字段"（`instructions` / `given` / `progress`+`missing`），**第四个不是**：信息明明在列表里、**取错了那一条**（无产物时只取最后一条 AI 消息，看不到前面几轮）—— 所以前三次的检查法**发现不了它** | 每加一个 LLM 判断都问一遍 |
> | **截断标记的措辞是被实测逼出来的**：原来写「……（此处省略 N 字）……」，模型会把它当成**作者偷懒的占位符** → **产物越长越必然判 incomplete**。实测代价：`s13` 一个任务被推回去 3 轮、**重写了 3 份重复教案**（607 秒 / 144k token）；`e13` 单 run 从 9.7k token 涨到 79k。**措辞只说平台知道的事实** | §三「交接三问」② |
> | **标注省略比保头保尾本身更重要** —— 不标的话，模型**不知道自己没看全**，会基于不完整信息**自信地下判断**，那比"猜"更糟 | 同上 |
> | **预算扫描实测**（`experiments/debug_clip_marker.py`，3 次采样、产物 3112 字）：800 字时占位符正好落在被截掉的中段，**既误判完整产物（3/3）、又漏掉真缺陷（0/3）**；1600 → 1/3；2400 → 2/3；**4000 → 两边都 3/3**。**单调** —— 判得准不准，基本取决于它能不能看到全文 | 这是"预算该定多少"的取证方式 |
> | **这只把门槛往后挪**：产物再长（48k 课件）还是会截断，截断之后**没有能力**验证完整性 —— 那时它给的"完成"是**推测**，不是判断（实测：74% 没给判定看，它仍判 `completed`，理由「平台截断部分不影响已有结果的完整性判断」） | 现在：平台**根本不下这个结论**了 |
> | **"有产物时不要把它说的话也喂进来"** 是实测踩出来的回归：执行器在产物之后补了句礼貌收尾「……**需要调整吗？**」，被当成"明确请求继续所必需的信息" → 判成 `waiting_for_input`，**而产物其实已经完整交付**（`debug_exit` 的 B 用例当场从 ✅ 变 ❌）—— 🔴 **这正是判定退休的根因**：喂了，礼貌收尾被误读；不喂，真问题被吞 | 两个语义不该压进一次判断 |
>
> 📌 相关的取证脚本（`experiments/debug_judge_variants.py` / `debug_clip_marker.py` /
> `test_judge_material.py`）依赖**已删的 API**，跟判定一起作废；结论留档在本文 §7.1 / §11.4
> 与 git 历史。

#### 4.3.5 出口限制循环

```python
MAX_REACT_ROUNDS = 3

for round_i in range(MAX_REACT_ROUNDS):
    resp = {}
    for chunk in trace.stream_agent(agent, {"messages": messages}, None, f"执行器·{skill.name}"):
        resp = chunk                       # ⚠️ 不传 config；边跑边录（逐字流式）
    outcome.artifacts = list(created)      # 记账（write_artifact 自己记的）
    outcome.report    = _last_ai_text(resp)
    outcome.rounds    = round_i + 1

    if asked.get("question"):              # ① 申报了要信息 → 这一轮到此结束
        outcome.asked = asked["question"]
        break
    if outcome.artifacts:                  # ② 交了产物 → 收工
        break
    # ③ 都没有 → 推回去（照**结构事实**说，不编"还缺什么"）
    if round_i + 1 < MAX_REACT_ROUNDS:
        messages = list(resp["messages"]) + [HumanMessage(nudge_text())]
    else:
        # 显式写出：推满了，不再推 → outcome 保持 incomplete → delegate 判 failed
        ...

outcome.status = _structural_status(outcome)   # ← 三态**由结构定**（见 §4.3.2）
```

> 🔴 **① 优先**：它可能交了一部分之后卡住 —— 那时该去要信息（`_structural_status` 同一顺序）。
> 🔴 **平台不等它继续说**：看到 `ask_user` 就 `break`（**结构**保证，不靠提示词让它自觉）——
> 它调完工具还会接着往下说，那半截话**不进这一轮的结论**。

**推回去的提示词**（`proto/handoff/nudge.py::nudge_text` —— 只说**平台看得见的两件事实** ＋ **两条出路**）：

```
这一轮**既没有交付产物，也没有说明你需要什么信息**。

两条路，选一条走：
- **干完了** → 用 `write_artifact` 把成果**交付成产物**（正文写在回复里平台看不到，不算交付）；
- **缺信息、干不下去** → 用 `ask_user` **说清缺什么**（平台会先问主 agent，它答不上再转用户）。
不要用「已完成」这类话收尾 —— 那句话不构成交付。
```

> **实测效果**（`--exec-path delegate` 真跑）：第 1 轮既没交也没申报 → **推回去** →
> 第 2 轮就**调了 `ask_user`**（nudge 把模型推上了正路）→ 试答答不上 → 登记待答 → 透传用户。
>
> 📌 **（历史）判定时代**这段带的是判定吐的 `progress` / `missing`（"你已经完成了什么、还缺什么"）——
> 判定退休后**没有来源**，也不许在这里编：做法改成"**平台造路**"（不猜它想说什么，
> 把正确的两条路摆在它面前）。

#### 4.3.6 产物识别（硬机制）—— **按 run 记账**（2026-11-03 改）

```python
# run_task 里：给这次 run 造一个**自己的** write_artifact（闭包）
created: list[str] = []
tools = [make_write_artifact(created), read_artifact, read_skill_file, make_ask_user(asked)]
...
outcome.artifacts = list(created)      # ← 谁写的谁记账，**不扫消息文本**
```

**原来**是 `_recover_artifacts(resp, preexisting)`：**扫执行器的消息文本**找回
"消息里出现过、且产物库里真实存在、且不是这次之前就有的" ID。两条口径缺一不可：

1. 必须在产物库里查得到 —— LLM 编 `art_999` 无效
2. 必须不是这次跑之前就存在的（`preexisting` 差集）—— 否则**把读来的算成它交付的**
   （F14，2026-10-29 实测：guided-learning 读 `art_001` → 任务记录变成"产出 art_001、art_002"）

🔴 **改成记账的理由**（用户 2026-11-03 的全局交接自查点 ④⑤）：
**扫文本既不是结构化、也不是硬机制** —— `preexisting` 差集就是给这个扫描打的补丁，
而差集本身还留着"两个执行器并行时互相覆盖"的窗口。改成**闭包记账**之后：

- **"读来的算成写出来的"结构性不可能**（读不记账）→ `preexisting` **不需要了**
- **并行窗口结构上不存在**（闭包按 run 归属，不是"难触发"）

> ⚠️ **闭包，不是模块级全局** —— 同 `executor._user_turn_reader` 的教训：
> 并行 delegate 时两个执行器会互相覆盖（`ARTIFACT_DIR` 那种全局状态在这儿就是坑）。
> 断言在 `evals/unit_handoff.py` ⑬。

#### 4.3.7 主 agent 的上下文大小：**只记录 + 超线 warning，不判红**

执行器读了哪些产物、主 agent 的上下文涨到多少 —— **只作为读数呈现，平台不据此判失败**
（2026-10-30 用户定：*"对于 main agent 的上下文大小 我们只记录就行 暂时不要加逻辑处理"*、
*"删掉这个测试 把这个信息记录到日志 warning 里面不就完了"*）。

**为什么不做成断言**：**读产物是主 agent 的合法能力**（它不是包工头，也要能干活、能按需读，
见 §4.2 的渐进式披露）。拿上下文大小判红 = **罚一个合法能力**，
而且"聊得久"、"多读一次技能原文"都会误伤（F17：t2 历史 7 轮只绿 1 轮，一半的红是这么来的）。

**读数在哪看**：

| 位置 | 打什么 |
|---|---|
| `evals/chat.py` | **每轮小结一行** `📊 CONTEXT`：`主上下文 N 字（消息 A + system B）｜产物库正文 M 字｜耗时` |
| `evals/harness.py` → `_run.md` | 每轮 `<sub>主上下文 … ｜产物库 … ｜delegate …</sub>` |
| `proto/__main__.py` | 每轮 `★ 主 agent 上下文 = N 字 ｜ 产物库正文 = M 字` + 隔离比 |
| 跑批 `report.md` | 指标表里的 `主上下文·消息` 中位数 / 最大 |

**超线怎么办：喊一声，不判失败。**

```python
CTX_WARN_CHARS = 12000        # evals/harness.py
def ctx_warn(total) -> str:   # 超线返回一句提示，否则空串
```

CLI 和 `_run.md` 都调它 —— 超了多打一行
`⚠️ 主上下文超告警线 12000 字（看看是不是把产物正文读进来了 —— 依赖转交只需传 ID，不必读全文）`。

> ⚠️ **口径**：`main_ctx_chars` **不含 system prompt**（`create_agent(system_prompt=...)`
> 不落 state），所以两个数一起给 —— 真实上下文是两者相加，system 是一笔固定开销。
>
> **参照读数**（历史跑批）：单技能隔离场景 517–1109 字；多技能长产物场景 7890–14832 字。
>
> 🔴 **代价要记明**：删掉 `main_ctx_under` 之后，**"产物正文不进主上下文"这条架构承诺
> 没有机判了** —— 从"每次跑批自动判"降级成"读数摆在眼前、超线喊一声、由人判断"。
> 这是用户明确选的取舍。

#### 4.3.8 可调优点（落地后调优从这里入手）

**这套机制的效果，几乎全由下面这几个地方决定。** 改完**不要凭感觉** ——
跑 `experiments/debug_exit.py`（出口限制行为）验一遍。

| # | 调什么 | 位置 | 往哪调 |
|---|--------|------|--------|
| 1 | 执行器缺信息时怎么表达 | `_PLATFORM_RULE` + `ask_user` 的工具说明 | 说得越清楚，越早走请求信息路径，越少被硬推 |
| 2 | 推回去时怎么说 | `proto/handoff/nudge.py::nudge_text` | 关键是**点明两条出路**（`write_artifact` 交付 / `ask_user` 说清缺什么），别让它从头再来 |
| 3 | **最多推几轮** | `MAX_REACT_ROUNDS`（现 3） | 调大 → 更执着但**更烧 token**；调小 → 更早交给主 agent |

> 📌 **第 3 条的取舍**：3 轮是"够它自我纠正一次、又不至于无限烧钱"的折中 ——
> **不是算出来的，是试出来的**。
>
> 🔑 **`_PLATFORM_RULE` 的一个副作用（好的）**：它让执行器**主动说明需要什么** ——
> 于是"干不成"的任务**不再被推满 3 轮**（1–2 轮就说明需要什么了），自然走请求信息路径。
> **早说早处理，不用硬推。** 所以 3 轮上限在实践中**很少被用满**。
>
> 📌 **（历史）判定时代这里还有 3 条**（`_JUDGE_RULES` 的三条规则怎么调：松 → 残次品放行 /
> 紧 → 吹毛求疵，实测推 3 轮 4m29s）—— 那三条规则随判定删掉了，"产物写完了没有"这类判断
> 搬到了**评测层**的软 rubric（`artifact_is_complete`，见 `architecture-diagram.md` §4.5）。

#### 4.3.9 正文提问：迁移 `sx-agent` 的必经之路

`sx-agent` 的 skill **全部是"把问题写进回复正文"**（见 §8.1）。所以每个现存 skill
迁移过来之后，**都会走"正文提问"这条路**。

| 层 | 机制 | 作用 |
|---|------|------|
| **预防** | `_PLATFORM_RULE`（"明确说明你需要什么"）＋ **`ask_user` 的工具说明**（"要信息必须用它：写在回复正文里**平台看不到**"） | 引导执行器**把缺什么说出来**，而不是含糊地"我做不到" |
| **兜底** | 🔴 **没有** —— 平台**不读正文**（那是判定时代的做法） | 正文里的提问**平台看不见** → 这一轮既没交产物、也没申报 → `incomplete` → 推回去，nudge **点明两条路** |

> 🔴 **这条变化要写清**（2026-11-05）：判定时代有"兜底"（判定规则 3 把正文里的提问**翻译**成
> `waiting_for_input`）；判定退休后**那层翻译没有了**，正文提问**只能靠推回去纠正** ——
> 实测可行：第 1 轮没交也没申报 → 推回去 → 第 2 轮就调了 `ask_user`。
> **迁移现存 skill 时，别指望正文提问还能被接住**。

**（历史）判定时代实测的三个场景**（`experiments/debug_body_question.py` 验的，
**该脚本已跑不起来** —— 依赖被删的 API，见 `../experiments/README.md`）：

| 场景 | 当时的结果 |
|------|------|
| 缺参数 | ✅ 被翻译成 `waiting_for_input`（`missing=['难度']`） |
| 参数齐全 | ✅ `completed`，**没有误报** |
| **只说不做**（正文说"已经帮你把题出好了"，但产物库是空的） | ✅ 判 **`failed`，不放行** |

> 🔴 **第三个场景仍然最关键** —— 它就是"**系统看起来成功了，但用户什么也没拿到**"。
> 现在接住它的是**结构**：没有产物 = 没有出口（`completed` 只认产物账）→ 推回去。

### 4.4 `agent.py` —— 主 agent

#### 4.4.1 工具集（**六个**）

| 工具 | 用途 |
|------|------|
| `delegate(skill_name, task, artifacts=[...])` | 委派一件具体工作（**建 Task**）；`artifacts` 是这次要参考的**产物 ID**，**当场校验**（引用了不存在的 → 拒绝派发） |
| `write_artifact(title, summary, content)` | 自己产出短内容（**不建 Task**） |
| `list_artifacts()` | 产物清单（ID/名称/字数/梗概），**不含正文** |
| `read_artifact(artifact_id)` | 按需读回产物全文（渐进式披露第二层） |
| `read_skill(skill_name)` | 按需读技能原文（渐进式披露第二层）——写 task 前核对交付标准 |
| `read_skill_file(skill_name, path)` | 按需读技能包里**某一份文件**的全文（渐进式披露第三层）——路径照抄清单里的 |

> ⚠️ **上面是默认档（`EXEC_PATH="auto"`）的六个工具。** 工具集**由 `proto/agent.EXEC_PATH` 决定**：
>
> | 档 | 工具 | 硬度 |
> |---|---|---|
> | `auto`（默认，产品行为） | 上面六个 | — |
> | `delegate` **强制委派** | `[delegate, list_artifacts]` | **半硬** —— 拿掉了"自己干"的原料，但挡不住它在回复里硬写 |
> | `inline` **强制主 agent 自己干** | 六个里**去掉 `delegate`** | **全硬** —— 工具不存在，它调不了 |
>
> 用途是**跑批时"测哪条链路就开哪条"**，不用碰运气碰一个愿意走那条路的 case。
> 见 `evals/README.md` 的「执行路径开关」与 `architecture-diagram.md` §4.1。

#### 4.4.2 系统提示的**五块**（逐字要点）

**① 两种做法**
```
1. **直接答**：闲聊、追问、解释、澄清、简单修改——不需要专业能力的事，你自己说。
2. **delegate 委派**：需要下面列出的**专业能力**时，**一律委派**，不要自己凭感觉做。

为什么必须委派：专业能力的产出可能很长，自己干会把你的上下文撑爆。
**你在派发前无法判断产出有多长**，所以不要猜——需要专业能力就委派。

委派回来如果显示「它在**要信息**（调了 `ask_user`）」——**什么都别做，尤其不要自己补一个答案**：
平台已经替你查过一次上下文了（`delegate` 内部做的）；确实没有，
平台会负责把问题**转达给用户**，用户答复后也会**投回给那个执行器**。
你这条回复只要说清楚「派了什么、还差什么」就行。

🔴 **绝不要替用户定一个答案再委派一次。** 用户没说过的，就是没有 ——
你猜的那个值会变成一份基于错误前提的成品，而用户不知道。
```

> ⚠️ **最后这两段是 2026-10-29 改的，别改回去**：原来是"先看自己的上下文里有没有它要的信息，
> 有就直接再委派一次"—— 把**试答**交给主 agent 自己判断。现在试答由
> `delegate` **内部强制**做（`_ask_main`），主 agent 只负责说清楚"派了什么、还差什么"。
> 原因见 §4.4.3 与 F7：让主 agent 自己决定要不要再派，它会**自己编一个答案**重新委派，
> 而平台顺手把待答标成 `superseded` → **用户从没被问过**。

**② 信息不全时怎么办**（B2 的落点）

> **实测依据（不写这段会怎样）**：不写的时候，**三轮下来 `Task` 始终 = 0** ——
> 它一直在问，**从来没委派过**。执行器本来就能自己判断缺什么，
> 平台抢先替它问，等于把执行器的活抢了。

```
## 信息不全时，**不要一律问** —— 先判断能不能推进

- 能推进就**先推进**（真的缺东西时，执行器会告诉你）；
- 确实推进不了的，才问用户；要问就**一次问完**（别挤牙膏）；
- **哪些参数是必答的、哪些有默认值，以技能指令为准** —— 平台不替你猜，你也别猜。
```

**③ 产出范围**（用户要求"保守优先"）

> **实测依据（走了一段弯路）**：加上 ② 之后，第一次修法是"**列默认值**" ——
> 结果它**一次派了 3 个技能**，自行扩大了产出范围。所以 ③ 必须单独写死。

```
## 🔴 产出范围**以用户明确说的为准**，不要自行扩大

用户说「帮我备课」就**只出教案**；不要说「我顺便把导学单和小测也做了」。
**用户没要的，不要直接做掉**——那会浪费他的时间和成本。

想提供的话，**在回复末尾提一句**就行（如「需要的话我也可以出导学单和随堂小测」），
让用户自己决定要不要。
```

**④ 前序产物怎么交给下一个任务**（2026-10-29 加，F11/F12 的直接产物）
```
**传 ID，不要转述正文。** 需要前面交付的产物当输入时：
delegate(skill_name="...", task="...", artifacts=["art_001"])
执行器会拿到它的名称与梗概，需要全文自己读。

- 把正文抄进 task 是**错的**：对方拿到的是你的摘要而不是原文（失真），
  而且正文会一直占着你的上下文。
- 不确定有哪些产物 → list_artifacts()
- 不确定某个能力**交付什么、按什么标准交付** → read_skill(name) 读原文核对，
  **不要凭一句话描述猜**：你猜出来的要求会压过能力自己的交付标准。
- 传了不存在的产物 ID 会被当场拒绝，并告诉你现有的清单。
```

**⑤ 回复用户时的硬要求**（隔离的关键）
```
**产物正文不要搬进你的回复。** 委派完成后，只告诉用户：
交付了哪几样、各自的产物 ID、以及执行器给的一句话摘要。

- **不要**用 `read_artifact` 把产物正文读出来贴进回复
- **不要**自己用 `write_artifact` 重新写一遍执行器已经交付的内容
- `read_artifact` 是**按需**能力：用户明确说「给我看看内容」「改一下某处」、
  或你自己确实要核对内容时才读；只是转交给下一个任务，传 ID 就够
```

#### 4.4.3 `delegate` 的返回口（**7 个可达**）

> 🔴 **所有出口都走同一个 `render_receipt`**（2026-11-02）：**固定段名 · 每段标来源 ·
> 一个字都不截** —— 和交接书 `render_briefing` 对称。理由见 `architecture-diagram.md` §3.2.7。

| # | 触发 | 回执里的关键段 |
|---|------|-------------------|
| 1 | **技能名不存在** | `【这次没有派发】❌ 没有能力「X」`（**不建 Task**，直接拒绝） |
| 2 | **产物 ID 不存在** | `【这次没有派发】❌ 产物 art_999 不存在` ＋ `【本会话现有产物】`（**不建 Task**） |
| 3 | `completed`（**交了产物**） | `【交付】它交付了 N 个产物` ＋ `【产出的产物】`（**带真实路径**）＋ `【下一步】`＝「**你判**：这次交付够不够？」 |
| 4 | **`waiting_for_input` → 试答成功 → 自动重跑 → `completed`** | 同上 ＋ `【你补的信息】（**你说的**）` |
| 5 | `waiting_for_input`（试答后仍缺信息） | `【交付】它在**要信息**（调了 `ask_user`）` ＋ `【下一步】`＝平台已登记待答 |
| 6 | `incomplete` → `failed` | `【交付】它既没交付产物、也没说要什么信息（推了 N 轮）` ＋ `【下一步】`＝换个说法重派／向用户说明 |
| 7 | **平台故障**（`outcome.fault`） | `【交付】⚠️ 没跑成 —— 平台故障` ＋ `【平台故障】` ＋ `【下一步】`＝**原样再 `delegate` 一次** |

**每个出口都带【执行器说】（全文，不截断）** —— 那是"它交付了什么"，
主 agent 靠它写回复、人靠它读日志。

> 🔴 **第 4 个出口最容易漏实现。** 试答成功时，平台会**带着补充信息自动重跑一次执行器**
> （`run_task(skill, render_briefing(rec))`，`qa` 里已经记下那一问一答），成功了**直接交付** ——
> 这是 `waiting_for_input` 主回路的**成功半边**。
> 若实现成"试答完就登记待答"，主 agent 的答案永远用不上，白多一轮往返。

> 🔴 **平台不下"完成了"的结论**（2026-11-05）：`【交付】`那一行是**事实**（交了几样 / 它在要信息 /
> 什么都没给），不是判决 —— "完成没"原来由判定给，主 agent 只是照转。现在
> **"够不够"由主 agent 判**，回执把交付账摆给它（第 3 条那个【下一步】就是这句）。
> ⚠️ 同时删掉的是"`completed` + **无产物**"那一档（正文交付）：三态由结构算之后它**不可能**
> —— 没产物就是 `incomplete`（见 §0.7 与 §11.2）。

> 🔴 **`report` 只取最后一条 AI 消息 —— 这是个**位置陷阱**（机制上确凿）。**
>
> `report = _last_ai_text(resp)` 取的是"最后一条**有内容的** AI 消息"。
> 在出口循环里，若第 1 轮说了 A → 判定 `incomplete` → 推回去 → **第 2 轮只回了句总结**，
> 那 `report` 就**只剩总结，A 丢了**。
>
> **实测**（把出口循环累积出的消息列表直接喂给 `_last_ai_text`）：
>
> ```
> report = '好的，配置已经生成完毕，请查收。'
> 前面那轮的正文还在吗？ False          ← ❌ 丢了
> ```
>
> ⚠️ **取最后一条不是 bug** —— 四家参考实现（deepagents / deer-flow / nanobot / protoAgent）
> **全部**这么做（"倒序第一个非空 `AIMessage`"）。**那是标准做法，不改。**
>
> **残留的真实影响只有一处**：**任务本来就不需要文件产物**（纯分析）且**跨多轮**时，
> 回执只带最后一轮的结论，前面的分析丢了 —— 而主 agent 只能看到这一条。
> 这个位置踩过一次：当时的修法是定位"带 `finish` 调用的那条 AI 消息"
> （`_inline_deliverable`）；后来 `finish` 被砍掉，就退回了"取最后一条 AI 消息" ——
> **修法没了，坑还在。**
>
> **要修就针对纯分析任务**（比如让 `report` 带上"这次 react 了几轮、前几轮的结论在哪"）——
> ⚠️ **不要为"正文交付"修**：那是反模式，平台不保证（§0.7）。

#### 4.4.4 ~~`_outcome_note`~~ —— **2026-11-05 删**（判定退休）

> 📌 它原来是"没完成"那几条出口上挂的信息交接：把**判定**给的
> `progress` / `missing` 渲染成【已做到】【还缺】两段贴给主 agent。
> **判定没了 → 这两个字段没有来源 → 函数一起删**（`agent.py` 里已经没有它）。
>
> 现在"没完成"的出口给主 agent 的是**结构事实 ＋ 它自己的原话**：
> 【交付】一行（它在要信息 / 既没交也没说）＋【执行器说】全文（**它说的**）＋【下一步】。
> "该换个说法重派、还是向用户说明"由主 agent 看这些**自己判**。

#### 4.4.5 `_supersede_old` —— 防台账挂过期项

```python
def _supersede_old(runtime, skill_name) -> list[dict]:
    for t in runtime.state.get("tasks") or []:
        if t.get("skill") == skill_name and t.get("stage") == "failed":
            out.append({**t, "stage": "superseded"})
```

🔴 **只取代 `failed` 的 —— `waiting_for_input` 一律不碰**（2026-10-29 改）。

原来连 `waiting_for_input` 一起取代，理由是"旧待答挂在台账里，主 agent 会以为还有事没做完"（S19）。
但那个理由是**为了美观**，代价却是**静默抹掉一个用户从没回答过的问题**：

> 实测（F7）：执行器正确地问了"难度是哪个"，平台试答也正确地说"答不上"，
> 平台告诉主 agent"就向用户提问" —— 结果主 agent 自己编了个"难度：基础"重新委派，
> `_supersede_old` 顺手把待答标成 superseded，于是 `finalize` 看到"没有待答"，什么都不做。
> **用户从没被问过。**

现在待答由平台负责投递和透传（`graph._feed_waiting` / `node_finalize`），
**重派不再是解除待答的路径** —— 所以这里碰它没有意义，只会把问题弄丢。

- `completed` 的是**历史记录**，不能被抹掉（用户可能还要看产物）
- `running` 的不会出现在旧 state 里（并行调用各读各的旧快照）

**实测日志**：`取代了 1 个同技能的未了结 Task：['t92d26841']`

#### 4.4.6 两个"实测踩出来的"实现细节

| **task id 取 `tool_call_id` 尾部** | 取前 6 位会撞车——`tool_call_id` 形如 `call_abc123…`，**前几位所有调用都一样**，实测两个任务的 id 都变成 `t_call_a` |
| **`_cmd` 统一返回口 `_out`** | 每个返回口都要带上 `superseded`，漏一个就丢 |

#### 4.5.2 State

```python
class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    tasks: NotRequired[Annotated[list[dict], _merge_tasks]]   # ← 按 id 合并的 reducer
    log: NotRequired[Annotated[list[str], operator.add]]
```

```python
def _merge_tasks(old, new) -> list[dict]:
    merged = {t["id"]: t for t in (old or [])}
    for t in new or []:
        merged[t["id"]] = t
    return list(merged.values())
```

> **为什么必须用 reducer**：模型会**并行**发多个 `delegate` 调用，
> 每个工具都读到同一份旧 state —— 直接覆盖会**只剩最后一个 Task**。

#### 4.5.3 `prepare` —— ① 投递用户原话 ② 注入台账

**顺序不能反**（先投递，注入的台账才反映投递后的新状态）。

**① 投递**（`_feed_waiting`）：把用户这条消息**原话**投给**所有** `stage=waiting_for_input` 的 Task，
答复**累积**进 `rec["answers"]`，用 `render_briefing(rec)` 重新跑执行器。

> 🔴 **不做任何判断** —— 不判断"用户是不是在回答""答的是哪一条"。用户 2026-10-29：
> *"只要是答复了 就直接恢复 subagent 就行啊"* · *"答非所问就答非所问呗"*。
> **平台不替用户判断他的话算不算回答** —— 那是语义判断，而且判断错了比"多问一遍"更糟（F7 就是这么丢的）。
>
> 这也是**待答唯一的解除路径**：投递后要么 `completed`，要么还在等。

**② 注入格式**：

```
【平台提示】你已委派出去的工作（共 N 项）：
- t92d26841  「quiz」  ⚠️ 它在要信息
      执行器说：三年级随堂小测，就差一个信息——难度要「基础/提升/挑战」哪一档？
- t8e89a3d4  「lesson-prep」  ✅ 它交付了产物 → art_001

**「等用户答复」的那些，平台已经负责把问题转达给用户、也会把用户的答复投回去** ——
你**不用**重新委派它们，更不要自己替用户编一个答案。
```

> 🔴 **这段提示是 2026-10-29 改的，别改回去。** 原来写的是
> 「用户这条消息**很可能是对上面『等用户答复』那条的答复**——若确实如此，带上信息重新 delegate 那一条」，
> 于是：**投递和转达都归主 agent 管**。
>
> 那个版本有个**已知坑：用户换话题时死循环**（把换话题当成对上一个问题的回答 → 清空待答 →
> 重跑执行器 → 又挂起问同样的问题）。所以当时还配了一句逃生话
> （"如果它明显是别的话题，忽略本提示，正常处理"）——**那是在用提示词补机制的窟窿**。
>
> **现在窟窿堵上了**：投递（`_feed_waiting`）和转达（`node_finalize`）都由平台做，
> 主 agent 不再有"要不要重派"的判断权，也就不需要那句逃生话。

**哪些状态展开细节**：`_NEEDS_DETAIL = ("waiting_for_input", "failed")`
—— 其余（`running` / `completed` / `superseded`）只列一行；展开的只有**执行器说**一行
（判定退休后没有"已做到 / 还缺"了，见 §11.2）。

> ⚠️ **目前是全量注入**（用户确认）。台账变长到撑上下文时，可改成只注入活跃的。
> **没有 Task 时完全不注入**（闲聊轮次里主 agent 上下文里没有这段）。

> 📌 **多待办 / 待办过期（TTL）尚未处理** —— 现在没有"这条待答挂了多久、要不要作废"的机制。见 §9.5。

#### 4.5.4 `finalize` —— **透传**（不再是"判断问没问出去"）

```python
waiting = [t for t in tasks if t["stage"] == "waiting_for_input"]
if not waiting: return {}
block = "\n\n".join(t["report"] for t in waiting)
return {"messages": [AIMessage(content=block)], "log": [...]}   # ← 无条件
```

> 🔴 **这里原来是 LLM 判断**（`_which_unasked`：问"主 agent 问出去了吗"，没问出去才补）。
> **已删除** —— 用户 2026-10-29：*"能用代码用机制保证的 一定不要用 llm 自行决策"*。
>
> 那个判断**两头都会错**：判"问出去了"其实没问 → **问题静默丢失**；
> 判"没问出去"其实问了 → 用户看到重复。而且它让"问题会不会到用户手上"**依赖 LLM**，
> 而这是平台该保证的事。
>
> **现在的分工**：
> - **保证**（代码）：有待答就原样贴出去，无条件
> - **礼貌**（提示词）：`prepare` 会告诉主 agent"平台负责转达，你不用重复问" ——
>   它照做了就没有重复；没照做也只是重复一句，**不影响不丢**

> ⚠️ **产物路径不在这里贴** —— 那条信息顺着 `delegate` 的返回走（`agent.render_receipt` 的
> 【产出的产物】）：
> 路径是 `write_artifact` 的返回里就有的，平台把它**顺着原路带上去**就够了，不需要另起一套注入。
>
> 🔴 **但 `feed` 那条路没有回执**（`Task.run_by`）—— 所以投递重跑之后，主 agent 拿到路径的
> **唯一入口**是 `list_artifacts`。2026-11-04 日志定位：那个入口当时**不给路径**，于是它报给
> 用户的是**自己编的** `art_001.md`（真实文件叫 `art_001_荷花-教案.md`）。现在
> `artifact_index_lines` 带路径（那一层是**按需**的，台账照旧只放 ID）。

### 4.7 可观测性：**agent 在干嘛，全程看得见**

> 用户（MVP 原型的设计与实现者，2026-10-30）：*"我需要知道主 agent 在干嘛 subagent 在干嘛
> ……**越多越好**，而不是看到一个 loading。"*

**能看到什么，取决于挂在哪一层**：

| 层 | 能看到 | 谁提供 |
|---|---|---|
| **图（super-step）** | 每步：模型调用完 → 决定了什么；工具跑完 → 返回了什么 | `trace.stream_agent` 的 `values` 那一支 |
| **LLM（token）** | 模型**正在写**的每一个字 | 同一个函数的 `messages` 那一支 |
| **工具内部** | 工具自己的日志（`trace.note`） | 各工具 |

**两层都在 `trace.stream_agent()` 里**（`graph.node_agent` 和 `executor.run_task` 共用）：

```python
for mode, payload in graph.stream(state, config, stream_mode=["values", "messages"]):
    if mode == "messages":   # ← 逐字：攒到换行就写一行日志
        ...write(f"[{ts}] ⟨生成·{who}⟩ {line}")
    else:
        yield payload        # ← 每个 super-step 的完整 state，调用方拿去做逐步 dump
```

**为什么必须这么干**（实测，不是推测）：

| | 静默占比（同一条 case `s01b`） |
|---|---|
| 原来：`invoke` 跑完整个循环才 dump | **80–92%**，最大一段 **336 秒**（一次真实 PBL 会话） |
| 逐 super-step dump | 降到"一次 LLM 调用"，最大仍有 **123 秒** |
| **+ 逐字流式** | **0%** |

> 📌 **黑屏的代价**：用户分不清"在干活"还是"卡住了"。实测就发生过 ——
> 用户看到 336 秒没动静，以为进程卡死（`discussion-log` 第二十五次）。

### 🔴 铁律：**交接处的每一跳都要看得见**

> 用户 2026-10-30：*"一定要清晰准确打印**涉及上下文交接的所有地方** ——
> 因为这些往往是**影响 agent 执行优劣最关键的地方**，而且**上下文极其敏感**，
> 往往交接的东西**多一些或者少一些、引导有些区别，决策结果大大不同**。"*

**为什么**：这套系统的行为几乎全由"喂给 LLM 的上下文"决定 ——
交接多了（噪音）或少了（信息不足）、措辞差一点，**同一个模型会走出完全不同的路**。
所以交接处是**最该被看见**的地方。

**两条硬规矩**：

1. **交接内容不许省** —— 判据是"**全文另有出处才省**"：
   `write_artifact(content=…)` 正文另有产物文件 → 省成 `<N字>`；
   `delegate(task=…)` **就是交接本身** → **一个字不省**。
   ⚠️ 踩过两次：`brief_args` 按"超过 120 字就省"一刀切，把 `task` 压成了 `<220字>`；
   显示层又砍了一刀 `args[:300]`。
2. **结构化的东西要"解开"再打**，不要甩裸 JSON ——
   决策记录的 `{"can_answer":…,"answer":…}` 要打成人话（前提 → 问题 → 结果 → 下一步）。
   ⚠️ 流式改动一度把裸 JSON 也流了出来（重复且不可读）。

**交接处清单**（**加机制时顺着它走一遍，别漏**）：

| 交接 | 从 → 到 | 打在哪 |
|---|---|---|
| 用户输入 | 用户 → 主 agent | 顶格（正文层） |
| **台账注入** | 平台 → 主 agent | `📥 INJECT`（Task 状态 / 执行器原话） |
| **派发** | 主 agent → 执行器 | `🔧 TOOL`（**`task` 全文 + `artifacts` 引用**） |
| **交接书** | 平台 → 执行器 | `📥 INJECT`（【任务】【用户原话】【问答经过】【可读产物】） |
| 执行器产出 | 执行器 → 平台 | `🔙 RETURN` + `🚀 RUN`（产物 ID / 报告） |
| **申报要信息** | 执行器 → 平台 | `ask_user` 的工具调用（参数里的原话） |
| **试答** | 平台 → 主 agent | `🧭 DECIDE`（前提 / 问题 / 结果 / 下一步） |
| 产物路径 | 平台 → 主 agent | `🔙 RETURN`（`文件：art_001 → <路径>`）＋ `list_artifacts`（**`feed` 那趟没有回执，只有这条路**） |
| **待答透传** | 平台 → 用户 | `💬 ASK` |
| 主 agent 回复 | → 用户 | 顶格（正文层） |

**三个实现上的坑**（都踩过）：

1. **日志是按行读的** —— 逐字写进去 CLI 也看不见（没有换行）。所以攒到**换行**才写一行。
2. **`render_message` 对 AI 的话只写头部** —— 正文已经流过了，再写一遍就是日志两份、终端两份。
   ⚠️ 这条依赖一个**不变量**：**所有 `AIMessage` 都从 `stream_agent` 流过**。改调用点时记得。
3. **`node='tools'` 是「工具内部的 LLM 调用」** —— 实测：试答跑在 `delegate` 这个工具**里面**，
   却被**外层**的 stream 捕获。不标出来的话，一段结构化 JSON 会被当成"主 agent 在说话"。
   现在标成 `⟨生成·主 agent·工具内⟩`，CLI 走**机制层**（暗灰）而不是正文层。

## 五、关键机制详解

### 5.1 三态（**由结构定**）

**核心**：平台**不判质量**，只算三件**它看得见的**结构事实（`executor._structural_status`）：

```
run_task 内部循环（最多 3 轮）
  ① 执行器干活
  ② 按**结构**定：completed / waiting_for_input / incomplete
       waiting_for_input（调了 `ask_user`）→ 出口 → 试答 → 转用户
       completed（交了产物）              → 出口（"够不够"由主 agent 判）
       incomplete（都没有）               → 推回去继续 → 推满 3 轮交给主 agent
```

> 🔴 **判定（一次 LLM 调用）2026-11-05 退休**，见 §11.2 —— 那之前是它回答"任务完成了没"。

**"产物库非空"为什么不够**（评审人 C2，**这条仍然成立**）：

| 反例 | 产物库 | 实际 |
|------|--------|------|
| 生成了文件但缺章节 | 非空 | **未完成** |
| 纯分析任务没有文件 | 空 | **可能已完成** |

**所以"够不够"交给主 agent 判**（它派的活、它看得见对话）——
平台**只保证"每一格都有确定的后果"**（交了东西 / 要信息 / 都没有，各有各的下一步），
**不保证"模型一定会走对格"**。

**三条原则在这里交汇**：

1. 平台**只报事实**（交了产物没有 / 申报了没有），**不判**"任务完成了没"—— 那是主 agent 的判断
2. **产物 ID 必须真实存在**（`art_999` 编不出来）—— 见 §4.3.6
3. **模型自报的清单不参与任何判断** —— 见 §10.3

> 🔴 **第 3 条踩过一次**：让模型**自报交付物清单**，拿它去精确匹配 skill 声明的名字 ——
> 模型给名字加了后缀 → 匹配不上 → **误判"教案缺失" → `failed`**，
> 而产物库里明明有 `art_002`。
> **修法：`claimed` 完全不参与判定，只写进日志供对照诊断**（`claimed` 本身后来也删了；
> 现在更彻底：**它说的话整段都不参与判断**，只原样进回执）。

### 5.2 出口限制（不许随便停）

> **执行器没干完活是它的问题，不该转嫁给用户。**

```
incomplete → 推回去继续（最多 3 轮）→ 推满仍不行 → failed，交给主 agent
```

**实测（注意：这个行为变过，两份文档各记了一半）** ——
一个"干不成、又不许问"的死局任务：

| 时期 | 表现 | 记录在 |
|------|------|--------|
| **早先**（14:14 / 15:00 / 15:04 的运行） | **推满 3 轮** → `incomplete`，没去烦用户 | `../scenarios.md` S18 |
| **后来**（15:09 之后的运行） | **1–2 轮就说明需要什么** → 走请求信息路径 | 本节 |

行为变化的原因是 `_PLATFORM_RULE` 让执行器"**早说早处理**"（见 §4.3.8）——
它不再硬扛到轮次上限，而是早点把缺什么说清楚。**这是好事**（少烧 token、少一轮往返）。

> ⚠️ **但它的代价要看清**：§5.2 的立意是「**执行器没干完不该转嫁给用户**」——
> 而死局任务现在**会经主 agent 触达用户**。也就是说，
> **这个立意在新行为下并未完全达成**，是"早说早处理"换来的。
> 这属于**已知取舍**，不是 bug；但别以为死局一定不会打扰用户。

### 5.3 信息交接链（用户原则 ①）

**交接点全表**（**13 跳，逐跳的精确内容见 `architecture-diagram.md` §三**）：

| # | 交接 | 内容 | 状态 |
|---|------|------|------|
| ① | 用户 → 图 | 原话（不加工） | ✅ |
| ② | 平台 → 主 agent（台账） | 每个 Task 一行 + 未了结的展开 `report` + 提示句 | ✅ |
| ③ | 主 agent → 平台（派发） | `skill_name` / `task` / `artifacts[]` | ✅ |
| ④ | 平台 → 执行器（交接书） | 【任务】【用户原话】【问答经过】【已产出产物】【可读产物】【续跑提示】 | ✅ |
| ⑤ | 执行器 → 产物库 | 产物 7 字段（含落盘 `path`） | ✅ |
| ⑥ | 执行器 → 平台（申报要信息） | `ask_user` 的参数 —— **它要什么**（原话） | ✅ |
| ⑦ | 平台 → 平台（三态） | 按结构算：申报 / 交了产物 / 都没有 | ✅ |
| ⑧ | 平台 → 执行器（推回去） | 结构事实（既没交付、也没申报）＋ 两条出路 | ✅ |
| ⑨ | 平台 → 主 agent（试答） | 任务 + **它要的信息** + 执行器原话 + **全部消息（全文，不截）** | ✅ |
| ⑩ | 平台 → 主 agent（工具返回） | 七个出口都走 `render_receipt`（**形式化 ＋ 不截断**） | ✅ |
| ⑪ | 平台 → 用户（透传） | 执行器原话，**无条件** | ✅ |
| ⑫ | 平台 → 执行器（答复投递） | 原话 + **累积的历次答复**（同一份交接书） | ✅ |
| ⑬ | **决策是否结构化**（能不能被代码用） | 剩下的 LLM 决策（试答）走 `with_structured_output`；**三态不再是 LLM 决策**（由结构定） | ✅ |

**这条链上实测踩过三次**（**判定时代**），全是同一类错 ——「**信息在内部产出了，但需要它的地方看不到**」：

| # | 缺什么 | 后果 |
|---|--------|------|
| 1 | 判定提示词没带 `instructions` | "按任务要求判断"是空话 |
| 2 | 判定提示词没带 `given` | 明明给了"第1课时"，判定说"没询问用户课时信息" → 误判成 `waiting_for_input` |
| 3 | `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道缺什么 → 回执里的【已做到】【还缺】就是为它加的 |

> 📌 **（历史）后两条随判定退休作废**（那两个字段没了）；**第 1 条那条教训留着** ——
> 试答同样只看得见 prompt 里的东西（见 §4.4 的 `_ask_main`）。

> **通用检查动作**：每加一个机制，顺着信息流走一遍——
> **产出它的环节 → 需要它的环节，中间断了吗？**

### 5.4 Task 生命周期（5 态）

```
running ──┬─→ completed          交了产物
          ├─→ waiting_for_input  调了 ask_user（等用户答复）
          ├─→ failed             推满 3 轮仍 incomplete
          └─→ superseded         同技能被重新委派（不用管了）
```

**与 `ExecOutcome.status`（三态）的关系**：前三个**同名**，唯一映射 `incomplete → failed`；
三态本身**由结构定**（§5.1），不是谁判的。

#### 🔴 四条语义区分（实现时的防错清单）

这四个"不等于"是 D1 的动机所在，写代码时最容易混：

| 不要混 | 说明 |
|--------|------|
| `waiting_for_input` **≠** Graph 运行失败 | 前者是**正常状态** —— 图跑得好好的 |
| `completed` **≠** 任务已经完成 | 它只表示"**交了产物**"这个事实 —— "够不够"由**主 agent 判** |
| `failed` **≠** 模型返回了错误字符串 | 它的定义是"推满 3 轮仍**既没交产物、也没申报要信息**" |
| **某个 Sub Agent 执行完成 ≠ Task 已经完成** | 执行器"跑完了"和"干完了"是两回事（所以平台只报结构事实） |

**暂未实现的三个**（记清了为什么、什么时候该做）：

| 状态 | 为什么现在不做 | 什么时候该做 |
|------|--------------|------------|
| `pending` | 建 Task 就立刻派发，没有"创建了还没跑"的窗口 | 做「计划-执行分离」时 |
| `waiting_for_dependency` | `delegate` 是**同步**的，依赖在主 agent 循环里天然解决 | 做「异步委派」时 |
| `cancelled` | 要给主 agent 新工具，场景**尚未实测到** | 真遇到时 |

### 5.5 上下文隔离

**落点**：产物正文只在产物库，主 agent 只拿 ID + 摘要。

**实测数据**：

| 场景 | 主 agent 上下文 | 产物库正文 | 比 |
|------|---------------|-----------|-----|
| 3 技能（轻量内容） | ~1500 字 | ~8000 字 | 5-13 倍 |
| **48k 字 HTML 课件** | **~2600 字** | 48,873 字 | **~19 倍** |

**隔离靠三条纪律**：
1. 执行器只回 `(产物ID, 报告)`
2. `delegate` 只把 ID + 摘要给主 agent
3. **主 agent 不把正文搬进回复**（系统提示的"硬要求"）

#### 🔴 为什么不走 `interrupt()` —— 完整成本清单

`sx-agent` 里这条路的代码是**半开的**：挂起（`tools_core.py` 的 `answer = interrupt(payload)`）、
传播（`graph.py` 的 `except GraphInterrupt: raise`）、恢复（`stream.py` 的
`if pending: return Command(resume=...)`）—— **三段全都写好了，只差工具没绑给模型**。

所以实施者最自然的动作就是"**把它接回去**"。接回去要付这些代价：

| # | 代价 | 说明 |
|---|------|------|
| 1 | **悬空 `tool_call` → 上游 API 400** | `interrupt()` 在**工具**里调用时，带 `tool_call` 的 AIMessage 已产生、`ToolMessage` 还没产生 → 挂起时**悬空** → 后续工具循环把它重新送进 LLM 输入 → `insufficient tool messages following tool_calls`。**项目已踩过**，也是当初关掉 HITL 的原因之一 |
| 2 | **传了 `config` 会静默吞掉挂起** | 实验 01–05 的决定性结论：唯一决定成败的变量是「dispatch 包装是否给 subagent 传 `config`」。**传了就静默吞掉** —— 裸 `checkpointer=True` 会 RuntimeError，但**套壳之后是静默的** |
| 3 | **包装层必须逐层显式透传** | `interrupt()` 是**返回值**、不是"异常穿透"。每层包装都要显式处理，漏一层就没了 |
| 4 | **节点会从头重跑 → 副作用必须幂等** | 子图作为函数调用时，父节点与子节点**都会从头重跑** |
| 5 | **五条铁律** | 裸 `try/except` 会吞异常 · resume 值**按索引匹配**（多中断下极易错位） · 不可传复杂对象 · 之前节点的副作用必须幂等 · **禁止 `while True` + `interrupt` 校验循环**（指数级重跑） |
| 6 | **子图持久化三模式的硬限制** | 见 §8.5 |

**不是"interrupt 不好"，是它要解决的问题我们已经用别的方式解决了**：

- **"提问走向不确定"** → 执行器**从不直接问用户**（§2.1），没有"答给谁"的歧义
- **"挂起恢复"** → `Task.stage` 由**代码**写，恢复是**纯代码查表**，LLM 不参与

> 📌 **实测数据（被放弃的收益，别误读成"interrupt 有问题"）**：
> `interrupt` 模式**跑得通**，而且主上下文更小 ——
> **143 字 vs message 模式 333 字**（问题在 interrupt 载荷里，不进消息历史），
> 耗时基本持平（1m20s vs 1m22s）。它只是在这个架构里**没必要**。

> 🔑 **一个可直接搬的结构性改进**：如果将来确实需要 HITL 提问，
> **把提问做成「图节点」而不是「工具」** —— 节点里调 `interrupt()` 不产生 `tool_call`，
> 于是**压根没有"未配对的 ToolMessage"**，代价 1 从根上消失。

### 8.5 旧路径的机制结论（备查）

下面两条在推演中自述"**仍然有效**" —— 它们解释了 **P2 为什么是「间歇性」的**。

**① 子图持久化的三种模式**

| 模式 | 语义 | 限制 |
|------|------|------|
| `checkpointer=None`（默认） | 每次调用一个全新状态 | — |
| `checkpointer=True`（**per-thread**） | 同一 thread 内**累积** | ⚠️ **同一个 subgraph 不能被重复调用** → 一个会话里一个 skill 只能有**一个活跃任务实例**；不同 subgraph 的同名节点会**命名空间冲突** |
| `checkpointer=False` | 无状态 | — |

**② 命名空间按「调用顺序」分配**

> *"reordering your calls can mix up which subgraph loads which state"*

**这就是 P2「间歇性」的唯一解释** —— 调用顺序一变，就加载到别的 / 空的 state。
它同时也是评估「subagent 该做成节点、还是节点内调用」的依据。

`sx-agent` 现状用的正是 `checkpointer=True`（per-thread），
上面那两个硬限制**直接适用** —— 换持久化 checkpointer 时要一并处理（§8.3 第 2 条）。

### 8.6 sx-agent 现状核查（改之前先看这些）

| 项 | 现状 | 影响 |
|---|---|---|
| **HITL 代码** | 挂起 / 传播 / 恢复**三段完好**，只差工具没绑定 | 落地成本评估的关键 —— 是"**能力已存在、只差绑定**"，不是"要重写一套 HITL" |
| **提问提示词** | **两处**在指示模型把问题写进回复正文：`agent_builder.py` 的平台约定、`engine.py` 的参数占位符 | **这正是 P3 的直接来源** |
| **关闭 HITL 的三条理由** | ① 「单 agent 架构下没作用」**不成立** —— 正文提问没有挂起点，正是 P1/P2/P3 的总根源；② 「同一问题被问两遍」成立，但成因是**双通道同时开着**，解法是只留一个；③ 「多个挂起中断无法用单一回答恢复」**已被证伪** —— `Command(resume={interrupt_id: value})` 就是官方为此设计的 | ⚠️ 理由 ③ 是写在项目自己文档里的**错误结论**，不纠正会继续据此否掉批量提问类设计 |
| **前端 `pendingSkill`** | 只存在内存 | 刷新即丢，与"Task 跨轮存活"配套不上 |
| **现状配置** | 父图 memory checkpointer · 子图 `checkpointer=True`（per-thread）· interrupt 调了但不挂起 | 见 §8.5 |

> ⚠️ **一处内部矛盾，落地前必须定**：`sx-agent` 自己的文档里，
> §8.4 的解法写的是"**留工具、删正文指令**"，而 §8.6 又明确"**不要删该约定**"。
> 两者**相反**，而本方案对此原先沉默 —— 实施者二选一都可能改错。
>
> **本方案的立场**：正文提问的提示词是 P3 的成因，**应当处理**；
> 但**不要在执行器里重新绑定 `interrupt()` 工具**（理由见 §8.4）。
> 具体改哪一处、怎么改，落地时单独定。

**落地前的自查清单**（对应 §6.5 的必查项）：

1. 同一会话的 `thread_id` 是否**跨轮稳定**？（不稳定 → Task / 台账 / supersede 全失效，**且不报错**）
2. subagent 是 `add_node` 还是**节点内调用**？（决定命名空间行为，见 §8.5）
3. 有没有**裸 `try/except` 包住 `interrupt`**？（会吞掉挂起信号）
4. memory checkpointer 的实例**活多久**？（多 worker 下是否共享）
5. 有没有**并行调用同一个 per-thread subagent**？（per-thread 的硬限制）

### 9.6 软 → 硬：哪些能转、哪些不能（2026-11-02 审计）

**判据（原则 ⑤）**：软的里面要**分成两类看** ——

| 类别 | 特征 | 结论 |
|---|---|---|
| **搬运信息**的软 | 信息**本来就在系统里**，只是让 LLM 转了一手 | 🔴 **都能转硬** —— 转述只会有损失 |
| **语义判断**的软 | 确实需要"理解"才能定 | 转不了，但可以**把其中机械可判的部分摘出去** |

#### A. 软判断清单（运行期）—— **S1 / S5 已随判定退休**（2026-11-05）

| # | 软判断 | 判什么 | 类别 |
|---|---|---|---|
| ~~**S1**~~ | ~~`executor._judge` 三态判定~~ | ~~任务完成没 / 在不在要信息~~ | **已删** —— 两个语义被拆开：**要信息改成执行器自己申报**（`ask_user`，结构）、"完成没"由**主 agent** 判（平台不判） |
| **S2** | `agent._ask_main` 试答 | 我的上下文里有没有它缺的信息 | 语义 |
| **S3** | 主 agent 决策循环 | ①要不要委派 ②**派给哪个技能** ③**产出范围** ④**`task` 怎么写** ⑤回复怎么组织 | 混合（②③④⑤ 都含"搬运"成分） |
| **S4** | 执行器决策循环 | ①怎么干 ②要不要落库 ③**缺什么信息**（调 `ask_user` 申报） | 语义 |

**评测期**另有 4 条软 rubric（`no_repeat_question` / `artifact_derives_from_source` /
`reply_is_summary` / `artifact_is_complete`）。

#### B. 可转硬的（按价值排序）

**B1 🔴 派给哪个技能 + 产出范围（S3②③）—— 最大的一处，而且需求本来就要求它硬**

需求 **F2** 白纸黑字写着"skill 由**用户在 UI 中显式选中**"，而**代码里根本没有这回事**：
原型没有 UI，现在是主 agent 从系统提示的能力清单里**自己挑**。
转硬 = 入口显式选中 → 平台按选中的派发。
**连带收益**：产出范围（"做几样"）**自动收窄** —— 选了几个就做几个，S3③ 这条软判断直接消失。
**不冲突**：F6/F7 要的"能直接答"仍在（**没选中技能**的轮次就是闲聊/追问）。

**B2 ~~🔴 正文交付的转达~~（S3⑤ 的一块）—— ❌ 2026-11-02 决定：不做**

当初的理由是"回执写着'请原样转达'，那是**提示词在求它**；而待答那一路早就是平台无条件贴，
两路不对称 → 转硬"。

**做完调研后否掉了**（完整理由见 **§0.7**）：

- 🔴 **四家参考实现没有一家做**（deepagents 明文不给 + 两道 UI 硬过滤；另外三家的直送全走**旁路 UI**）
- 实测**没复现**它要治的问题 —— `r2` 强制委派那次，块 **2086 字逐字**到用户手上
- 真技能那次（2026-11-02）也是**逐字**（1602 字）
- 它治的是"过手的保真"，而按 §0.7 的立场，**这条路本来就不保证** —— 给它打补丁等于**自己造机制**

> 📌 **顺带纠正**：`_last_ai_text` 只取最后一条**不是 bug** —— 四家全部这么做（见 §0.7）。

**B3 🔴 `task` 里的用户事实（S3④）** —— ✅ **已实现（2026-11-02）**：平台搬原话，分两层（渐进式披露）

**问题**：见 §9.2 —— 首次派发时执行器看到的"任务"**100% 是主 agent 的转述**，实测有"加料"。
**修法**：平台把用户原话**硬搬**进交接书。但**不是全量塞** ——
那就是"一上来全加载"，正是 2026-10-30 被否掉的做法。**按渐进式披露分两层**：

| 层 | 露出什么 | 在哪 |
|---|---|---|
| **L1 清单** | 每轮一行：`第 N 轮（M 字）：{开头 40 字}…` | 交接书【用户原话】段，**常驻** |
| **L2 全文** | 某一轮的**原话全文** | 新工具 `read_user_turn(n)`（加进**执行器**工具箱） |

**为什么这样分**：用户消息多数很短（几十字），但**可能粘贴长文**（改教案那种）。
清单常驻让执行器**知道"用户说过什么、哪一轮值得看"**，全文按需取 ——
和技能包（能力清单 → `read_skill` → `read_skill_file`）、产物库（清单 → `read_artifact`）
**同一套做法**。

**清单天然有界** —— 所以"取全部还是最近 N 条"这个问题**自动消解**：
一行几十字，50 轮也就 1500 字；真到撑不下的量级再加总量上限 + 显式标注。

**（历史）判定怎么办**：判定退休前**没有工具循环**（单次结构化调用），它拿到的是同一份**清单**
（`briefing` 就是判定输入之一）—— 那时靠"开头 40 字通常已含最关键约束"来撑。
📌 **2026-11-05 判定退休**：现在读这份清单的只有**执行器**，它手里有 `read_user_turn`（按需取全文）。

**冲突规则**（写死在段里）：【用户原话】是**事实**，【任务】是**要求**；**事实冲突时以原话为准**。

**🔴 每段都标来源**（用户 2026-11-02：*"我们只需要从机制上保证数据传递正确，
**标记上啥是模型交代的、啥是用户说的就行**"*）——
**平台不拦着主 agent 加料**（那是它的活，也拦不住），但**必须让下游知道每句话是谁说的**，
否则模型补的东西会被当成用户的事实。实测就是这么错的：执行器把主 agent 编的
"三年级/四年级" 说成了"**您写的是**…"。标法见 `architecture-diagram.md` §3.2.2 那张表。

**快照，不现取**：在 `delegate` 建 Task 时把原话快照进 Task（`user_turns`）——
① 答复投递那条路**自动也带上** ② 与 `answers` **天然去重**（快照是派发前、answers 是派发后）。

**这一步不治"主 agent 加料"**：原话是给**下游**（执行器）看的，主 agent 该怎么转述还怎么转述 ——
它治的是**加料的后果**（执行器手里有原始事实可对照）。要治加料本身，得上第二档：
主 agent 只**选轮次**，平台按引用搬原话 —— **LLM 只做选择，代码做搬运**。
（📌 **第二档没做，`based_on_turns` 2026-11-03 整个去掉了** —— 用户原话现在只有**索引**一种形状，
全文由读的人按需取，见 `architecture-diagram.md` §3.2.2。）

**B4 ~~🟡 产物完整性的机械部分（S1 的一块）~~ —— ❌ 随判定退休作废（2026-11-05）**

原来的想法：在 `_judge` **之前**跑一遍确定性扫描（作者占位符 / 声明 html 却没头没尾）→
直接判 `incomplete` 并写进 `missing`，把判定收窄到"机械查不出来的部分"。

🔴 **对象没了**：判定退休后运行期**不再判质量**（平台只说"交了东西"），也就没有"在 `_judge` 之前"
这一步。**"产物写完了没有"现在整个在评测层**（软 rubric `artifact_is_complete`，
`artifact_no_placeholder` 那条代码侧找词断言 **2026-11-05 删** —— 断模型吐的字等于没效果）。
**平台不判产物质量**，这条立场写死在 §0.7 与 §11.2。

**B5 🟡 评测期 `reply_is_summary` 的硬近似**

现在是软 rubric（问"回复有没有搬运产物正文"）。可以用**最长公共子串**做机械近似
（回复里出现产物正文的连续 N 字 → 疑似搬运），当**辅助证据**，不替换。

#### C. **不该**转硬的（免得走回头路）

| 不转什么 | 为什么 |
|---|---|
| 技能"缺什么参数"（S4③） | 转硬 = 要求 skill 声明 `params` —— **已被砍**（约束作者 + 实测模型会改写参数名、算错并集）。**正解是写在 `instructions` 里**（"你需要知道 X"） |
| 交付形态声明（S4②） | 同上，`deliverables` 已砍；**正解是平台自己的交付契约** —— `_PLATFORM_RULE` 就写着"要交付成文件的内容，调用 `write_artifact`"。再加一个 per-skill 的 `delivers` 就是**同一条规矩的第二份拷贝** |
| 上下文超线判红 | F17：只记录 + 喊一声（**读产物是主 agent 的合法能力**，拿它判红是罚一个合法能力） |
| "用户是不是在回答" | **已删**（2026-10-29）—— 这是"软转硬"的**成功先例**：不判断，原话直接投递 |
| 同技能旧待答要不要取代 | **已收窄**：只取代 `failed`（F7）—— 又一个"别让代码替用户做语义判断"的先例 |

## 十、设计原则（贯穿全案）

### 10.1 五条**设计**原则

| # | 原则 | 落地 |
|---|------|------|
| **①** | **理解要柔性，状态要硬** | 平台不抽参数（原话原样传）；但状态由代码写、分支穷举 |
| **②** | **能靠既有事实判定的，不要发明协议** | 删掉了 `finish` / `status` / `deliverables` / `criteria` |
| **③** | **能靠代码算的，不要交给 LLM；能靠 schema 约束的，不要靠提示词** | LLM 决策走 `with_structured_output`（§4.2）；**三态干脆不是 LLM 决策了**（由结构定，§5.1）；实测模型会漏字段、会改写参数名 |
| **④** | **平台少约束 skill 作者** | 形式能跑即可，效果由作者迭代。任何**依赖作者配合**的机制都是脆的 —— 作者一句自然语言就能覆盖平台约定 |
| **⑤** | 🔴 **交接靠硬机制，软判断收紧到最紧** | 委托负载由 `render_briefing` **硬拼**（不是主 agent 转述）；要信息由**执行器自己申报**（`ask_user`，不再让 LLM 从文本里认）；推回去 / 试答的提示词由代码拼。**平台主动发起的 LLM 调用只剩试答一处**（其余是两个 agent 自己的循环，见 `architecture-diagram.md` §4.1），且输入**缺一不可**。理由：软判断的效果完全取决于喂给它的上下文 —— **组织上下文是根本，那是代码的活** |

### 10.2 处事原则（8 条 —— 本次推演的工作方式）

> 这几条**不是产品设计**，是"这次怎么把设计做出来"的规矩。
> 它们同样适用于**下一次架构迭代**。

| # | 原则 | 一句话 |
|---|------|-------|
| ① | **批判性审视，不要照办** | 先看业界怎么做，再决定要不要自造 |
| ② | **讨论先行** | 要写代码前，先说清"验什么 / 怎么验 / 预期结论" |
| ③ | **结论必须实测，优先真实模型** | 想当然的结论几乎全被推翻（见 §10.4） |
| ④ | **分支必须闭合** | 分类要覆盖所有情况、互斥、每个都被妥善处理。**靠约定排除的组合，说明该用枚举** |
| ⑤ | **信息交接要说细节 + 决策要结构化** | 产出它的环节 → 需要它的环节，中间不能断（§5.3） |
| ⑥ | **平台少约束作者** | 同 §10.1 ④ |
| ⑦ | **保留讨论历史，不删** | 过期结论标"已被 §X 取代"+ 一句为什么被推翻。**未标记的过期内容比没有更糟** |
| ⑧ | **场景沉淀成回归集** | 每次架构迭代回来跑，防"修好一个、弄坏一个"（实测：去掉 `load_skill` 修好 S12，立刻暴露 S13、S14） |

### 10.3 一条贯穿的观察：「**模型的话是线索，不是事实**」

这个坑**踩了三次**，每次都是同一件事 —— **拿模型说的话当事实用**：

| # | 场景 | 后果 | 修法 |
|---|------|------|------|
| 1 | 执行器在正文写"教案已完成，请查收" → 判 `completed` | 主 agent 报"已交付"，**用户什么也没拿到** | 原来靠判定规则 2（"不能凭声称完成"）；**现在更彻底**：平台**只看结构**（交了产物没有）—— 声称完成**不构成交付**（§5.1） |
| 2 | 让模型**自报交付物清单**，拿它去精确匹配 skill 声明的名字 | 模型给名字加了后缀 → 匹配不上 → **误判"教案缺失" → failed**，而产物库里明明有 `art_002` | `claimed` **完全不参与判定**，只写进日志供对照诊断 |
| 3 | 想靠提示词让模型**按格式输出参数名** | 模型把「学科」改写成「科目」 | 用 `with_structured_output` / schema 约束（§10.1 ③） |

> **推论**：凡是"模型的产出"要参与逻辑判断的地方，
> **要么用代码验证它**（产物 ID 必须在产物库里查得到），**要么别用它**。
>
> ⚠️ 这个坑会复发的地方：`sx-agent` 有 `app/skills/validating/` —— 加"交付物核对 / 参数核对"时最容易重犯。

### 10.4 附：被实测推翻的"想当然"

> 📌 带「判定」的几行是**判定时代**的记录（2026-11-05 退休）—— **教训本身仍然成立**：
> 它们说的是"**别让 LLM 去判平台自己能算的事**"，而这正是判定被拿掉的理由。

| 想当然 | 实测 |
|--------|------|
| "criteria 是确定性检查" | 它本质也是 LLM 判断；**自己写的测试 9/9 全过，仍无增量价值**。砍它的理由是"**没必要**"，不是"分数低"（早先记的"4/6 更差"已不可复现 —— 见 §7.1） |
| "有产物就算完成" | 有产物但内容是残次品 → **误判成完成** |
| "出口限制救不了『干了一半就停』" | **救得了** —— 没交产物就没有出口（`completed` 只认产物账） |
| "判定带上 `instructions` 就够了" | 还要带 `given`，否则误判（判定已退休；**这条对试答同样成立**） |
| "`failed` 分支不用带 `progress`/`missing`" | 主 agent 只知道"没做成"，不知道缺什么（那两个字段已随判定删掉） |
| "两个布尔值表达三态没问题" | 4 种组合只有 3 种合法 → **该用枚举**（今天的 `ExecOutcome.status` 就是枚举） |
| "**隐式 else 没问题**" | 试答后重跑只判两种 → `incomplete` 被当成"在请求信息" → **去问用户，P3 复发** |
| "提示词写'符合要求'就行" | 太笼统导致**吹毛求疵**（推 3 轮 4m29s vs 1 轮 1m5s） |
| 🔴 "**把两个问题压进一次判断没关系**"（2026-11-05 新增） | "任务结没结束" 和 "在不在要信息" 是**两个语义**：喂它说的话，礼貌收尾被当成要信息；不喂，真问题被吞 → **根因移除**（判定退休，`ask_user` ＋ 主 agent 判） |
| "模型自报的交付清单可以用来核对" | **不可信**（§10.3 第 2 条） |
| "豆包和 DeepSeek 等价可用" | 豆包在 `response_format` 上**静默失效**，HTML 3/3 空响应（§9.4） |

### 10.5 设计依据 —— 不是我们自己推的

`Skill` / `Task` / `Sub Agent` **三者正交**、**执行器不问用户**、**skill 与 subagent 解耦** ——
这几条**不是本次推演的独创**，是从参考实现里读出来的：

| 来源 | 借鉴了什么 |
|------|-----------|
| **DeepAgents**（`../ref/deepagents`） | subagent 的 `task` 工具 · skills 渐进式加载 · **文件系统作为共享记忆** · **async subagents（后台非阻塞，未拉取）** |
| **Claude Code Skills** | `SKILL.md` 渐进式披露 · **subagent 上下文隔离（子 agent 不能反问用户）** |

**决定性发现**（读 `ref/deepagents` 得到的）：那里的子 agent 是
**ephemeral / stateless / 一次报告 = 纯函数** ——
所以 **P1/P2/P3 在它那里压根不会发生**。
skill 里写"必须先委派给 researcher" → **拆分由 skill 决定、交接靠文件系统**。

> 这也是为什么"**执行器从不直接问用户**"是一条**硬边界**，而不是措辞选择。
>
> 同时说明：这套设计的**新颖部分很少** —— 主要是把业界已验证的结构
> 搬到"需要跨轮交互"的场景上，并补上 `Task` 这一层状态载体。

## 十一、三态怎么来的（**由结构定**）

> 2026-10-29 由 `completion-mechanism.md` 并入；**2026-11-05 重写**（判定退休，见 §11.3）。
> ⚠️ **这一章不写"逐字提示词"副本** —— 真值在代码（下面标了常量名 / 函数名）。
> 副本必然漂移 —— 要改提示词，直接改 `proto/` 里的常量。

### 11.1 执行器干完活之后，平台要回答的三个问题

1. **它交东西了吗？** —— 交了就 `completed`（**平台只说这个事实**，"够不够"由主 agent 判）
2. **它申报要信息了吗？** —— 调了 `ask_user` 就是 `waiting_for_input` → 试答 → 转用户
3. **两样都没有怎么办？** —— `incomplete` → 推回去（nudge 点明两条路）→ 推满 3 轮交给主 agent

**前两问都不需要"理解"**：它们是平台**看得见的**事件（工具调用 ＋ 产物账）。
第三问也不需要：**没有事实就是没有事实**。

### 11.2 三态

| 状态 | 平台**看得见**的结构事实 | 后续 |
|------|------|------|
| `completed` | 交了产物（`write_artifact` 记账） | 交付 —— 回执把交付账摆给主 agent，**"够不够"由它判** |
| `waiting_for_input` | 调了 `ask_user`（申报要信息） | 主 agent 先试答 → 答不上问用户 |
| `incomplete` | 都没有 | 推回去继续；推满 → 交给主 agent |

**闭合性**：交了东西 / 没交且在要信息 / 没交也没要 —— **覆盖所有可能**，
且 `Literal` 类型保证**不存在第四个值**。
**顺序**：申报优先（它可能交了一部分之后卡住 —— 那时该去要信息）。流程见 `architecture-diagram.md` §二。

> 🔴 **`completed` ≠ 任务完成**（用户 2026-11-05）：*"判断任务是否结束 和 普通请求输入
> 是完全不同的语义"* · *"平台保证'**每一格都有确定的后果**'，不保证'模型一定会走对格'"*。

### 11.3 🔴 **判定退休**（2026-11-05）—— 为什么拿掉、拿掉了什么

**原来**：执行器**每一轮**之后，平台**再叫一次 LLM**（"判定"），从"产物正文 ＋ 执行器说的话"里
一起判三态，输出 `_Judgement{status, progress, missing, reason}`；`progress` / `missing`
落进 `Task`，再渲染进交接书 / 台账 / 回执 / 推回去。

**为什么拿掉** —— **根因**：两个语义不同的问题被压进了**同一次判断**，
于是"要不要把它说的话喂给判定"成了**死结**：

- **喂了** → 礼貌收尾（"……需要调整吗？"）被当成"明确请求信息" ✗（实测：产物其实已完整交付）
- **不喂** → 真问题被吞 ✗

**现在两条机制各管一件事**：

| | 是什么 | 谁产出 | 平台拿它干什么 |
|---|---|---|---|
| **执行器要信息** | 一个**事件** | **执行器自己申报**（`ask_user`） | 试答 → 答不上把**参数里那句原话**转用户 |
| **任务完成没** | 一个**判断** | **主 agent**（它派的活） | 它决定下一步；**平台不判** |

**退休时一起消失的**：判定那个模块**整个文件**（schema / 判定规则 / 材料取材 /
保头保尾截断 / `need_more` 那个"先标记、未来可能做"的 TODO）· `run_task` 里那次 LLM 调用 ·
`progress` / `missing` **整条链**（`ExecOutcome` / `Task` / 交接书 / 台账 / 回执 / 词汇表）·
回执里"`completed` 但没产物"那一档（正文交付本来就是反模式，见 §0.7）。

**当时的实测与教训**留档在 §4.3.3 那张表 ＋ `handoff-audit.md` §九。

> 🔴 **通用检查动作**（留着）：每加一个机制，顺着信息流走一遍 ——
> **产出它的环节 → 需要它的环节，中间断了吗？**（这个坑踩过三次）

### 11.4 实测：五种判定提示词对比（**历史** —— 判定已退休）

`experiments/debug_judge_variants.py`（**依赖已删的 API，跑不起来了**），
6 个用例（完整产出 / 缺章节 / 在问用户 / 有产物但残次品 / 纯分析无产物但完成 / 什么都没干）：

| 变体 | 全对 |
|------|------|
| A 只给产出 | 3/6 |
| B 产出 + `instructions` | 5/6 |
| C 产出 + `completion_criteria` | **4/6** |
| E 产出 + instructions + 反省式 | 6/6 |
| **F 用户拟的模板（三态 + 明确规则）** | **6/6** ✅ 生产用这个 |

**结论**：`completion_criteria`（把要求拆成字段声明）**反而最差** —— 要求本来就在
`instructions` 里，再抄一遍是重复，还会把"必须包含 X"硬套到不该套的任务上。
**"带 instructions + 明确规则"就够了。**

> ⚠️ 单次采样的分数会漂（重跑过一次，A/B/C/E 全变成 5/6）——**别拿单个数字当论据**。

### 11.5 踩过的坑（**历史** —— 前三条随判定退休作废，后三条仍然成立）

| 坑 | 后果 | 修法 |
|---|---|---|
| 判定提示词没带 `instructions` | "按任务要求判断"是空话 | 带上 |
| 判定提示词没带交接书 | 把"已经给过的信息"当成"没问" → 误判成在请求信息 | 带上 |
| `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道该重派还是该问 | 带上（回执的【已做到】【还缺】）—— 📌 两个字段 2026-11-05 删 |
| 用两个布尔表达三态 | 4 种组合只有 3 种合法，"矛盾组合"只能靠约定排除 | **改用枚举**（今天的 `ExecOutcome.status`） |
| 隐式 else | 试答后重跑有三种结果只判了两种 → `incomplete` 被当成"在请求信息"，跑去问用户 | 显式穷举 |
| 措辞太笼统（"符合上面的要求吗"） | 模型吹毛求疵，推 3 轮跑了 4m29s | 规则**列举具体失败形态**（占位/待补充/半成品），同任务降到 1 轮 1m5s |
| 🔴 **两个语义压进一次判断** | 喂它说的话 → 礼貌收尾被当成要信息；不喂 → 真问题被吞（**死结**） | **根因移除**：要信息改成**执行器自己申报**（`ask_user`），"完成没"由**主 agent** 判（2026-11-05） |

### 11.6 可调优点（**现在调什么**）

**现在**的可调优点只有三处 —— 见 §4.3.8（执行器缺信息怎么表达 / 推回去怎么说 / 最多推几轮）。
**调优方式**：改完跑 `experiments/debug_exit.py`（出口行为），**别凭感觉**。

**（历史）判定时代的可调优点**：

| 位置 | 作用 | 调优方向 |
|------|------|---------|
| `_JUDGE_RULES` 规则 1 | 有产物时怎么算完成 | 失败形态可以继续补（如"只有标题没有正文"） |
| `_JUDGE_RULES` 规则 2 | 无产物时怎么算完成 | 确认性文字的例子可以补 |
| `_JUDGE_RULES` 规则 3 | 什么算"请求信息" | **这条最敏感**——松了会把"找借口"当请求，紧了会把真请求当没做完 |
| `_PLATFORM_RULE` | 执行器缺信息时的行为 | 影响它多早说明需要什么（**这条今天还在**） |
| `_nudge_text` | 推回去时说什么 | 影响它能不能"接着做"而不是"从头来"（**今天还在**，见 §4.3.8） |
| `MAX_REACT_ROUNDS` | 推几轮 | 现在 3；调大更执着但更烧 token（**今天还在**） |
| `JUDGE_ITEM_BUDGET` | 判定能看到多少字 | 现在 4000（800 时会把长产物误判成半成品）—— 📌 随判定删 |
