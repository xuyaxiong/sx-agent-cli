#### ① 批判性审视，不要照办

> "我一直在跟你说场景、说需求，我可能提出了某些见解或方案，但那都是**我一家之言**，
> 你应该批判性地看待——某些做法是不是常规通用做法？有没有最佳实践？
> 是不是重复造轮子？是不是过度设计？……如果你一味顺着我说，很容易出现偏差。"

**执行顺序很重要：先读参考实现，再决定要不要自造。** 不要用推理替代读源码。

> **本次教训**：`deepagents` 就在本地，我却在没读它的情况下自造了一整套方案——
> 读完才发现其中一半是过度设计（`deliverables` 清单、`status` 枚举、`finish` 工具）。

---

#### ② 讨论先行，测试要有预案

> "我抛出问题或者见解，你**先回复我跟我讨论**；如果需要测试，你要说清楚
> **想验证什么、准备怎么验证、结论预期是什么**，**等我确认再写代码**。"

---

#### ③ 结论必须实测，优先真实模型

> "我们在形成结论的时候**必须测试**，而且**最好是真实模型实测**。"

**为什么**：这半天里，**几乎每一条"想当然"的结论都被实测推翻或修正过**：

| 想当然 | 实测结果 |
|--------|---------|
| "criteria 是确定性检查" | **它本质也是 LLM 判断**，而且比不写还差（4/6 vs 6/6） |
| "有产物就算完成" | 实测：有产物但内容是残次品 → **误判成完成**（⚠️ 2026-11-05 判定退休后，"交没交"归**平台按结构说事实**、"够不够"归**主 agent 判** —— 见本行下方注） |
| "出口限制救不了『干了一半就停』" | **救得了** —— 改成问"任务完成了没"就行 |
| "判定提示词带上 instructions 就够了" | 还要带 `given`，否则误判 |
| "两个布尔值表达三态没问题" | 4 种组合只有 3 种合法 → **该用枚举** |
| "提示词写'符合要求'就行" | 太笼统导致**吹毛求疵**（推 3 轮 4m29s vs 1 轮 1m5s） |

**落地方式**：
- 形成结论前先跑一遍，不说"我觉得应该没问题"
- **优先真实模型** —— 假模型能跑通图逻辑，但**行为差异很大**（真模型会"将就着做"、会"吹毛求疵"）
- 结论里要写"实测 N/M 通过"，不能只说"应该行"
- 留测试脚本，改完能重跑

#### ④ 分支必须闭合

> "不管一个问题被我们分成几类，这几个分支，**每个情况我们必须都得讨论**，
> 这样才不会有漏网之鱼。所以对于出口处那几个分支，
> **是否这几个划分是闭合的，是否每个分支都得到了相应的妥善处理**。"

**每设计一组分支，问三个问题**：

1. **闭合吗？** 这些分支加起来，覆盖了所有可能吗？
2. **互斥吗？** 有没有一种情况同时落进两个分支？
3. **每个都被妥善处理了吗？** 有没有"落进 else 但 else 什么也没做"的？

**三种典型的不闭合**（本次审计实测，全踩过）：

| 类型 | 例子 | 修法 |
|------|------|------|
| **用 N 个布尔值表达 M 种状态** | `ExecOutcome` 用 `completed`+`asking_user` 两个布尔表达三态 → 4 种组合只有 3 种合法，**矛盾组合靠约定排除** | **改用枚举**（`Literal`）—— 从类型上闭合 |
| **裸字符串 + 字典 fallback** | `Task.stage` 是 str，`_STAGE_MARK.get(stage, stage)` 兜底 → **拼错字母不报错，静默 fallback** | 用 `Literal` 约束取值 |
| **隐式 else** | "推满轮次"靠循环自然结束，读代码要推理才能确认它被处理了；<br>**更严重的**：主 agent 试答后重跑，结果有三种，但只判了两种——`incomplete` 被当成"在请求信息"，**会去问用户** | **显式写出 `else` 分支** |

> **信号**：发现"靠约定才能排除"的组合，就是该用枚举的信号。

#### ⑤ 信息交接要说细节 + 决策结果要结构化

> "只要涉及到**信息交接、信息转移**的地方，一定要说**更多的细节**，
> 这样大模型用作决策的有效信息更多，得出的结论才更强。"
>
> "**决策的结果最好是结构化的**，这样我们才可以在流程中用代码处理，比如参与逻辑转移判断。"
>
> 什么叫结构化：**Structured Output**（OpenAI `response_format` / LangChain
> `with_structured_output`）——把 JSON Schema 传给模型，**模型原生保证结果符合结构**，
> **不需要靠工具参数去约束**。

**实测踩过的四次，全是违反前半句**（⚠️ 下面第 1、2、3 条讲的是**判定**那次调用 —— 它 2026-11-05 退休了；**教训本身仍然成立**：喂给 LLM 的东西少一样，它就凭空猜）：

| # | 缺什么 | 后果 |
|---|--------|------|
| 1 | 判定提示词没带 `instructions` | "按任务要求判断"是空话 |
| 2 | 判定提示词没带 `given` | 明明给了"第1课时"，判定说"没询问用户课时信息" → 误判 |
| 3 | `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道缺什么 |
| 4 | **答复没带上它回答的那个"问"**（2026-11-02） | 用户答「A」，交接书里就只有 `第 4 轮：A` —— **选项列表不在**，执行器既解读不了、也核对不了主 agent 的转述；而这一段还写着"冲突时以原话为准"，等于把一个**无法解读的片段**标成最高权威 |

> 🔴 **第 4 条的一般形式**：*"交接时上下文一定要清楚，**一问一答**。"*
> 一条信息**脱离了它的语境就不是信息** —— 代词、选项字母、省略句都是这样。
> 平台**不判断**"这句是不是短应答"（那是语义判断），而是**结构上保证成对**：
> 收下答复的那一刻，把**它回答的那句**一起原样截下来（见 `Task.qa` / `user_turns.after`）。

> **推论**：**信息在内部产出了，不代表需要它的地方看得到。**
> 每加一个机制，都要顺着信息流走一遍：
> **产出它的环节 → 需要它的环节，中间断了吗？**

**后半句的反面教材**：早期的 `finish` 工具——**用工具参数传决策**，模型不调，决策就丢了。
现在**所有** LLM 调用点都走 `with_structured_output`（2026-11-05 判定退休后，产品侧只剩**试答**一处，评测层的软 rubric 也是）。

#### ⑥ 产品原则：平台少约束 skill 作者

> "尽量减少对用户的 skill 的强制约束。**形式上流程能跑，至于效果是否好不保证**。
> 用户想要效果好，自然会尝试调整 skill。"

**推论**：**任何依赖作者配合的机制都是脆的**——作者一句自然语言就能覆盖平台约定。
所以平台机制必须建立在**既有事实**（产物落盘没有）上，而不是执行器的声称上。

**分工**（B2 实测后确定）：

| 判断 | 谁负责 |
|------|--------|
| 信息不全时该不该问（**机制**） | 平台提示词 |
| 哪些参数必答、哪些有默认值（**业务**） | **skill 的 `instructions`** |

#### ⑦ 文档维护：保留讨论历史，不要删

> "**讨论的历史不要直接删去，可以更新为过期。**"

**为什么**：
1. **推演过程本身有价值**——它记录了"当初为什么往那个方向走、为什么那是弯路"。删掉就只剩结论，下次会重新踩坑
2. **未标记的过期内容比没有更糟**——读者从文档中段进去会被带偏，而且不知道已被推翻

**本次实测**：主文档 1687 行、17 次讨论，**9 处结论已过期**，
其中 `§8.6 建议改动清单` **给出的行动建议与最终方向完全相反**（它建议"重新绑定 interrupt"，
而最终设计**删掉了 interrupt**）。

**做法**：
- **更新，不删除**：保留原文，在上方加标记
- **标记含三样**：`⚠️/🔴` + "已被 §X 取代" + **一句为什么被推翻**
- **指明权威**：文档开头写清"以哪节为准"
- **危险等级要区分**：一般过期用 `⚠️`；**方向相反的行动建议**用 `🔴` + 逐条说明"哪几条不要做、哪几条仍成立"
- **部分有效的要拆开说**：如 §8.6 整节被推翻，但**第 6 条（换持久化 checkpointer）仍然成立**
- **变更后主动回头扫全文**——不要只往前写

#### ⑧ 场景要沉淀成回归集

> "我之前说的若干场景，你应该**精心准备为测试场景**记下来。
> 这样**每次我们迭代架构设计的时候，就会回来覆盖这些场景**，看能不能满足各种需求。"

**为什么**：架构迭代最容易"**修好一个、弄坏一个**"。

> **本次实测**：去掉 `load_skill` 修好了"主 agent 能自己干活"（S12），
> 却立刻暴露出"隔离失效"（S13）和"重复委派"（S14）。

**做法**：
- 用户口述的场景**当场记**进回归集（说过就散会丢）
- 每条写清四样：**输入 / 期望 / 为什么重要（挂到真实痛点上）/ 当前状态**
- **每次架构改动后主动回来跑一遍**，更新状态表
- **标出"未验证"和"不达标"**，不要只记通过的

**落地**：`scenarios.md`（19 条）

#### ⑨ 断言要断「机制与目标」，**不要断「模型走了几步」**

> "你经常断言一些**数量上的东西** —— 有没有想过这些断言**极其脆弱**？
> 大语言模型本就是**基于概率**的呀。"

**判据**：写断言前先问一句 —— **这条断言的对象是「谁的行为」？**

| 断谁 | 例子 | 判 |
|---|---|---|
| **平台机制**（代码，确定性） | 有没有透传 / 投递 · 产物 ID 唯不唯一 · 有没有把**读来的**算成它产的 | ✅ **稳** |
| **产物性质** | 有没有占位符 · 声明 html 的有没有头有尾 | ✅ **稳** |
| **不变量** | 同一技能最多一个 `completed` · 每个任务都有产物 | ✅ **稳** |
| **目标状态**（断结果，不断路径） | 某技能**最终**到了 `completed` | ✅ 大体稳 |
| 🔴 **走了几步** | `task_count==n` · `delegate_calls==n` · `llm_calls<n` · `run_task≥n` | **脆** |
| 🔴 **输出多长** | `reply_chars<n` · `artifact_chars>n` · `main_ctx<n` | **脆** |

**两条修法**：

1. **数量断言 → 不变量或边界**（`== n` 改 `≥1` / `≤n`），或者干脆换成"**目标达成了没**"
2. 🔴 **有效性断言别指望模型去走那条路 —— 让平台把路造出来。**
   最好的先例是 `fault.structured` **故障注入**：它不靠模型配合，平台直接注入。
   同理，要压"重入路径"就该能**注入一个 `waiting_for_input` 的初始 Task**，
   而不是指望执行器先问一轮 —— `t3-split-answers` 的 `run_task_count_over: 3`
   就是这么脆的：主 agent 自己在第 2、3 轮把信息收齐了才派发，执行器**一次就干完**，
   那条路径压根没被走到（**基线臂和实验臂逐字相同地都挂这一条**）。

**同源的教训：做对照实验前，先花小钱确认「基线里这个问题存在吗」。**

> 2026-11-02 实测：我拿一份**过期的**基线报告（更早的代码版本，上面写着某 rubric ❌）
> 论证"这个问题存在"，据此设计了 A/B。现跑一次基线才发现**它现在本来就全过** ——
> **撞天花板，整个实验从设计上就测不出东西**，白跑两臂 24 分钟。
> **两个 run 就能先确认的事，别用二十四个 run 去测。**

#### ⑩ 别自己造机制 —— **先看大多数 agent 怎么做**

> "我们就是要**遵循大多数 agent 的搞法**，**不要自己去随便造机制**。"

**判据**：想加一层机制之前，先问两句 ——

1. **参考实现里有吗？** 本地就有 `agents-ref/ref/`：`deepagents` · `deer-flow` · `nanobot` · `protoAgent`
2. **它是在给「大家都支持的形态」打补丁，还是在给「没人支持的形态」打补丁？**

**2026-11-02 的教训**：真技能 `zhiwo-ai-multi-role-agent-builder` 把交付物写在**回复正文**里，
我围绕它提了**四条机制** —— 平台无条件贴 / 声明标记 + 存在性校验 / 平台自动落库 / 拼接全部轮次 ——
**四条全被否**。读完四个参考项目才发现：**没有一家支持「交付物在正文里」这个形态**，
它们的交付物一律走**独立通道**（文件 / artifact / 路径 / 指针）。

**结论自己就出来了**：平台**只保证产物**（`solution.md` §0.7）。

> 🔴 **"我发现一个可能的问题 → 提议加一层机制"这个反射要按住。**
> 没证到的问题别用机制去兜（`principles.md` ⑨ 同源）；真有问题，**先看别人怎么解的**。

#### ⑪ 交接三问 —— **每一条交接，都要过这三关**

用户 2026-11-02 定的规矩（原话，重复过两遍）：

> "一定要注意交接的地方：**① 交接了什么内容　② 内容是否被截断了
>  ③ 过长的交接内容是否考虑了渐进式披露的原则** —— 这三点**深刻影响 agent 执行效果**。"

**为什么是这三条**：agent 的"理解"完全建立在**它手上有什么**之上 ——
交接是**唯一**把信息送到它手上的途径。交接漏了、被切了、或者长了没法按需取，
它就只能**猜**；而它猜的时候**不会说自己是在猜**（⑨ 的同源：概率系统里，
"自信的错误"比"明确的不知道"更贵）。

| 关 | 问什么 | 反例（本项目实测踩过） |
|---|---|---|
| **① 交接了什么** | 这一跳**该给**的东西给全了吗？ | `failed` 分支没带 `progress`/`missing` → 主 agent 只知道"没做成"（原则 ⑤ 第 3 条） |
| **② 有没有被截** | 有没有 `[:N]` 把话切了？**切了标了吗**？ | `delegate` 的回执 `report[:150]` 切在表格中间；答复没带它回答的"问" |
| **③ 长了怎么办** | 长的走**渐进式披露**（清单常驻 + 正文按需），还是**显式截断**？ | 【用户原话】只给清单 + `read_user_turn` 按需取 ✓ 正面例子 |

**三条各自的"正确姿势"**：

- **①** —— 顺着信息流走一遍：**产出它的环节 → 需要它的环节**，中间断了吗？（原则 ⑤ 的推论）
- **②** —— 🔴 **切了不标，是最糟的一种**：读的人分不清"它就说这么多"还是"被切了"，
  而这两种情况该做的决定**完全不同**。要切就带**显式标记**（`【平台截断：还有 N 字…】`），
  并说清**全文在哪**。
  > **"摘要"和"截断"是两回事**：要短就该**另写一段短的话**，而不是把原话切一刀。
- **③** —— 长内容只有两条正当出路：**渐进式披露**（清单常驻、正文用工具按需取），
  或**显式截断**。**没有第三条** —— 悄悄切一刀不算。

**机制化**（不靠人记得）：`evals/unit_handoff.py` —— 扫 `proto/*.py` 里每一处切片，
**要么在豁免名单里写明理由，要么不许有**；再逐个交接点喂超长输入，断"一个字都没丢"。
以后谁手滑加一个 `report[:150]`，那里当场红。
