# 场景回归集

> **用法**：每次架构迭代后，**逐条跑一遍**，看能不能满足。
> 架构改动容易"修好一个、弄坏一个"——这份清单就是防这个的。
>
> 来源：全部来自与用户的讨论（用户口述的真实场景 + 实测中发现的边界）。
> 状态列记录**最近一次实测结果**（2026-10-28，DeepSeek v4 pro）。

---

## 一、用户原始痛点（🔴 必过，其余都是次要的）

### S1 · 多技能参数重叠，**不重复问**

| | |
|---|---|
| **输入** | "帮我备课、导学单，再出个随堂小测，三年级数学" |
| **期望** | 年级/学科**只问一次**（备课和导学单都要），不要两个技能各问一遍 |
| **为什么** | 用户最初的痛点："我明明已经输入过了，为什么还要我再输一遍？" |
| **状态** | ✅ 当前：主 agent 自己收齐再派发，不重复 |

### S2 · 任务没干完，**不从头重开**

| | |
|---|---|
| **输入** | 缺参数的请求（如没给"课题"） |
| **期望** | 补上参数后**继续**，而不是"重新建一个全新任务、再问一遍参数" |
| **为什么** | P2 原始症状："主 agent 会调用全新的 subagent 从头再干一次" |
| **状态** | ⚠️ **部分**：主 agent 会补信息重派（✅ 不重复问），但**会重复委派**（见 S14） |

### S3 · 提问后答复**走向确定**

| | |
|---|---|
| **输入** | 系统提问 → 用户答复 |
| **期望** | 答复**确定地**回到提问的那个任务；不出现"重开一个"或"主 agent 自己干" |
| **为什么** | P3 原始症状："用户看到输入后，1）主 agent 重新调用全新 subagent 2）自己干" |
| **状态** | ✅ 当前：提问者是主 agent 自己，无"答给谁"的歧义 |

## 二、边界与异常（容易漏，但真实会发生）

### S4 · 闲聊 / 不需要技能

| | |
|---|---|
| **输入** | "你好" |
| **期望** | 主 agent **自己答**，**不建 Task** |
| **为什么** | 旧版这里是 bug：返回"（无产出）"——主 agent 是纯路由器，连话都不会说 |
| **状态** | ✅ 当前：自己答，Task = 0，7 秒 |

### S5 · 参数**运行中才出现**

| | |
|---|---|
| **输入** | "帮我出随堂小测，三年级数学"（没说难度） |
| **期望** | 执行器跑到一半发现缺"难度"→ 主 agent 先试答 → 答不上才问用户 |
| **为什么** | 用户确认过："真有这种情况，而且业务人员不知道 agent 运行机制，很容易写出这种 skill" |
| **状态** | ✅ 当前：`delegate` 内部保证先试答，失败才登记待答 |

### S6 · 业务人员写的**不规范 skill**

| | |
|---|---|
| **输入** | 一个没声明任何参数、没写清交付形态的 skill |
| **期望** | 平台**照样兜住**，形式能跑 |
| **为什么** | 产品原则："尽量减少对用户 skill 的强制约束……效果由作者迭代" |
| **状态** | ✅ 当前：`Skill` 只有 `description` + `instructions`，平台不要求任何声明 |

### S7 · **任务本来就不需要文件产物** 🔴 **循环版实测失败**

| | |
|---|---|
| **输入** | 一个**纯分析**的任务（读一份教案、给口头修改建议 —— **不需要产出任何文件**） |
| **期望** | 没有产物也算**完成**；判定不能把"产物库是空的"当成"没完成" |
| **为什么** | 用户指出过："skill 要求 llm 生成特定标记的配置……不需要落库" —— 当时的判定把"完成"等同于"产物库非空"，**无产物的任务永远过不了** |
| **状态** | ✅ **已修复**（2026-10-28）：<br>修复前：判成"在等用户"（当时的 `stage=awaiting_user`）、主上下文 **22237 字**、耗时 3 分钟<br>修复后：判成完成（当时的 `stage=done`）、主上下文 **581 字**、耗时 **25 秒**<br>⚠️ 那两个 stage 名现在都不存在了 —— 现行是 **5 态**，见 `architecture-diagram.md` §6.2 |

**根因**：`完成 = 产物库非空` 这条判定**只对「落库交付」成立**。

> ⚠️ **这推翻了 §10.11 的判断**——当时把"交付形态"当过度设计砍掉了，**砍过头了**。
>
> **现在的做法**（取代了当时的"方案甲"）：判定改成**问「任务完成了没」**（三态，
> `executor._judge`），**产物只是证据之一** —— 无产物时判定看的是**执行器的产出全文**，
> 所以"只说不做"会被判 `failed`、不放行。
> 当时的"方案甲"（在 `delegate` 里单独让 LLM 判断"在要信息还是已交付"）**已删除** ——
> 那个判断被三态判定吸收了（`solution.md` §5.1）。
>
> **弃用的方案（理由仍然成立）**：
> - 乙（skill 声明 `delivery`）—— 零运行时成本，但**约束作者**且作者可能声明错
> - 丙（交给主 agent 判断）—— 但"平台保证先试答"就没了

> 🔴 **2026-11-03 换壳：这条 case 原来叫 `s07-no-store-delivery`，壳是"正文交付"。**
>
> 那个形态**平台不保证、且是反模式**（用户：*"我们平台根本就不保证正文交付这条路径……
> 因为正文交付就是反模式"*）。所以**换掉壳、保留性质**：
> case 改名 `s07-no-artifact-task`，用一个**纯分析技能**压它 ——
> 断的仍是「**无产物照样能判完成**」，**不再**断"配置块原样转达"（平台不保证那条）。
>
> 🔴 **2026-11-05 这条 case 也删了 —— 前提彻底没了**：它断的是「**无产物照样能判完成**」，
> 而判定退休后三态**由结构定**（`executor._structural_status`）：`completed` **必然有产物** ✗
> （`completed_in_reply` 那一档同时被删 ✗）。"没有产物"现在**结构上就是** `incomplete`
> → 推回去让它交付 ✓ —— 这条 scenario 描述的状态**不可达**了。
> （**性质没丢**：正文交付仍是反模式 ✓，平台只保证产物 ✓ —— 见 §0.7。）
>
> 同批删掉的：`r1-protocol-delivery` / `r2-body-delivery`（前提已不成立 ——
> 真技能 `zhiwo` **已改成 `write_artifact` 落产物**）、内置玩具技能 `courseware-config`、
> `evals/fixture-skills/`。详见 `solution.md` §0.7。
>
> **真技能上实测过一次**（2026-11-02，`zhiwo-ai-multi-role-agent-builder`）：
> 执行器交付了**五类**配置，用户只拿到**一类** —— 因为它第 2 轮补差异、回执只带那一条。
>
> **要平台保证交付 → 走产物**（`write_artifact`）。

### S8 · 用户**换话题**（挂起后不回答） ✅ **循环版实测通过**

| | |
|---|---|
| **输入** | 第 1 句出小测（缺难度 → 待答）→ 第 2 句换话题"算了，先帮我备一节课" |
| **期望** | 待答**不丢**，但也不阻塞新需求 |
| **为什么** | 实测踩过：旧版这里**死循环**（把换话题当成答复，重跑执行器又挂起） |
| **状态** | ✅ **通过**（2026-10-28 实测）：<br>· 新需求正常处理（备课 → `art_001`）<br>· 待答**没丢**（quiz 仍 `awaiting_user`）<br>· **主 agent 主动提醒了待答**：「顺便提醒一下，之前那份随堂小测还在等您选难度…」<br>· **没有死循环** |

> 💡 这里是**台账注入**（`prepare`）的功劳——主 agent 看到了"quiz 还在等答复"，
> **自己**在回复里提了一句，**不需要 `finalize` 兜底**。兜底成了双保险。

## 三、新架构的行为要求（用户明确提的）

### S9 · 主 agent **先答**（不打扰用户）

| | |
|---|---|
| **输入** | 执行器缺信息，但**用户之前已经说过** |
| **期望** | 主 agent 用**自己的上下文**补上，**不打扰用户** |
| **为什么** | 用户明确要求："先主agent尝试回答这个问题 如果不行就请求用户输入" |
| **状态** | ✅ 当前：`delegate` 工具内部强制这一步（平台代码，LLM 跳不过） |

### S10 · **一次只问一个**

| | |
|---|---|
| **输入** | 多个任务同时缺参数 |
| **期望** | 逐个问，"谁在问、答给谁"完全确定 |
| **为什么** | 用户选定的方案（乙）：避免广播导致"答案里的哪部分给谁"不确定 |
| **状态** | ✅ **2026-11-05 落实**：平台**一次只摆一个**（`graph.next_pending`），用户在**那个带标识的提示符**下答 → **只投给那一条**（`State.answer_to`）；答完接着摆下一个。"答给谁"由**通道**决定，不读文本 ✓ 见 `solution.md` §0.65 Y1。⚠️ 主 agent **自己**的那句回复里仍可能问它自己的问题（那是它的话，与平台摆的待答是两回事） |

### S11 · **不委派就没有 Task**

| | |
|---|---|
| **输入** | 闲聊、追问、简单修改 |
| **期望** | Task 列表为空 |
| **为什么** | 用户明确要求："主agent不必所有事情都委派出去" |
| **状态** | ✅ 当前：S4 实测 Task = 0 |

### S12 · 主 agent **能自己干活**（不只是包工头）

| | |
|---|---|
| **输入** | 不需要专业技能的事（澄清、追问、简单修改） |
| **期望** | 主 agent 直接处理，不为了用技能而用技能 |
| **为什么** | 用户明确要求："主 agent 能否直接干活儿（不只是包工头，也可以干活）" |
| **状态** | ✅ 当前：S4 通过；但**"技能活能不能自己干"已决定：不能**（去掉 `load_skill`，避免它绕过隔离） |

## 四、隔离与成本（架构的核心收益）

### S13 · **产物正文不进主上下文**

| | |
|---|---|
| **输入** | 委派出去产出一份**长**文档 |
| **期望** | 主上下文只留产物 ID + 摘要；正文只在产物库 |
| **为什么** | 用户放弃 subagent 的原因就是上下文爆炸；实测 HTML 课件 48k 字 |
| **状态** | ✅ **架构成立**（2026-10-28 更正）。<br>⚠️ **但必须用长内容测**：日志核对确认主 agent **一次都没调 `write_artifact`**（那 8 次全在执行器的消息轨迹里），它的回复是「产物 ID + 一句话摘要」表——**正是要的行为**。<br>隔离比看着只有 0.8–1.2 倍，是因为**原型提示词写着"150 字以内"，测试内容太短**，产物库总共才 2k 字，隔离效果看不出来。**换成 48k 的课件，主上下文还是那 2.6k 字。** |

> 🔴 **测试要求**：验隔离**必须用长内容**（执行器产出 ≥5000 字），否则测不出来。

> ⚠️ **2026-10-30 变更：这条不再有硬断言了。**
> 原来的 `main_ctx_under`（主上下文 < 3000 字）**已删** —— 用户定：
> *"对于 main agent 的上下文大小 我们只记录就行 暂时不要加逻辑处理"*。
> 理由：读产物是主 agent 的**合法能力**（它也要能干活），拿它判红是罚一个合法能力（见 F17）。
> **现在怎么验**：CLI 每轮打 `📊 CONTEXT` 行、`_run.md` 每轮有 `<sub>` 读数，
> 超 `CTX_WARN_CHARS`（12000）出 warning —— **读数摆在眼前，由人判断**。
> 参照值：单技能隔离场景实测 517–1109 字（产物 14270 / 34525 字）。

### S14 · **不重复委派**

| | |
|---|---|
| **输入** | 先派 3 个技能，用户再补一句「难度要基础的」 |
| **期望** | 只重跑**受影响**的任务 |
| **为什么** | 实测发现主 agent 把三个任务**全部重跑**，产物重复（两份教案） |
| **状态** | ⚠️ **重新定性：不算 bug**（用户判定）。<br>日志核对：第 2 轮的"重跑全部"是因为主 agent 把「难度要基础的」**理解成全局指令**——**这是 LLM 的抉择，不是机制缺陷**。<br>台账注入已生效（日志有 `prepare` 记录），主 agent 确实看到了"已派过什么"。<br>真要收敛，得在**产物库层面**做版本/覆盖，不属于本架构。 |

> 🔴 **顺带修了一个真 bug**：`task id` 取 `tool_call_id` **前 6 位会撞车**（两个任务都叫 `t_call_a`），
> 已改成取**尾部**。这条要留在回归集里，防止改回去。

### S17 · 产出**不完整**时不能判完成（评审人 C2 提出的场景）✅

| | |
|---|---|
| **输入** | 一个有明确交付要求的技能（导学单），执行器产出的文件**缺了「当堂检测」** |
| **期望** | **不能**因为"产物库里有东西"就判完成；要能**指出具体缺哪条** |
| **为什么** | 评审人：*"假设导学单 Skill 已经生成了一个文件，但文件缺少关键章节。产物库里有文件，任务是否完成？我认为不能直接判定为完成。"* |
| **状态** | ✅ **通过**（2026-10-28）：技能声明 `completion_criteria` 后，平台逐条检查——<br>· 完整产出 → 判完成<br>· **缺「当堂检测」→ 判未完成，且明确指出是第 3 条**<br>· 产出在索要信息 → 判未完成<br>· **没声明条件的技能一个字不用改，照样跑**（走既有事实 / LLM 兜底） |

> **机制（2026-10-28 更新）**：~~作者声明 `completion_criteria`~~ →
> **`completion_criteria` 已移除**（实测证明它没有增量价值，见 `architecture-review.md` D1）。
> 现在用**三态判定 + 明确规则**：`completed` / `waiting_for_input` / `incomplete`，
> 且判定提示词里带上 `instructions` + `given` + 产出 + 产物数量。
> **测试**：`debug_judge_variants.py`（5 种提示词对比）、`debug_exit.py`（出口限制）。

### S18 · 执行器**没干完就停**时不许它停 ✅

| | |
|---|---|
| **输入** | 一个"干不成、又不许问用户"的任务（故意设计的死局） |
| **期望** | **不让它随便结束**——推回去继续；推满上限仍不行 → 判 `incomplete`，交给主 agent，**不烦用户** |
| **为什么** | 用户提的机制：*"限制出口——如果最后一轮不是交付产物、也不是请求参数、也不是主动 finish，就让它回去继续 react"* |
| **状态** | ✅ **通过**（2026-10-28，`debug_exit.py`）：<br>· 死局任务 → 推满 3 轮 → `incomplete`，**没去烦用户**<br>· 正常交付 → **1 轮**返回，没被误推<br>· 正常提问 → **1 轮**返回，没被误推<br>⚠️ **死局那一条已被后来的行为取代** —— 见下方「行为变过」 |

> ⚠️ **行为变过，上面记的是早先版本。**
>
> `logs/` 里能看清分界（约 15:09）：
>
> | 时期 | 死局任务的实际表现 |
> |---|---|
> | **早先**（14:14 / 15:00 / 15:04） | `轮次=3` `asking=False` → **推满 3 轮 → `incomplete`** ← 上面记的就是这个 |
> | **后来**（15:09 之后） | `轮次=1~2` `asking=True` → **早说早处理，走请求信息路径** |
>
> 原因是 `_PLATFORM_RULE` 改成了让执行器**主动说明缺什么**，它不再硬扛到轮次上限。
>
> **新的期望应该是**：死局任务 → **1–2 轮**就说明需要什么 → 走 `waiting_for_input`。
> 代价是**它会经主 agent 触达用户** —— "执行器没干完不该转嫁给用户"在死局下**并未完全达成**。
> 这属已知取舍，重跑本场景时按新期望判定。

> **机制**：`executor.run_task` 的循环 + `_nudge_text()`。
> **关键**：判定给出的 `missing`（还缺什么）会**写进推回去的提示**——
> 用户要求：*"尽可能暴露一些有用信息到外部，不然你只是说没完成，
> 后续即使回去继续 react 也不知道该怎么做。"*

### S19 · 重新委派同一技能时，**旧的待答不能留在台账里** ✅

| | |
|---|---|
| **输入** | 第 1 句出小测（缺难度 → `waiting_for_input`）→ 第 2 句"难度要基础的" |
| **期望** | 旧的 Task **自动标记为 `superseded`**，台账里不再显示"等答复" |
| **为什么** | 实测发现：不清理的话，主 agent 每轮看到过期的待答，**会以为还有事没做完** |
| **状态** | ✅ **通过**（2026-10-28，假模型 + 真实模型各一次）：<br>`t92d26841 stage=superseded` / `t8e89a3d4 stage=completed`<br>日志：`取代了 1 个同技能的未了结 Task：['t92d26841']` |

> **机制**：`agent._supersede_old()` —— 委派时把同 skill 下
> **`waiting_for_input` / `failed`** 的旧 Task 标记为 `superseded`。
> **`completed` 的不动**（历史记录，用户可能还要看产物）。

### S20 · 真实技能包的多技能链：依赖靠**传 ID**，不靠转述 🔴 **新机制待复测**

| | |
|---|---|
| **输入** | 一条消息要三样（教案 / 导学单 / 交互网页），且明确要求后两样**参考教案内容**。用真实技能包（`evals/cases/t2-same-turn.yaml`，技能见 `evals/skills/`） |
| **期望** | 三样都交付；后两样的 task 带**产物引用**（`artifacts=["art_001"]`）；主 agent **不把正文读进自己的上下文** |
| **为什么** | 首轮实测暴露两条结构问题：**F11**（主 agent 自己读 5162 字全文再转述 → 隔离破功、转述失真）与 **F12**（它在 task 里发明"控制在一页A4以内"，压过技能的 7 板块模板） |
| **状态** | 🔴 **首轮不达标**（2026-10-29，`--tag t2-probe`：12/13，`main_ctx_under` 红）→ 机制已按 F11/F12 修法改造，**待复测** |

> **机制**：`delegate(skill_name, task, artifacts=[...])`（平台当场校验 ID、只注入清单）
> \+ 产物三件套（名称 / 梗概 / 正文）+ 技能与产物**同一套渐进式披露**

### 附带发现：模型侧基础设施抖动（生产必看）

实测 **DashScope 会偶发** `grammar validation or compilation failed: sandbox grammar compile timed out`
——发生在 `with_structured_output` 调用上（`executor._judge` / `agent._ask_main`）。
**一次抖动会炸掉整个 turn**（实测踩过两次）。

**已加兜底**：`proto.llm.safe_structured()` —— 重试一次后退化到**保守默认值**：

| 调用点 | 失败时的默认 | 理由 |
|--------|------------|------|
| `executor._judge`（三态判定） | `status="incomplete"`（当作没完成） | 会让它再 react 一轮 |
| `agent._ask_main`（试答） | `can_answer=False`（当作答不上） | 交给用户，而不是编一个答案 |

> ⚠️ **兜底表原来有三行**，第三行是 `_which_unasked`（`finalize` 里 LLM 判断"问题问出去没"）——
> **该调用点 2026-10-29 已删除**，改成平台**无条件透传**（`solution.md` §4.5.4）。
> 所以现在只剩两个 LLM 判定点要兜底。

> **通用教训**：任何 LLM 调用点都要有兜底，**基础设施抖动不该让整轮失败**。

### S10 的重新定性（2026-10-28 两次实测）

| | 旧设计（workflow） | 循环版（第一次实测） | **循环版（第二次实测）** |
|---|---|---|---|
| 需要"一次只问一个"吗 | ✅ 平台硬约束（多 subagent 各自 interrupt，要硬机制决定答给谁） | ❌ 不需要 | ❌ **不需要，而且不该** |
| 实测表现 | 平台强制 | 只有缺参数的那个问 | **3 个任务同时缺参数 → 自动合并同类项，一次问完** ✅ |

**第二次实测（3 个任务全部 `waiting_for_input`）**：

```
🤖 "三个任务都遇到了同样的情况——执行器需要你补充一点信息，我一次性问完：

**关于备课和导学单**：这是《分数的初步认识》的第几课时？
**关于随堂小测**：你想要的难度档是？

告诉我课时和难度，我马上一起推进。"

finalize: 3 条待答都已问出 ✅
```

> **关键**：它**自动把"备课"和"导学单"的同一个问题合并了**——两个技能都要"课时"，它合成一条问。
> **这正是 P1 的目标**，而且是在多任务场景下做到的，**比"平台去重"更自然**
> （LLM 自己看出"这俩要的是同一个东西"）。

**所以 S10 的最终定性**：不是"逐个问"，而是「**合并同类项，一次问完**」——
**比逐个问体验好，而且不需要平台硬约束**。
