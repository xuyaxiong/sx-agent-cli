## 〇、用户补充的两条**工程原则**（2026-10-28，贯穿所有讨论）

> **① 信息交接处，一定要说更多的细节。**
> *"只要涉及到信息交接、信息转移的地方，一定要说更多的细节，
> 这样大模型用作决策的有效信息更多，得出的结论才更强。"*
>
> **② 决策结果要结构化。**
> *"决策的结果最好是结构化的，这样我们才可以在流程中用代码处理，比如参与逻辑转移判断。"*
> 具体指 **Structured Output**（OpenAI `response_format` / LangChain `with_structured_output`）：
> 把 JSON Schema 传给模型，**模型原生保证结果符合结构**，
> **不需要靠工具参数去约束**（反面教材：`finish` 工具——模型不调，决策就丢了）。

**实测踩过的三次，全是违反原则 ①**：

| # | 缺什么 | 后果 |
|---|--------|------|
| 1 | 判定提示词没带 `instructions` | "按任务要求判断"是空话 |
| 2 | 判定提示词没带 `given` | 明明给了"第1课时"，判定说"没询问" → 误判 |
| 3 | `failed` 分支没带 `progress`/`missing` | 主 agent 只知道"没做成"，不知道缺什么 |

> **推论**：**信息在内部产出了，不代表需要它的地方看得到。**
> 每加一个机制，都要顺着信息流走一遍：
> **产出它的环节 → 需要它的环节，中间断了吗？**

**审计结果（2026-10-28）**：

| 交接点 | 是否符合 |
|--------|---------|
| 判定 ← `instructions` + `given` + 产出 + 产物数量 | ✅ |
| 判定 → 执行器（推回去）：`progress` + `missing` | ✅ |
| 判定 → 主 agent（`failed` / `awaiting_user`）：`progress` + `missing` | ✅ |
| 执行器 → 主 agent 试答：`progress` + `missing` | ✅ |
| 平台台账 → 主 agent（每轮注入）：`progress` + `missing` | ✅ |
| **决策是否结构化** | ✅ 三处判定全用 `with_structured_output`，无"用工具传决策" |

## 一、评审人认可的三个判断（附补充）

### A1 · 主 Agent 应该是完整 Agent ✅认可 + ⚠️补充 → ✅ **已满足**

**评审人的补充**：
> 主 Agent 可以决定做什么，**不应该独自承担所有任务状态的正确性**。
> 例如主 Agent 可以决定委派教案生成，但**平台必须能确定这个任务究竟是
> 运行中、等待输入、已完成，还是失败**。这是**模型决策与程序控制之间的分工**。

**我们的实现**：

| 谁决定什么 | 谁 |
|---|---|
| **要不要委派、委派给谁、说什么** | **主 agent（LLM）** |
| **任务状态是 running / completed / waiting_for_input / failed / superseded** | **平台代码**（`rec.update(stage=...)`） |

**关键**：判定虽然由 LLM 给出（`_Judgement.status`），但**映射到 `Task.stage` 是代码做的**，
而且**三态穷举**（枚举 if），LLM 决定不了"走哪条路"。

**结论**：A1 已满足 ✅



**认可**：主 Agent 应能直接回答、自己完成短内容、判断何时需要专业能力、委派复杂工作、
根据子任务结果继续推理、判断是否需补充信息。

**补充（关键）**：

> 主 Agent 可以决定做什么，**不应该独自承担所有任务状态的正确性**。
> 例如主 Agent 可以决定委派教案生成，但**平台必须能确定这个任务究竟是
> 运行中、等待输入、已完成，还是失败**。
> 这是**模型决策与程序控制之间的分工**。

### A2 · Sub Agent 是可选执行者，不与 Skill 一一绑定 ✅认可 + ⚠️修正表述 → ✅ **部分采纳（2026-10-28）**

**评审人的修正**：把"一次性、通用"改为
**"按需创建、可配置、具有明确执行边界的执行者"**。
理由：**不要过早限制未来的执行模型**（"可以一次性执行，也可以通过持久化状态支持多阶段执行"）。

**我们的处理：措辞采纳，功能保持。**

| 评审人说的 | 我们的 | 采纳？ |
|---|---|---|
| **按需创建** | ✅ 每次 `delegate` 时 `create_agent` | ✅ |
| **可配置** | ⚠️ 现在是固定配置（工具固定、提示词固定） | ✅ 措辞采纳；将来要按 skill 配工具时再扩 |
| **有明确执行边界** | ✅ `MAX_REACT_ROUNDS = 3` + 出口限制 | ✅ |
| **不一一绑定 Skill** | ✅ 执行器通用，skill 指令由调用方传 | ✅ |
| **可以通过持久化状态支持多阶段执行** | ❌ **不采纳** | 见下 |

**为什么"多阶段执行"不采纳**：

它和我们的核心设计**冲突**——我们明确选了 **"状态在 Task 上，不在执行器上"**（F3 的「重新调用」路线）。
执行器**用完就丢**，正是为了让"重新起一个"变得无害。

**但我们**已经能"接着做"**，只是方式不同**：
- **同一次 `run_task` 内**：推回去时带 `progress`（"你已经完成了 X，还缺 Y，接着做，别从头来"）
- **跨 `run_task` 调用**：⚠️ **现在做不到** —— 重新调用时只传了累积的 `given`，**没传上次的 `progress`**

> 🔴 **记一个可改进点**：重新调用执行器时，**把上次的 `progress` 也传进去**，
> 让它"接着做"而不是从头来。这能同时缓解 **G7（不重复问）** 和 **T3（产物重复）**。
> **现阶段不做**，记进待讨论清单。



**认可**：不要因为存在一个 Skill，就必须创建一个专属 Sub Agent。

**修正**：**"一次性、通用"这个表述要改**。

> Sub Agent 可以是通用的，也可以是针对特定任务预先配置的；
> 可以一次性执行，也可以通过持久化状态支持多阶段执行。

**建议改为**：**按需创建、可配置、具有明确执行边界的执行者。**

理由：既不强求每个 Skill 配 Sub Agent，也不**过早限制未来的执行模型**。

#### 🔴 程序强制（代码保证，LLM 无法违反）

| # | 约束 | 怎么强制的 | 在哪 |
|---|------|-----------|------|
| 1 | **产物必须真实存在** | 只认产物库里查得到的 ID，LLM 编 `art_999` 无效 | `artifacts.make_write_artifact`（按 run 记账） |
| 2 | **执行器不许无限跑** | `MAX_REACT_ROUNDS = 3`，硬上限 | `executor.run_task` |
| 3 | **状态字段由代码写** | `rec.update(stage=...)`，不是 LLM 声称 | `agent.delegate` |
| 4 | **三态穷举分派** | 枚举 if —— **没有第四种** | `agent.delegate` |
| 5 | **同技能旧的待答自动取代** | `_supersede_old()` | `agent.delegate` |
| 6 | **待答不丢** | 循环结束后 `finalize` 检查并补问 | `graph.node_finalize` |

| 11 | **主 agent 试答是强制的** | 在 `delegate` 工具内部，LLM 跳不过 | `agent._ask_main` |
| 12 | **入口/出口节点固定** | 图是 `prepare → agent → finalize`，主 agent 改不了 | `graph.build` |

#### 🟡 行为建议（提示词，LLM 可以违反）

| # | 建议 | 在哪 | 违反了会怎样 |
|---|------|------|------------|
| 1 | 缺信息就**明确说明**需要什么 | `executor._PLATFORM_RULE` | 判定会判 `incomplete` → 推回去 |
| 2 | 不要用「已完成」糊过去 | 同上 | 同上 |
| 3 | 判定任务状态的三条规则 | `executor._JUDGE_RULES` | 判错 → 走错分支（**但有兜底默认值**） |
| 4 | **不要一律问** / 产出范围以用户说的为准 | `agent._MAIN_PROMPT` | 体验变差（问太多 / 多做） |

#### 这张表回答了什么

**H3 的"可执行的状态转换"** = 上表第 1-12 条：
它们定义了**状态怎么流转、什么情况下走哪条路**，而且**不依赖 LLM 配合**。

**H3 的"恢复机制"** = **「重新调用」**（F3）：
不是恢复图执行，而是**重新 `delegate` 一次**，带上累积的 `given`。

**A3 的分界线** = **机制在程序里，业务在提示词/skill 里**：
- **程序强制**：跟"任务状态正确性"有关的（产物真实、状态由代码写、三态穷举、不丢待答）
- **行为建议**：跟"业务判断"有关的（什么算必答、要不要问、产出范围）

> **判据**：**如果一条约束被违反了会导致"状态不一致"，它就必须是程序强制的；
> 如果只是"效果差一点"，可以是行为建议。**

## 二、第一张图的问题：把「是否创建 Task」与「是否需要持久化状态」混在一起

### B1 · "先问一个问题"不一定需要业务 Task，但**可能需要持久化交互状态** ✅ **实测不成立（2026-10-28）**

> **结论：靠对话历史够用，不需要额外状态。但实测意外暴露了 B2。**

**先分清两套机制**（评审人担心的"全靠对话历史"，只发生在第一种）：

| 谁在问 | 有没有 Task | 靠什么记住"在等什么" |
|--------|------------|-------------------|
| **主 agent 自己问**（"哪个课题？"） | ❌ 无 | **对话历史** |
| **执行器缺信息，主 agent 转达** | ✅ `waiting_for_input` | **台账注入**（平台保证） |

**实测两个场景**（真实模型）：

| 测试 | 结果 |
|------|------|
| **① 连续两轮主 agent 自己问** | ✅ 每轮都正确接上（"好的，「分数的初步认识」——"） |
| **② 中间插一轮别的，再回答** | ✅ **隔了一轮仍正确关联**，而且**主动把话题拉回来** |

测试 ② 的完整记录：
```
Turn 1  帮我备课
   🤖 问 4 个关键信息
Turn 2  先等等，23×17 等于多少？
   🤖 23 × 17 = 391
      "好了，回到备课——你需要我帮你备什么科目、什么内容的课？"   ← 主动拉回
Turn 3  分数的初步认识
   🤖 "'分数的初步认识'——这应该是三年级数学的内容对吧？"       ← 正确关联
```

**关键**：问答**相邻**时，LLM 不会看错；隔一轮也能靠上下文关联。
而且现在 `prepare` 注入的是**提示**（"用户这条消息很可能是答复——**若确实如此**…"），
**主 agent 自己判断**，比旧设计的硬规则（"一律当补充"）更宽松。

**评审人说的"复杂任务的参数对齐阶段"在我们这里天然有 Task** ——
参数是执行器运行时才发现缺的，那时**必然已经委派了**，必然有 Task。

**但实测暴露了另一个问题**（见 B2）：**它一直在问，从不动手**。

### B2 · "信息不足先问"不应该成为**固定的优先级规则** ✅ **实测成立，已解（2026-10-28）**

**实测现象**（B1 的测试里）：
```
Turn 1  问 5 个问题（含"有没有公开课/赛课"这种可选的）
Turn 3  又问 2 个（"课时？""特殊场景？"）
三轮下来 Task 始终 = 0 —— **一直在问，没委派**
```

**根因**：系统提示写着"用户没给全信息时，**先问清楚再委派**，别拿着半截信息硬派" ——
**把"信息不全"直接映射成"必须问"**。

**第一次修**（列出"哪些有默认值"）→ 部分有效，但**引入了新问题**：

```
帮我备课，三年级数学，分数的初步认识
   🤖 使用默认值：1 个课时、常规课型、基础难度   ← 用了默认值 ✅
```
```
帮我备课 → 分数的初步认识 → 第1课时
   → **派了 3 个技能**（备课 + 导学单 + 小测）   ← 自行扩大了产出范围 ❌
```

**用户判定**：*"我倾向于保守的，**没明确说的还是不做**。"*

**最终解法（用户提的）—— 平台管机制，skill 管业务**：

| 判断 | 谁负责 |
|------|--------|
| **信息不全时该不该问**（机制） | **平台提示词** |
| **哪些参数必答、哪些有默认值**（业务） | **skill 的 `instructions`** |

**平台提示词（最终版）**：
```
## 信息不全时，**不要一律问** —— 先判断能不能推进
- 能推进就**先推进**（真的缺东西时，执行器会告诉你）；
- 确实推进不了的，才问用户；要问就**一次问完**（别挤牙膏）；
- **哪些参数是必答的、哪些有默认值，以技能指令为准** —— 平台不替你猜，你也别猜。
```

**平台提示词（另一处）**：
```
## 🔴 产出范围**以用户明确说的为准**，不要自行扩大
用户说「帮我备课」就**只出教案**；不要说「我顺便把导学单和小测也做了」。
想提供的话，**在回复末尾提一句**就行，让用户自己决定要不要。
```

**skill 侧**（`lesson-prep.instructions`）：
```
**你需要知道这节课的「课题」和「课时」（第几课时）**
——不知道就先问，不要自己编，也不要用默认值糊过去。
```

**最终实测（真实模型）—— 整条链路按设计走**：

```
Turn 1  "帮我备课"
   → Task=0，它先问（信息确实太少）

Turn 2  "分数的初步认识"
   → 🧠 派发了
   → 执行器读 skill 指令，发现缺「课时」→ stage=waiting_for_input ✅
   → 主 agent 试答 → 答不上 → 问用户：
      "执行器按人教版三年级上册处理了，需要你确认一个关键信息" ✅

Turn 3  "第1课时"
   → 旧的 stage=superseded ✅（自动取代）
   → 新的 stage=completed ✅
   → "备课搞定了。需要的话我还可以帮你出导学单和随堂小测，要一起做吗？" ✅
```

**四个验证点全中**：

| # | 验证点 | 结果 |
|---|--------|------|
| 1 | 主 agent **不再自己猜"课时算不算必答"** | ✅ 派发，交给执行器判断 |
| 2 | 执行器**读 skill 指令**发现缺课时 | ✅ `waiting_for_input` |
| 3 | 主 agent 试答 → 答不上 → 问用户 | ✅ |
| 4 | **保守范围**：只提一句"要一起做吗"，**不直接做** | ✅ |

**顺带观察（不阻塞）**：Turn 3 那个 Task 是 `completed` 但 `产物=（无）`
—— 执行器走了**正文交付**路径。按设计是对的，但**用户拿不到文件**。
真要收敛，得让 skill 的 instructions 说清"要不要落库"（还是"业务写进 skill"那条原则）。

图中把"信息不足 → 先问"划成"不建 Task"的分支。**评审人认为是实质性漏洞。**

场景：
```
用户：帮我设计一份高一物理教案。
主 Agent：具体是哪个知识点？
用户：牛顿第二定律。
```

**系统仍然需要知道**：
- 这是在补充**哪一次**请求？
- 原始请求是什么？
- 已经问过什么？
- 用户这次回答对应**哪个待补充的信息**？
- 主 Agent 应该**继续原来的意图**，还是视为全新请求？

> 如果只是"不建 Task，然后立刻回复"，这些信息只能依靠**对话历史隐式恢复**。
> 这对简单对话未必有问题，但对有状态的 Agent 系统，**不能把它当成普遍可靠的机制**。

**建议**：
- 简单、独立的澄清 → 可只依靠主 Agent 的会话状态
- **明确进入复杂任务的参数对齐阶段 → 创建 Task，或把已有 Task 标记为等待输入**
- **已经存在 Task 时，后续用户回答应优先与对应的待处理交互关联**，
  而不是让主 Agent 每次重新猜

**引用**：LangGraph 图执行状态与业务实体不是同一回事——
Checkpointer 保存会话执行状态，**是否创建业务 Task 应由业务规则决定**。

### B2 · "信息不足先问"不应该成为**固定的优先级规则** ✅ **实测成立，已解**

图中把"信息不足"作为独立分支，但实际更复杂：

```
用户：帮我做一份高一物理教案。
```

缺具体知识点，但**不一定意味着必须先询问**。主 Agent 可以判断能否：
- 用已有上下文补全
- 采用明确的默认值
- 先生成草案，再让用户确认
- 才把无法推断的关键参数交给用户

> 真正需要的不是固定的"信息不足 → 先问"，而是：
> **主 Agent 判断当前信息是否足以推进任务，以及缺失信息是否必须由用户提供。**
> 平台可以约束"不能伪造用户事实"，但**不应该把所有信息缺口都转换成提问**。

## 三、第二张图的问题：Task 的边界不够明确

### C1 · Task 不能只是"委派时创建的一个任务账本" ✅ **已定（2026-10-28）**

> **结论：7 态里只做 2 个（`superseded` + 命名统一），另外 3 个先不做但记清为什么。**

**审计：评审人 7 态 vs 当时的 4 态**

| 评审人的状态 | 处理 |
|---|---|
| `running` / `failed` | ✅ 已有 |
| `waiting_for_input` / `completed` | ✅ 已有，**改名对齐**（原来是 `awaiting_user` / `done`） |
| **`superseded`**（评审人没提，实测发现需要） | ✅ **新增** |
| `pending` | ⏸ **不做** —— 建 Task 就立刻派发，没有"创建了还没跑"的窗口。等做「计划-执行分离」时再加 |
| `waiting_for_dependency` | ⏸ **不做** —— `delegate` 是**同步**的，依赖在主 agent 循环里天然解决（它先调 A、拿到产物 ID、再调 B）。等做「异步委派」时再加 |
| `cancelled` | ⏸ **不做** —— 需要给主 agent 新工具，且该场景**尚未实测到**。等真遇到再加 |

**最终 `Task.stage`（5 态）**：

```
running · completed · waiting_for_input · failed · superseded
```

**与 `_Judgement.status` 前三个同名**，唯一映射 `incomplete → failed`（显式写在代码注释里）。

**为什么加 `superseded`**：实测发现——同一个技能被重新委派后，
旧的 `waiting_for_input` Task 还挂在台账里，主 agent 每轮看到，会以为还有事没做完。

**只取代 `waiting_for_input` / `failed` 的**：`completed` 是历史记录，不能被抹掉
（用户可能还要看产物）。

**验证**：假模型 + 真实模型各一次，日志都能看到
`取代了 1 个同技能的未了结 Task：['t92d26841']`。

图中台账写的是"派过什么、干到哪、每轮告诉主 Agent"。**必要，但不够。**

**建议至少区分这些状态**（业务状态，**不是** LangGraph 内置枚举）：

| 状态 | 含义 |
|------|------|
| `pending` | 已创建，尚未开始执行 |
| `running` | 正在执行 |
| `waiting_for_input` | 正在等待用户补充信息 |
| `waiting_for_dependency` | 正在等待其他任务或产物 |
| `completed` | 业务任务已满足完成条件 |
| `failed` | 执行失败 |
| `cancelled` | 任务已取消 |

**四条特别提醒**：
- `waiting_for_input` **不等于** Graph 运行失败
- `completed` **不等于**某次模型调用正常结束
- `failed` **不等于**模型返回了一个错误字符串
- **某个 Sub Agent 执行完成，不等于 Task 已经完成**

### C2 · **产物库非空不能作为任务完成条件** ✅ **已解（随 D1 落地）**

**反例 1**：导学单生成了文件，但**文件缺少关键章节** → 算完成吗？
**反例 2**：任务是分析用户上传的文件并给建议，**可能没有任何独立文件**，但业务工作已完成。

> **产物是否存在 与 Task 是否完成 是两个独立的判断。**

**建议的完成条件**：
1. 任务要求的工作已经完成
2. 规定必须交付的产物已生成**并成功持久化**
3. 必要的**质量检查**通过
4. 没有未解决的必需输入或依赖
5. 任务结果已被可靠记录

> 并不是每个 Task 都必须满足所有条件（纯分析任务可能没有文件产物）。
> 更准确地说：**Task 是否完成，应由业务完成条件决定；
> 产物库提供证据，而不是单独决定任务状态。**

## 四、评审人认为的**最大内在矛盾** 🔴

### D1 · 不要求 Skill 声明交付物，却要求平台保证任务完成 ✅ **已定（2026-10-28）**

> **结论：不引入任何新字段，改为「把判定提示词写清楚 + 让模型暴露缺失项」。**

**过程（走过一版弯路，记下来免得回头）**：

1. **先做了 `completion_criteria`**（可选元数据，放 `metadata.platform` 里，
   兼容通用规范——DeepAgents 就是这么放 `include_tools` 的）。
   实测 `debug_criteria.py`（**脚本已删**）9/9 通过。
2. **用户质疑**：*"criteria 根本也是 LLM 判断，其实也是软机制，
   搞这么软硬结合感觉就单纯在提高复杂度，没有本质提升。"*
   —— **质疑成立**：`_check_criteria` 本质就是"把要求放进提示词让 LLM 逐条核对"。
3. **跑对比实验**（`debug_judge_variants.py` —— **脚本已删**；6 个用例，5 种提示词）：

   | 变体 | 全对 |
   |------|------|
   | A 只给产出 | 3/6 |
   | B 产出 + `instructions` | 5/6 |
   | **C 产出 + `criteria`** | **4/6** |
   | E 产出 + instructions + 反省式 | 6/6 |
   | **F 用户拟的模板（三态 + 明确规则）** | **6/6** ✅ |

   **criteria 没有增量价值**（要求本来就在 `instructions` 里，再抄一遍是重复），
   甚至更差——它会把"必须包含 X"硬套到不该套的任务上。

4. **最终方案**：
   - **`Skill` 仍然只有 `description` + `instructions`**（`criteria` 已删）
   - **判定用三态 + 明确规则**（用户拟的模板，原样采用）：
     `completed` / `waiting_for_input` / `incomplete`
   - **判定必须看到完整上下文**：`instructions` + **`given`（执行者已拿到的信息）** + 产出
   - **暴露缺失项**（用户要求）：*"即使是软判断，描述要尽可能清晰……
     尽可能暴露一些有用信息到外部，不然你只是说没完成，后续即使回去继续 react 也不知道该怎么做"*
     → `_Judgement.missing` 逐条列出**还缺什么**，`_nudge_text()` 用它**精确引导**执行器继续

**🔴 一条踩了两次的教训**：

> **判定看不到它需要的信息，就只能猜。**
>
> - 第一次：提示词没带 `instructions` → "按任务要求判断"是空话
> - 第二次：提示词没带 `given` → 明明给了"第1课时"，判定说"未询问用户课时信息"，
>   误判成 `waiting_for_input`
>
> **凡是让 LLM 判断的地方，都要问：它看得到做这个判断所需的信息吗？**

**实现与验证**：`../proto/executor.py` 的 `_judge` / `_nudge_text`；
`debug_exit.py` 3/3（推满上限 / 正常交付一轮返回 / 正常提问没被误推）。

**图左侧写着**：
> Skill 只有两样东西：`description` + `instructions`。无参数声明、无交付物声明、无协议。

**图右侧又要求平台保证**：
- 不重复问参数
- 缺信息时能够补问
- 任务状态可靠
- 产物已交付
- 执行结束后能判断是否完成

> **这两组要求存在冲突。**
> **如果平台不知道一个 Skill 需要什么输入、应该产出什么结果，
> 就无法仅靠通用机制可靠地保证参数完整性和交付完整性。**

**举例**：导学单 Skill 的 instructions 写着"根据用户提供的信息，生成一份完整的导学单"。
平台无法仅从这句话可靠地确定：
- 年级是否是必填参数
- 教学主题是否必须由用户确认
- 生成的文件必须包含哪些章节
- 哪些信息可以采用默认值
- 是否必须生成 Markdown 文件
- 生成文件后还需不需要检查

**建议：保留轻量 Skill，但增加「最小的可检查元数据」**

| 元数据 | 用途 | 是否必须 |
|--------|------|---------|
| `description` | 告诉主 Agent 这个 Skill 能做什么 | **必须** |
| `instructions` | 告诉执行者如何完成工作 | **必须** |
| `input_requirements` | 声明哪些输入是必需的、哪些可以默认 | 复杂任务建议提供 |
| `completion_criteria` | 描述什么条件下才算完成 | 有明确交付要求的建议提供 |
| `output_expectations` | 描述预期产物及交付方式 | 有文件或结构化产物时建议提供 |

> **不是要求所有 Skill 都填五项。** 简单 Skill 只需前两项就能运行；
> 但教案、导学单这类**有明确交付要求**的 Skill，应该**允许**声明必要的输入与完成条件。
>
> 这样平台才能区分**四件不能混为一谈的事**：
> ① 模型说"已经完成" ② 执行者正常终止 ③ 产物已生成 ④ 业务任务真正满足完成条件

## 五、第一张图的 `delegate` 流程：方向正确，但**完成与重试的责任划分要改**

### E1 · 不应该只根据"有没有写入产物库"判断是否交付 ✅ **已解**

- 纯文本分析 → 产物库为空**不一定是错误**
- 上传了无效文件 → 产物库非空**也不代表完成**

**平台应该检查「任务要求的交付条件」**：

```
任务要求：生成导学单
    ↓
是否生成预期产物？
    ↓
产物是否成功持久化？
    ↓
必要的质量检查是否通过？
    ↓
是否仍缺少必需输入？
    ↓
满足条件 → 任务完成
不满足  → 进入恢复或补救流程
```

> 是否需要质量检查、检查哪些项目，**应由任务的完成条件决定**，而不是所有任务用同一套规则。

### E2 · "平台先让主 Agent 试着补救"**不能变成无条件重试** ✅ **已解**

**情况 A：执行失败或结果不完整**
（没正确保存产物 / 文件缺章节）
→ 平台把**明确的失败原因、已有结果、剩余要求**交给主 Agent，
让它决定重新委派 / 修复产物 / 换执行方式

**情况 B：确实缺少用户才能提供的信息**
（教案必须围绕某知识点，但用户完全没指定，也无可靠依据推断）
→ **不应该让主 Agent 不断重试**。平台明确记录缺失项，允许主 Agent 请求用户补充

**建议新增原则**：

> **平台负责识别和记录确定的状态，主 Agent 负责选择补救策略；
> 重试次数和允许的恢复方式由平台约束。**
>
> 否则主 Agent 可能不断重复调用相同 Skill，消耗大量模型资源，却始终无法解决问题。

2. Task 要**跨会话**存活
3. 多个 thread 共享一个 Task

> 🔴 **必须做但还没做的**：`ARTIFACTS` 是**内存 dict** —— 生产要换成真存储（你们的产物表）。

### F2 · 哪些状态由 LangGraph 保存，哪些由业务层管理 ✅ **已定**

> 要避免两个极端：把所有东西塞进 Graph State，或把所有东西都放进自己的数据库。

| 数据 | 建议归属 | 原因 |
|------|---------|------|
| 主 Agent 的对话历史 | Main Graph State | 属于会话执行上下文 |
| 当前主图的执行位置 | LangGraph Checkpointer | 属于图的恢复状态 |
| **Task ID、业务状态** | **Task 记录** | 属于业务生命周期 |
| 多个 Skill 共享的参数 | **Task 共享上下文** | 避免重复收集和参数分叉 |
| Sub Agent 的中间推理与执行状态 | 对应 Agent/Graph State | 属于执行者的内部状态 |
| **待处理的用户交互** | **业务交互记录**，并与相关执行状态关联 | 用于可靠路由和恢复 |
| 产物内容 | 产物存储 | 不应全部塞入对话状态 |
| 产物 ID、摘要、状态 | Task 结果记录 / Graph State 中的引用 | 方便后续使用和交付 |

> **LangGraph 的 Checkpointer 负责持久化图执行状态；业务层的 Task 记录负责表达任务的业务意义。
> 两者可以相互引用，但不应该被视为同一套状态。**

**另一个实现决策**：

> 一个 Task **不一定**需要一张独立 Graph，也不一定需要独立 `thread_id`。
> 简单任务可在主图中直接执行；需要跨多轮恢复的复杂任务可关联专门执行线程；
> 多个 Task 也可由同一主图协调。
>
> **但只要一个业务 Task 的状态可能跨多次执行持续存在，
> 就应该有一个稳定的业务身份，不能只靠某次模型调用的上下文识别它。**

### F3 · 中断与恢复策略 ✅ **已定**

**区分两种交互**：

**① 普通对话澄清** —— 不一定需要创建业务 Task。
若主图需暂停并在用户回答后继续，可用 LangGraph 的 `interrupt()` + Checkpointer 保存执行状态。

**② 复杂业务任务中的用户输入**（教案 Skill 已开始执行，发现缺必要参数）：
1. 将 Task 标记为 `waiting_for_input`
2. 记录缺少哪些信息，以及用户回答应该关联到哪个 Task
3. 通过 LangGraph 的中断机制暂停相关执行
4. 用户回答后，使用正确的执行标识恢复
5. 更新共享上下文，再继续推进任务

> 🔴 **不要把「用户回答后重新调用 Skill」与「恢复原来的 Graph 执行」视为同一件事。**
> 前者是**重新执行一次业务能力**；后者是**恢复已持久化的图执行状态**。
> 两种方式都可以合理存在，但**必须明确当前采用哪一种**。

**提醒**：恢复时**节点可能从头重新执行**，因此写文件、上传产物等有副作用的操作
**也需要考虑幂等性**。

**建议**：**先为最复杂的 Skill 做一个最小原型**，验证中断、恢复、父图状态和子图状态之间的关系，
**而不是直接重构所有 Skill**。
